## 2. 枚举可行性探针

### 2.1 深度

用最小字段集连续翻 200 页，每页 1,000 条。之所以不带 `expand[]`，是因为游标只与排序键和 `_id` 有关，
与返回哪些字段无关；字段开销单独在 §2.4 测。

| 量 | 实测 |
|---|---|
| 请求页数 | 200（页预算用尽，不是流结束） |
| 记录数 | 200,000 |
| 唯一 id 数 | 200,000（重复 0 条） |
| 满页（1,000 条）的页数 | 200 / 200 |
| `createdAt` 逆序违例 | 0 |
| 第 200 页是否仍有 `rel="next"` | 是 |
| 墙钟 | 21.7 秒 |
| 下载量 | 74.5 MB，每页中位 371 KB |
| 每页耗时 | 中位 0.103 秒，最大 0.388 秒 |
| 限流余量 | 498 → 299（200 次请求消耗 200 个额度） |

这 200,000 条覆盖的创建时间是 2026-08-18T15:19:59Z 到 2026-06-13T08:46:05Z，即最近约 66 天。

### 2.2 游标结构，以及为什么换排序键

按 `createdAt` 降序时，`Link: rel="next"` 里的游标解出来是：

```json
{"_id": {"$lt": "6a843c4a07a1157c55537d14"}}     // 第 0 页
{"_id": {"$lt": "6a2d18cdf9f1d089a22719e7"}}     // 第 199 页
```

作为对照，不指定排序（默认按 `trendingScore`）时是：

```json
{"$or": [{"trendingScore": 10451, "_id": {"$gt": "..."}},
         {"trendingScore": {"$lt": 10451}},
         {"trendingScore": null}]}
```

后者是建在可变字段上的复合 keyset，正是 R2 记录的 F-T2-9：`downloads` 天天在变，
翻页期间涨过游标位的模型会被跳过。前者只用 ObjectId，而 ObjectId 的前 4 字节就是创建时间戳，
所以 `createdAt` 降序与 `_id` 降序是同一个顺序，实测 200,000 条零乱序印证了这一点。

由此得到一条可以写进报告的性质：按 `createdAt` 降序枚举时，
枚举开始之前就存在的模型不会被跳过。枚举期间新建的模型 `_id` 更大，落在已经翻过的头部，因此不会被计入；
枚举期间被删除的模型直接消失。快照口径因此记为一个时间区间，而不是一个时刻。

### 2.3 全站规模估计

游标既然只是 `{"_id": {"$lt": X}}`，就可以为任意日期合成一个游标（`hex(unix_ts)` 加 16 个零），
把 API 变成创建时间轴上的随机访问探针。对 2022-01 起的每个月各取一页 1,000 条，
用这 1,000 条覆盖的天数得到该时点的日创建率，再沿时间轴梯形积分。

54 个采样点，估计值 **2.89×10⁶**。日创建率从 2022 年初的约 120 涨到 2024 年末的约 3,000，
2025 年后基本稳定在 2,500–3,000 之间。

这是估计不是计数，三个已知偏差：2022 年之前的模型没有计入（当时日创建率约 100 量级，
按两年计漏掉数万条，约占 1–2%）；已被删除的模型不在时间轴上；月度采样之间是线性插值。
最后一个采样点是不足一天的区间，率值偏高，但在积分里权重很小。

按 ±15% 计，F1 的规模应当落在 2.5–3.3 百万之间。真实值以 F1 枚举结束时的计数为准。

| 量 | 实测 |
|---|---|
| 每条记录 | 4,753 B（区间 4,386–5,950） |
| 每页 | 4.4–5.9 MB，0.268 秒 |

需要更正 R2 文档里的一个数：[`100k/100kplan.md`](100k/100kplan.md) §5.3 写「约 34 KB 每条」，

### 2.5 对 F1 的预测

## 3. 爬虫的排序参数

改动集中在 [`scale1m/hf_crawl.py`](../../scale1m/hf_crawl.py) 的单流模式：

- 新增 `--sort`（`downloads` / `createdAt` / `likes` / `lastModified` / `trendingScore`）
  与 `--direction`（`-1` / `1`），默认 `downloads` / `-1`，因此 v1 快照的复现路径逐字不变。
- 排序键与方向写进 `CURSOR.json` 与 `PROVENANCE.json`。续爬时若命令行给的排序与 `CURSOR.json` 里存的不一致，
  直接退出码 2 并说明原因。这不是洁癖：两种排序的游标指向不同的流，混在同一批分片里会得到一个既不是全量、
  也不是前缀的集合，而且不会报错。
- 单流模式原本以 `n_written >= --limit` 作为成功条件，全量枚举达不到 `--limit`，会被判成失败。
  改为「达到 `--limit` 或游标耗尽」都算正常终止，并把 `exhausted_cursor` 写进 `PROVENANCE.json`。
- 进度行改为显示当前排序键的值，`stats` 里同时记 `last_created_at` 与 `last_sort_value`。
- `main()` 拆出 `build_parser()`，使默认值可以被单测直接检查。

新增四个单测（`scale1m/tests/test_hf_crawl.py`）：默认排序仍是 `downloads` / `-1`；
`--sort createdAt` 可用而无效值被拒；全量枚举在游标耗尽时返回 0 且 `PROVENANCE.json` 记录正确；
续爬遇到排序不一致时返回 2。

F1 的调用形式：

```bash
C=$MLF_DATA_DIR/data1m/candidates_full
python -m scale1m.hf_crawl --sort createdAt --direction -1 \
       --limit 100000000 --v2-fields --shard-size 50000 --out $C
```

## 4. 图拆件与内存映射

新增 [`scale1m/graph_store.py`](../../scale1m/graph_store.py)。目录布局：

```
x_model.npy    [N, 448] float32     加载时内存映射
x_dataset.npy  [D, 458] float32     加载时内存映射
nodes.npz      其余节点整数列
edges.npz      每种关系的 edge_index / edge_attr / relation_id
unique_model_id.parquet, unique_dataset_id.parquet
meta.json      xm0_meta、xd0_meta、provenance、每个张量的形状与 dtype、每个文件的 sha256
```

`meta.json` 为每个文件记 sha256，加载时可选校验，因此被截断或被替换的分片在加载时就暴露，
而不是变成一个奇怪的指标。

### 4.1 在真实 100K 图上的验证

| 检查 | 结果 |
|---|---|
| 转换 | 223.4 MB 的 `.pt` → 6 个文件共 220.0 MB，耗时 0.4 秒 |
| 逐张量比对 | 全部相同，包括 dtype、形状、五种边的 `edge_index`/`edge_attr`/`relation_id` |
| `xm0_meta` / `xd0_meta` / 两张 id 表 | 逐项相同 |
| Stage-2 契约检查（`--sharded`） | CONTRACT OK，与在 `.pt` 上的逐条判定相同 |

契约检查里包含一次完整的前向反向，因此它同时回答了一个不测就不知道的问题：
只读的内存映射张量能不能走完前向反向。能，两张 embedding 表梯度非零、frozen `x` 无梯度，
`z_m` 仍是 100,000 行。副作用是 torch 会对不可写数组发一次 `UserWarning`，属预期，
因为流程中没有任何一处写 `x`。

### 4.2 加载时的常驻内存

同一台机器，每种方式各起一个新进程，用 `psutil` 的 `peak_wset` 减去导入完成后的基线：

| 加载方式 | 峰值增量 | 说明 |
|---|---|---|
| `torch.load` 单文件 `.pt` | +243.3 MB | 全部张量一次性materialize，另有反序列化缓冲 |
| 拆件 + 内存映射 | **+50.3 MB** | 两个 `x` 留在磁盘上按需分页 |
| 拆件 + 内存映射，随后遍历 `x` 的全部行 | +237.8 MB | 触碰全部行后自然回到同一量级 |
| 拆件但不映射（`--no-mmap`） | +247.3 MB | 与 `.pt` 相当，说明省下的确实来自映射而不是格式 |

要如实说明的一点：训练一个 epoch 会触碰几乎所有行，所以稳态常驻内存不会比 `.pt` 少多少。
拆件真正解决的是三件事：加载瞬间的峰值（243 MB → 50 MB，全量档按线性外推是 5.2 GB → 约 0.3 GB）；
页面是文件支撑的、系统在内存紧张时可以回收，而 `torch.load` 产生的是私有匿名页
（实测私有提交量 1,992 MB 对 1,865 MB）；以及不需要在 `x` 之外再留一份反序列化缓冲。

冷启动读取时间没有单独测：首次加载 `.pt` 实测 7.5 秒，重复加载因系统文件缓存降到 0.1 秒，
映射方式则把这部分读取推迟到实际取行的时候。这个量在全量档上才有意义，留给 F5 实测。

### 4.3 单测

`scale1m/tests/test_graph_store.py` 六条：往返逐张量相同且 dtype 不变；
特征以 float32 存盘（防止有人日后顺手改成 fp16）；映射开关与取值正确；
截断分片被 sha256 抓到；`compare()` 能报出真实差异（一个不会失败的比对不是检查）；
`meta.json` 覆盖目录里的每个文件。

全套 `scale1m/tests` 167 项通过。

## 5. 与计划的偏离

| # | 计划原文 | 实际 | 理由 |
|---|---|---|---|
| 1 | F0 补做 `plan.md §4` 第 9 项：特征存 fp16、前向转 fp32 | **不做，特征保持 float32** | 用户 2026-08-18 定。`x` 是模型输入里被冻结的那一半，也是整条梯子跨档保持逐字节相同的那一个量（约束 1）；存储格式不是引入数值差异的地方。省内存改由内存映射实现，不牺牲精度。登记为 D-55 |
| 2 | 深度探针用真实字段集 | 深度用最小字段集，另测 5 页真实字段集 | 游标只与排序键和 `_id` 有关，与 `expand[]` 无关。拆成两问省掉约 1 GB 下载，且两个问题各自答得更干净 |
| 3 | 计划没有要求估计 N | 增加了规模估计（§2.3） | F1 的时间、磁盘与分片数都要按 N 折算，量级从「未知」变成「2.9M ± 15%」才能提资源申请 |
| 4 | 契约检查按原样在 `.pt` 上跑 | 给 `check_stage2_contract.py` 加了 `--sharded` 入口 | 只读映射张量能否走完前向反向是个真问题，不实际跑一次就不知道 |
