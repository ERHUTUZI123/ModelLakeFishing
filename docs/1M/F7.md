## 2. 预注册对照

两条都在 §6 写下的区间内，没有需要事后解释的地方。

| 预注册（§6） | 区间 | 实测 | |
|---|---|---|---|
| `median rank / N` 是主指标 | [1e-5, 5e-3] | 2.92e-4 / 6.33e-4 / 1.11e-3 | 命中 |
| `gold@10` | [0.005, 0.15]，且 `vs random ≥ 10³` | 0.0399 / 0.0696 / 0.0700，vs random 1.2–2.1 万 | 命中 |
| HNSW p50 外推 | 约 0.018 ms | 0.0167–0.0196 ms（本机，见 §7） | 量级相符 |
| 索引磁盘外推 | 约 2.2 GB | 2,209.3 MB | 相符 |

`gold@10` 落在预注册区间内，所以按 §6 的规定不需要去查候选池、查询自看监督边、RL 混入
这三处——那三条是为「高于上界」准备的。候选池断言本来就每次都跑（G-F7a）。

一个此前没有答案的问题现在有了：`ef_search` 在 3M 上没有升高。100K 档三档都停在 52/52/50，
本档在全湖与四个子采样档上一律是 50，也就是 `ef = K` 的下界，而 recall 仍在 0.998 以上。
§6 设想的「规模开始逼出 ANN 的代价」在这个规模上没有发生。

按每 10 万模型折算，索引是 73.3 MB，与 100K 档实测的 73.2 MB 相同——索引开销随 N 线性，
没有隐藏的超线性项。

## 3. 两个候选池

`rf-gold-2.0` 冻结了一条报告义务：每个 A 轴数字都要按全体候选与仅存活候选各报一遍。
梯子把快照保持为精确前缀（F3），所以「仅存活」就是把 `z_m` 截到前 3,003,759 行。

| seed | 全体候选 N=3,016,439 | | 仅存活 N=3,003,759 | | |
|---:|---:|---:|---:|---:|---:|
| | 查询 | gold@10 | 查询 | gold@10 | 落选查询 |
| 0 | 1,558 | 0.0700 | 1,003 | 0.0229 | 555 |
| 1 | 1,153 | 0.0399 | 752 | 0.0532 | 401 |
| 2 | 1,595 | 0.0696 | 636 | 0.0613 | 959 |

两列不是同一批查询，因此不能当作「去掉 12,680 个干扰项之后的变化」来读。
限制候选池会让一部分查询失去可比的候选：seed 0/1/2 各有 567 / 324 / 1,002 个查询的最优模型
本身就在快照外，落选是按建候选集时的同一条规则重新判定的（存活候选少于 3 个，或它们的
取值恒定）。落选比例 35%–60%，远高于 12,680 / 3,016,439 = 0.42% 的候选池变化——
原因是那 12,680 个模型正是历史监督覆盖的那批，在 gold 里的密度远高于湖里的平均密度。

方向上三个 seed 不一致（一降两升），这与「两批不同查询」的解释一致，不能解读为存活模型更容易或更难。
F8 报 A 轴时两列都要给，并且要写明查询集不同。

## 5. 检索侧 scaling 曲线的索引

§3.5 要求每个 N 与三个抽样 seed 各一个索引，且子集必须包含全部带监督的模型。
实现上先取「带监督模型 ∪ 全部 gold 候选」共 **46,146** 行固定保留，再在其余无标签模型里均匀抽样。
索引的 label 用原始 `mappedID`，所以 gold id 在任何一个子集里都仍然有效。

| N | 抽样 seed | `ef_search` | recall@50 | 建索引 | 磁盘 |
|---:|---|---:|---|---:|---:|
| 100,000 | 0 / 1 / 2 | 50 | 0.9985 / 0.9987 / 0.9987 | 0.8–0.9 s | 75 MB |
| 250,000 | 0 / 1 / 2 | 50 | 0.9985 / 0.9985 / 0.9984 | 3.0–3.1 s | 188 MB |
| 500,000 | 0 / 1 / 2 | 50 | 0.9983 / 0.9986 / 0.9985 | 7.8–7.9 s | 376 MB |
| 1,000,000 | 0 / 1 / 2 | 50 | 0.9984 / 0.9986 / 0.9988 | 18.2–18.7 s | 752 MB |
| 3,016,439 | 全量 | 50 | 0.9986 | 64.7 s | 2,209 MB |

全量那一行不是在这一步重建的，它就是 §1 里那个服务索引，`ef` 与 recall 的口径相同。
曲线的五个点因此是同一份 `z_m` 的五个候选宇宙，训练侧没有任何变化——这正是 §3.5 想要的受控设置。

建索引时间随 N 线性（3M / 100K = 30.2 倍对 64.7 s / 0.85 s = 76 倍，超线性来自 M=32 时
邻居搜索的 log 项，但仍远低于二次）。

## 6. 实现

新写 [`scale1m/export_rf.py`](../../scale1m/export_rf.py)，分四个阶段，各自独立进程：

| 阶段 | 做什么 | 峰值内存来源 | 实测 |
|---|---|---|---|
| `embed` | 加载图与 checkpoint，两次分块前向，写四个矩阵与 gold 候选集 | 图 | 55.8 / 57.1 / 72.1 s |
| `metrics` | 只读矩阵，两个候选池各算一遍，跑泄漏门与 harness 对账 | z 矩阵 | 26–33 s |
| `index` | 建全湖 HNSW，二分 `ef` 到 iso-recall | 索引 2.2 GB | 110–113 s |
| `curve` | 12 个子采样索引 | 单个子索引 | 合计 113 s |

分阶段不是洁癖。`z_m` 是 1.54 GB，索引是 2.2 GB，图的 `x_model.npy` 是 5.41 GB，
本机可用内存装不下同时驻留的组合，而 `export_rung.py` 是在一个进程里做完全部四件事的。

没有沿用 `export_rung.py` 的另外三个原因：它读单文件 `.pt` 图、用 `sha256_of` 校验绑定
（对目录会抛异常）、读 CSV 梯子。所有决定数字的部分都没有换：同一个 `build_models`、
同一个 `chunked_forward`、同一个从 checkpoint binding 里读 `split_seed` 的
`make_root_aware_splits`、同一个 `five_metric_eval` 与 `global_metrics`、
同一个带 iso-recall 调参的 `build_hnsw`。

绑定检查在花任何算力之前先跑：checkpoint 记的图摘要与 `graph_digest(hgraph_rf)` 不符就直接停。
三份 checkpoint 都对上 `0e80b839…`。

新增 [`scale1m/tests/test_export_rf.py`](../../scale1m/tests/test_export_rf.py) 九条，
覆盖三个会静默失败的地方：行序门能抓到任意位置的一次交换、泄漏门是不等式而不是注记、
子采样的保留规则按 `model` 而不是按顺序做连接。仓库合计 **307 passed**。

## 7. 与计划的偏离

| # | 计划原文 | 实际 | 理由 |
|---|---|---|---|
| 1 | F7 在 watGPU 上跑（D-67） | 本地 | 本会话没有 watGPU 的 SSH 私钥（`Permission denied (publickey)`），而所需三件——三份 checkpoint（169 MB，F6 已回收）、拆件图、`hnswlib` 与 `faiss`——本机都在。代价见下 |
| 2 | 用 `export_rung.py` | 新写 `export_rf.py`，分四阶段 | 见 §6 |
| 3 | 分块推理 `batch_size=100_000` | 50,000 | 内存换稳，与 F6 训练里 `--chunked-infer 50000` 取同一值 |
| 4 | 产物在 `$OUTPUT_ROOT/runs/<RUN_ID>/exports/` | `data1m/exports_rf/<RUN_ID>/` | 20 GB 的二进制不应该放进 `docs/`；`F7_runs/` 只留 JSON 报告 |
| 5 | 曲线含全量那一档 | 全量档复用服务索引 | 同一份向量、同一套 `ef` 口径，重建一次只是多花 65 秒和 2.2 GB |

第 1 条的代价必须写清楚：**本文报的 HNSW 延迟是本机（RTX 4060 笔记本，24 逻辑核）的数，
而 100K 档的 B 轴是在 watGPU 上测的，两者不能并排比较。**
F8 的 B 轴有两条合法路径，二选一并写明：要么把全部档位在同一台机器上重测一遍，
要么只报同机测得的「HNSW 对全扫」的加速比——比值对机器不敏感，绝对值敏感。
本阶段没有测全扫基线，那是 F8 的事。

F7 的其余产物不受机器影响：嵌入是确定性的前向，索引与 `ef` 是在同一份向量上算的，
`recall@50` 与磁盘占用都与机器无关。
