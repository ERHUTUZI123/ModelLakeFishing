## 1. 结论

在 root-aware 协议下无法触发的 S2 兄弟先验，在 node-level 协议下是有效的，
而且比预注册时估计的更强。在能触发它的那一层查询上，
`gold@10` 从纯 MIPS 的 0.0678 提到只用兄弟先验的 0.2866，三 seed 均值 4.2 倍。

更有实用意义的一条是增量：兄弟通道加在已经采纳的 task 先验之上，
全部查询的 `gold@10` 从 0.3009 提到 0.3536，提升 17.5%；
在有兄弟的那一层上从 0.3251 提到 0.3975，提升 22.3%。
也就是说这两条通道不是同一件事的两种说法，兄弟通道带来的信息 task 先验没有覆盖。

代价同时变大。top-10 的参数量中位数从 2.42 B 涨到 12.11 B，
`at_least_one_feasible@10` 从 0.9118 降到 0.7615。
X2 里 task 先验单独造成的体积膨胀是 3.1 倍，这里是 5.0 倍。
先验越强，推荐越集中在被反复评测过的大模型上，这条代价随之等比例增长。

兄弟通道里约一半来自名字与查询相近的兄弟配置。
把名字 3-gram Jaccard 大于 0.5 的兄弟从先验里去掉，
有兄弟那一层的 `gold@10` 从 0.2866 降到 0.1532。
这不是泄漏修正，因为同一 benchmark 的不同配置正是这个协议要表示的服务场景，
但它说明这条通道的强度对「兄弟有多像」很敏感，报数字时应当带上这一行。

## 2. 两个协议

root-aware 协议的划分单位是 root：某个 root 下所有数据集的 `trained_on` 边整体落在一侧。
它对应的服务场景是「查询来自一个系统从未见过的 benchmark 家族」，
是三种场景里最难的一种，应当继续作为主协议报告。

它同时让 S2 完全不触发。D 被划到 test 侧时，D 所在 root 的其它配置也一并划过去，
所以 D 没有任何训练可见的兄弟。X1 §9 在三个 seed 的全部查询上测到这个数是 0，
X2 把它写成了 P 轴里的一条断言。

被排除掉的场景并不罕见。18,729 个数据集节点里有 11,313 个（60.4%）落在含至少两个节点的 root 内，
三个 seed 的查询里分别有 1,029 / 778 / 1,239 个（66.0% / 67.5% / 77.7%）属于这种情况。
对这些查询，真实的服务场景是「一个已知 benchmark 家族的新配置」。

第二协议 node-level 把划分单位改成数据集节点：对查询 D 而言，
先验可以读除 D 自身以外的全部边，D 的兄弟因此可见。

## 3. 这次改了什么，没改什么

审计规定顺序 3 不改训练也不改索引，这条约束决定了实现方式。

完整的 node-level 重跑需要按节点重新划分并重新训练。这次没有那样做，原因需要说清楚。
现有嵌入是在 root-aware 划分下训练的。node-level 的查询集里会包含一些数据集，
它们所在的 root 在 root-aware 划分中位于训练侧，因此模型见过这些数据集自己的标签。
用现有嵌入去评这样的查询集会泄漏。

所以第二协议只定义在服务侧：

- 查询集仍是 root-aware 的 test 查询集。在两个协议下，模型都没有见过这些数据集的标签。
- 嵌入仍是 F7 冻结的 `z_*_eval`。
- 索引没有重建也没有使用，全部名次在 3,016,439 个模型的完整候选池上计算。
- 只有「先验被允许读哪些边」这一件事发生变化。

由此产生两个方向相反的偏差，报告时需要同时说明。
检索侧从未见过兄弟边，所以协议 B 的嵌入部分比一个真正按 node-level 训练的系统更弱，
这一半是下界。先验侧则拿到了真正的 node-level 划分会放进自己验证集与测试集的一部分标签，
所以先验这一半是上界。两者不能相互抵消，本次也不声称测到的就是完整 node-level 重跑会给出的值。

## 4. 实现

先验的两个通道沿用 `stage3HNSW/serving_rerank.py`，没有修改：
兄弟先验是组内归一化精度的平均值（不收缩），
task 先验是收缩平均值（k = 5），融合分数为

```
fused(D, m) = minmax(z_d[D] · z_m)[m] + alpha · sibling_boost(m) + beta · task_boost(m)
```

alpha = beta = 1，min-max 在全湖上取，与参考实现一致。

先验的边集来自两份 sidecar。协议 A 用 X2 建的按 seed 的 sidecar（train + val 边）；
协议 B 用不带 `--split-seed` 的完整 sidecar（全部 247,803 条边），
查询自身的边在算 boost 时逐条减掉。三个 seed 的数据集 id 表相同，
所以完整 sidecar 建一次即可服务三个 seed。

减掉查询自身贡献的做法是先按组预聚合、再减去 D 的那一部分，
比每个查询重新遍历整组快得多。这个写法与「按数据集列表逐条重建」的结果
在随机抽取的 6 个查询上逐元素相同，兄弟组与 task 组都对上。

运行命令：

```
python -m ModelLakeFishing.stage3HNSW.build_prior_sidecar \
    --graph-store <DATA>/data1m/graphs/hgraph_rf \
    --export <DATA>/data1m/exports_rf/RF_full_s0_e25 \
    --task-nodes <DATA>/data1m/rf/canon/dataset_nodes_merged.parquet
python -m scale1m.eval_rf --axis s
```

三个 seed 共 659.8 秒。

## 5. 结果

七条排序，三个 seed，完整候选池。下面给 `gold@10` 的三 seed 均值，
按预注册的三个分层排列。分层的定义是 D 所在 root 内是否还有别的、
在完整图上至少带一条 `trained_on` 边的数据集节点。

| 排序 | 兄弟先验来源 | task 先验来源 | 全部查询 | 有兄弟 | 无兄弟 |
|---|---|---|---:|---:|---:|
| 纯 MIPS | 无 | 无 | 0.0598 | 0.0678 | 0.0418 |
| A：task | 无 | V_A | 0.3009 | 0.3251 | 0.2551 |
| B：兄弟 | 全部兄弟 | 无 | 0.2145 | 0.2866 | 0.0418 |
| B：兄弟（仅名字不相近） | 名字不相近的兄弟 | 无 | 0.1209 | 0.1532 | 0.0418 |
| B：兄弟 + task(A) | 全部兄弟 | V_A | 0.3536 | 0.3975 | 0.2551 |
| B：task | 无 | task(B) | 0.3744 | 0.4163 | 0.2622 |
| B：兄弟 + task(B) | 全部兄弟 | task(B) | 0.4314 | 0.4961 | 0.2622 |

分层规模是 1,029 / 778 / 1,239（有兄弟）与 529 / 375 / 356（无兄弟）。
逐 seed 的值、其余 k 值、`top3@10`、`gold-gap@10` 与中位名次都在
`X3_PROTOCOL_B.json` 里，本节只取有结论的部分。

三件事可以从这张表读出来。

第一，兄弟通道单独就能把有兄弟那一层的 `gold@10` 从 0.0678 提到 0.2866，
中位名次在 seed 0 上从第 2,262 位提到第 68 位。
这条通道在当前唯一报告的协议下是完全看不到的。

第二，兄弟通道与 task 通道互补。把兄弟加在协议 A 的 task 先验之上，
全部查询从 0.3009 到 0.3536，有兄弟那一层从 0.3251 到 0.3975。
在 D0 上 v6 测到的对应增量是 0.239 到 0.261，约 9%；
全量档上是 22%，方向一致而幅度更大。

第三，`B：task` 这一行不能与前面几行同等看待。
它的 task 先验读的是完整 sidecar，包含真正的 node-level 划分会自己留作验证与测试的那部分标签，
所以它是先验侧的上界。seed 2 上这一行尤其高（有兄弟层 0.5165），
原因是 seed 2 的协议 A task 池本来就很小（X1 §1 测到同任务池中位只有 6 个模型），
放开限制后补进来的标签特别多。要报一个可辩护的 node-level 数字，
应当用 `B：兄弟 + task(A)` 那一行，它只放开了兄弟这一处。

无兄弟那一层给出一条内部一致性检查：在该层上，
`B：兄弟` 与纯 MIPS 的每一个指标逐位相同，
`B：兄弟 + task(A)` 与 `A：task` 逐位相同。没有兄弟的查询拿到全零的 boost，行为应当如此。

## 6. 名字相近兄弟的敏感性

兄弟共享 root，名字往往相近。把与 D 的名字字符 3-gram Jaccard 大于 0.5 的兄弟从组里去掉后，
有兄弟那一层的 `gold@10` 从 0.2866 降到 0.1532，三个 seed 分别是
0.3178 到 0.1341、0.2288 到 0.1440、0.3132 到 0.1816。
被去掉的兄弟数中位数是 1 / 1 / 6。

这一行是敏感性分析，不是泄漏修正。同一 benchmark 的不同配置正是协议 B 要表示的场景，
把它们算作泄漏就等于取消了这个协议本身。
它说明的是另一件事：这条通道的强度大约有一半来自「兄弟与查询高度相似」的那部分，
所以在兄弟差异较大的服务场景里，实际收益会明显低于表里的 0.2866。

三个 seed 的兄弟池规模差别也很大，模型数中位数分别是 11 / 15 / 83，
p90 是 395 / 1,183 / 244。seed 2 的兄弟池普遍更大，这与它的兄弟通道相对更强是一致的。

## 9. 与预注册的对照

预注册第 5 节记的预期是：兄弟先验会把有兄弟那一层的 `gold@10` 相对纯 MIPS 提高一到两倍，
并且不会明显强于 task 先验。

第一半没有命中。实测是 4.2 倍，超出预注册区间约一倍。
预期是照 v6 在 D0 上的 1.64 倍写的，没有考虑到全量档的纯 MIPS 基线低得多
（D0 有兄弟层是 0.158，全量档是 0.0678），同样的绝对提升在这里对应更大的倍数。

第二半命中。兄弟先验单独是 0.2866，协议 A 的 task 先验是 0.3251，兄弟仍然稍弱。

预注册的七条排序、三个分层、第二层的三行全部照原样报告，没有增删。

## 10. 局限与未决

现有嵌入是在 root-aware 划分下训练的，协议 B 的检索侧因此偏弱，
真正按 node-level 训练之后兄弟边会进入消息图，检索侧本身也会变。
这次没有测那件事，它需要重训，属于 GPU 配额范围内的工作。

`B：task` 一行读了真正的 node-level 划分会留作验证与测试的标签，是先验侧的上界。
本文所有需要一个可辩护数字的地方都用 `B：兄弟 + task(A)`。

第 6 节的名字相似度只能识别名字相近的兄弟。名字完全不同、实为同一批数据的兄弟配置，
这个方法看不到，接通道时仍应按数据来源再核一次。

主协议不变。root-aware 继续作为主协议报告，协议 B 作为第二套口径并列给出，
两者对应的服务场景在第 2 节写明。这次没有、以后也不应当在看到数字之后改选其中一个报。
