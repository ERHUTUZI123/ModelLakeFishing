## 4. 两处为本机内存做的改动

本机总内存 16.9 GB，跑之前只有 **4.0 GB 可用**，而 `x_m` 本身就是 5.41 GB。
原实现把矩阵在内存里拼好再 `np.save`，会直接失败。改了两处：

**特征矩阵用 memmap 分块写盘。** `np.lib.format.open_memmap` 先在磁盘上开出
`[3016439, 448]`，`e_name` 每 25 万行算一批写进去，`e_desc` 从分片里逐块拷贝。
全过程常驻内存不超过几百 MB。这与 D-55 的思路一致：保 float32，省内存靠映射而不是降精度。

**描述符按分片生成。** 三百万个 Python 字符串约 330 MB，没有必要与矩阵同时驻留。
现在每个分片生成一次、编码完即丢，只把长度与子句标志留下来算统计量。

顺带把门禁也改成分块的：`np.isfinite(x).all()` 与逐行范数在 5.41 GB 上都会临时翻倍，
现在按 25 万行一块算。

| # | 判据 | 结果 |

| 1 | 形状 `[3016439, 448]` | 通过 |
| 2 | 无 NaN 与 Inf | 通过 |

| 5 | 行序抽样覆盖追加段 | 通过，200 行里 **100 行来自尾段** |

第 4、5 条是本阶段最重要的：`x_m[i]` 必须属于梯子里 `mappedID == i` 的模型，
而 F3 在梯子尾部追加的 12,680 行是新引入的、最容易被错接的一段。
门禁从快照段与追加段各抽 100 行，按 id 重算 `e_name` 与矩阵前 64 维比对，
两段都是逐位相同。

## 7. 描述符的形态

| 口径 | 行数 | 平均字符 | 中位 | 带 size 子句 | 带 family 子句 |
|---|---|---|---|---|---|
| 全湖 | 3,016,439 | 55.3 | 53 | **28.07%** | 100% |
| 快照段 | 3,003,759 | 55.3 | 53 | 28.19% | 100% |
| 追加段 | 12,680 | 47.1 | 44 | **0.00%** | 100% |

追加段的 size 子句是精确的 0：那 12,680 个模型没有 HF 记录，因此没有 `safetensors.total`，
按 D-26 也不从名字猜。这是 F3 §3 预告过的结果，现在被实测确认。
它们的描述符平均短 8.2 个字符，这一条要留在 F8 的分层归因清单里。

`x` 的行范数均值 1.0815，区间 [1.0076, 1.4142]。量级正确：
`e_name` 是单位向量的哈希平均，`e_desc` 是未归一化的 MiniLM 输出，拼起来略大于 1。

抽样看描述符原文（`descriptors_head.txt`）：

```
zoarag evilpeterpan family evilpeterpan
lie24 qwen38 mtp head q2q4 cons family qwen
...
δ vs gemma 3 family gemma
π0 family Other
```

**一个要写进报告的观察**：`family` 子句覆盖率是 100%，但 `family_id` 有 13.56% 落在 `Other`。
两者不矛盾——描述符里放的是 family 字符串原文，而 id 走 `FAMILY_MIN_COUNT=3` 的折叠。
上面第一行的 `family evilpeterpan` 就是名字规则给单个模型造出来的家族串：
它进了文本，却不会有自己的嵌入行。全湖有 414,478 个不同的 family 字符串（F3 §5），
意味着 `e_desc` 里带着大量近乎唯一的 token，而 `e_fam` 看不到它们。
这不是缺陷，是既有设计在这个规模上的表现，但 C 轴归因时要把它算作一条通道。
