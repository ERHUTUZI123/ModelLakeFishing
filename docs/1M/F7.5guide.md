# D 轴：Incomplete Gold 下的真实推荐质量评估

## 1. 要回答的问题

A 轴目前使用已有评测记录定义 gold，并测量：

> 在一个数据集查询下，已有观测中表现最好的模型能否进入检索 top-k？

这个指标是必要的，但它只评价 **observed gold recovery**。

这里存在一个重要问题：

**没有出现在 gold / labeled evaluation records 中的模型，并不能直接视为错误推荐。**

Hugging Face 上的评测记录非常稀疏。一个模型可能：

* 实际适用于这个任务；
* 与已知高性能模型有很强的架构、训练数据或 lineage 关系；
* 甚至真实性能优于 observed gold；
* 但从未有人在该 dataset / task / metric 上公开记录结果。

因此 D 轴需要研究：

> **检索出的高排名 non-gold 模型究竟是真的 irrelevant，还是只是 unlabeled？**

换句话说，D 轴不再问“有没有把历史答案找回来”，而问：

> **如果真的按照系统推荐去选择模型，这些模型的实际质量如何？**

---

## 2. 首先明确统计语义

不要继续把所有 non-gold 当成 negative。

更准确地把候选模型分成三类：

1. **Observed positive**

   * 在该 dataset/task 上存在评测记录；
   * 并且属于 gold / top-performing observed models。

2. **Observed inferior**

   * 在该 dataset/task 上存在评测记录；
   * 但性能明确低于 gold。

3. **Unobserved**

   * 对该 dataset/task 没有评测记录。
   * 真实性能未知。

A 轴中第 2、3 类目前都会导致 retrieval metric 下降，但它们的语义完全不同。

D 轴首先应统计 top-k 返回结果中这三类分别占多少。

例如：

```text
Top-10 composition:
observed gold        6%
observed non-gold   18%
unobserved          76%
```

如果绝大部分“错误”其实是 unobserved，那么应该明确说明：

**A 轴测到的主要是 annotation coverage，而不完全是 recommendation error。**

但不要仅凭这个事实推断 unobserved 模型很好。D 轴的核心任务就是进一步验证它。

---

## 3. 最重要的实验：对 top-ranked unobserved candidates 获取新 label

优先考虑是否能够对一部分检索出的 unobserved 模型进行真正的重新评测。

这是最有说服力的 D 轴。

不要尝试评测整个 3M 模型池。目标应该是做一个统计上可解释的 audit。

建议从测试查询中抽样，例如：

* 固定随机抽取若干 query；
* 每个 query 取：

  * top-1 unobserved；
  * top-3 / top-10 中若干 unobserved；
  * 随机候选作为 control；
  * 已知 gold 作为 calibration。

然后真的运行对应 dataset/task 的 evaluation。

核心问题是：

> **系统挑出的 unlabeled candidate，真实性能是否显著高于随机模型？**

以及：

> **它与 observed gold 的性能差距是多少？**

可以定义类似：

### D1. Newly evaluated success rate

对于原本没有 label 的 top-k candidate：

```text
P(new candidate ≥ threshold)
```

threshold 可以是：

* observed gold 的 90%；
* observed top-3 的最低性能；
* 某个合理 task-specific baseline；
* 或 percentile-based threshold。

不要只用 exact-best，因为模型选择通常不需要找出唯一第一名。

---

## 4. 比 exact gold 更有意义的 utility 指标

D 轴应考虑直接衡量推荐模型的实际性能，而不是 binary hit。

例如对 query (q)，系统返回最高排名的可实际评测模型 (m_r)。

定义：

[
U(q)=\frac{P(m_r,q)}{P(m^*_q,q)}
]

其中：

* (P(m_r,q))：推荐模型真实表现；
* (P(m^*_q,q))：已知或重新测出的最佳表现。

可以报告：

* mean utility ratio；
* median utility ratio；
* regret：

[
R(q)=P(m^*_q,q)-P(m_r,q)
]

这样能够回答：

> “虽然 exact gold@10 只有 6%，但实际 top-ranked recommendation 平均达到了 best-known performance 的 96%。”

如果最终出现这种结果，它比 gold@10 本身更能说明模型选择系统的价值。

---

## 5. Near-optimal relevance，而不是唯一 gold

检查现在的 gold 定义是否过于严格。

例如：

```text
Model A: accuracy 91.4
Model B: accuracy 91.3
Model C: accuracy 91.1
```

如果 A 是 gold，而系统返回 B，那么 `gold@10 = 0`，但这在实际模型选择中几乎不能称为失败。

因此考虑增加 tolerance-based relevance。

例如：

[
Relevant_\epsilon(m,q)
======================

P(m,q) \geq P^*(q)-\epsilon
]

或者：

[
P(m,q) \geq \alpha P^*(q)
]

然后计算：

* near-optimal@1；
* near-optimal@10；
* regret@k；
* top-k 中最佳真实 performance。

需要研究合理的 (\epsilon) 应该如何定义。

不要随意选择一个对结果最有利的 epsilon。最好：

* 根据 metric 的自然尺度；
* 或报告多个阈值；
* 例如 1%、2%、5% performance gap。

---

## 6. 特别分析 “false negative”

定义一种案例：

> A 轴认为 retrieval 失败，但 D 轴重新评测发现推荐模型实际上非常优秀。

例如：

```text
Query: dataset X

Observed gold:
Model A = 84.2

Retriever:
1. Model B [unobserved]
2. Model C [unobserved]
...
8. Model A

Fresh evaluation:
Model B = 85.1
Model C = 84.0
```

按照 A 轴：

```text
gold rank = 8
```

但事实上 Model B 比 historical gold 更好。

这种案例非常有价值。

统计：

[
FalseNegativeRate
=================

P(\text{retrieval counted wrong by A but recommendation is near-optimal})
]

这可以直接量化 incomplete ground truth 对 A 轴的低估程度。

---

## 7. 建立一个小规模 Dense-Judgment Benchmark

如果计算资源允许，考虑从大 benchmark 中选择一小部分 query，构造一个更加完整的 evaluation subset。

例如：

```text
D-dense:
50–200 queries
×
若干 carefully sampled candidate models/query
```

候选可以来自：

* 当前方法 top-k；
* strongest baseline top-k；
* random；
* popularity baseline；
* known gold；
* lineage-neighbor；
* embedding-neighbor。

然后对这些候选统一获得新的 evaluation result。

这样得到一个小但相对 dense 的 relevance matrix。

它的作用不是替代 3M-scale benchmark，而是校准：

> sparse historical gold 对 retrieval quality 的测量偏差到底有多大。

这是一个很适合论文的双层 benchmark：

```text
A axis:
3M-scale, sparse but realistic historical observations

D axis:
small-scale, expensive but much denser newly evaluated judgments
```

两者回答不同问题。

---

## 8. 必须设置 control，避免只证明“我们自己的结果很好”

D 轴一定要包含 baseline retrieval 的 unobserved candidate。

否则实验容易变成：

> 我们从自己的 top-10 中挑模型重新测，然后发现其中一些不错。

这没有足够说服力。

需要比较类似：

```text
Our retriever top-ranked unlabeled
vs
BM25 / text embedding top-ranked unlabeled
vs
popularity baseline
vs
random candidate
```

比较 fresh evaluation performance。

如果我们的 unobserved candidates 显著优于 baseline 和 random，才真正证明 retrieval embedding 捕捉到了 latent utility。

---

## 9. 注意 selection bias

不要只挑“看起来像是会成功”的案例。

sampling protocol 必须在看结果之前固定。

Claude 应设计一个 deterministic protocol，例如：

```text
固定 split seed
→ 从 test queries 均匀随机抽 N 个
→ 对每个 query 取 predetermined rank positions
→ 过滤技术上无法运行的模型
→ 按事先定义的 replacement rule 补齐
→ 全部执行
```

记录：

* 为什么某个模型无法评测；
* gated / unavailable / incompatible / too large；
* 失败率是否与方法相关。

不要静默删除失败案例。

---

## 10. “模型可用性”也可以成为 D 轴的一部分

实际推荐系统不只关心 accuracy。

对于一个模型湖 retrieval system，推荐出的模型还应该考虑：

* 模型是否仍然可下载；
* 推理框架是否兼容；
* parameter count；
* model size；
* license；
* gated/private；
* latency / hardware feasibility。

因此可以考虑把 D 轴最终定义得稍微广一点：

> **Recommendation Utility**

而不是单纯 fresh accuracy。

但不要一开始就创造复杂 composite score。

首先把最核心的问题回答清楚：

**unobserved top-ranked models 的实际 task performance 是否优秀？**

其他 practical utility 可以作为附加分析。

---

## 11. 可以尝试回答的几个核心研究问题

Claude 在设计 D 轴时，围绕下面几个问题展开：

### RQ-D1

**How incomplete is the observed gold?**

即：

top-k 中有多少模型只是没有历史 label，而非已知低质量模型？

### RQ-D2

**Are retrieved unlabeled models actually useful?**

fresh evaluation 后，我们的 top-ranked unlabeled candidates 是否显著优于 random / baseline？

### RQ-D3

**How much does sparse gold underestimate retrieval quality?**

比较：

```text
historical gold@k
vs
dense/fresh relevance@k
```

差异有多大？

### RQ-D4

**Does the system retrieve near-optimal models even when it misses the exact observed gold?**

报告：

* regret；
* utility ratio；
* ε-optimal hit rate。

### RQ-D5

**Does scaling to a 3M candidate lake discover good models that historical benchmarks never labeled?**

这是最值得关注的问题。

如果答案是 yes，这不仅是在为低 gold@10 辩护，而可能本身就是论文的重要发现：

> 大规模开放模型湖中的 ground truth inherently incomplete，因此传统 exact-gold retrieval metrics 系统性低估真实 recommendation quality。

---

## 12. Claude 需要特别避免的错误

不要：

* 直接宣称 non-gold 就是好模型；
* 用模型名称相似度代替真实 performance；
* 用 LLM 判断“这个模型应该适合这个 dataset”然后当 ground truth；
* 挑几个成功案例作为主要证据；
* 根据实验结果反向挑 epsilon；
* 把 historical gold 和 newly evaluated gold 混在一起而不说明；
* 修改 A 轴定义来让结果变漂亮。

A 轴应该继续保留。

D 轴是对 A 轴语义的补充，而不是事后修改评价指标。

---

## 13. 最理想的论文结果形态

最终希望得到类似这样的结果：

```text
Historical sparse evaluation:
gold@10 = 6.0%

Among top-10 recommendations:
72% are previously unevaluated.

Fresh evaluation audit:
63% of retrieved unlabeled models are within 5% of
the best-known model performance,
compared with 14% for random candidates.

After dense judgment:
near-optimal@10 = 41%
median recommendation regret = 1.8%
```

这里的数字只是说明形式，不是预期结果。

如果真实实验支持类似结论，那么论文叙事将发生重要变化：

A 轴说明：

> 从三百万模型中恢复历史已知最佳模型非常困难。

D 轴进一步说明：

> 但历史 observation 本身高度不完整；系统所谓的很多“false positives”实际是高质量模型。

这比单纯努力把 gold@10 从 6% 调到 8% 更有科学价值。

## 15. Claude 的想法

§14 第 2 条要求先分清哪些量现在就能算。我把能算的都算了，结果在 §15.2 与 §15.4，
脚本产出落在 [`F7_runs/topk_composition.json`](F7_runs/topk_composition.json) 与
[`F7_runs/task_match_control.json`](F7_runs/task_match_control.json)，
三个 split seed 各跑一遍，用的是 F7 导出的 `z_m_eval` / `z_d_eval` 与合并后的全部监督边。

结论先说：这份文档的前提成立，而且比它设想的更极端。A 轴计为「错误」的 top-10 结果里，
我们确实知道更差的只占 3.3%，其余九成以上是这个数据集上没有记录的模型。
但同一批数据里还有一条相反方向的事实（§15.4 后半），它会改变 D 轴该怎么分层报告。

### 15.1 先解决一个命名冲突

`1Mplan.md` §5 的 F8 里已经有一个「D 轴」，指的是工程成本：端到端建库墙钟、峰值显存、
索引磁盘、增量上线一个新模型的耗时、多线程 QPS。本文档定义的是另一件事。
两个 D 轴同名，在论文和后续文档里迟早出问题。

建议把本文档这条改称 **E 轴（Recommendation Utility under Incomplete Gold）**，
或者把原来那条改称「系统成本轴」。哪个都行，但要在动手写代码之前定下来。

### 15.2 top-10 的实际组成（§2 要的那张表）

对每个测试查询取 top-10，按该模型在这个数据集节点上有没有监督记录分类：

| | seed 0 | seed 1 | seed 2 |
|---|---:|---:|---:|
| observed gold（含并列最佳） | 1.98% | 1.32% | 1.84% |
| observed 但更差 | 2.78% | 4.67% | 2.34% |
| unobserved，但该模型在别的数据集上有记录 | 92.20% | 90.73% | 95.17% |
| unobserved，且全湖任何地方都没有记录 | 3.05% | 3.28% | 0.65% |
| 查询的 top-10 里至少有一个 observed 模型 | 18.8% | 27.2% | 16.4% |
| 得分最高的 observed 模型的排名中位数 | 386 | 104 | 1,044 |

三点值得记下来。

**A 轴计为错误的部分里，只有约 3.3% 是我们知道更差的模型。** 其余是标注缺口。
§2 那个「A 轴测到的主要是 annotation coverage」的说法，在数字上成立。

九成以上的 unobserved 模型不是长尾。 它们在别的数据集上有真实评测记录，
只是没在这个数据集上评过。真正「全湖任何地方都没有记录」的只占 0.65%–3.28%。
这对 D 轴的可行性是好消息：这批模型多半有卡片、有已知任务、能跑，
重新评测的工程风险比「随便从三百万里挑」低得多。

八成的查询 top-10 里一个 observed 模型都没有。 所以 A 轴的 `gold@10 ≈ 0.06`
不是「排在第 11 到第 50 位」的问题，而是「这个数据集上被评过的模型总共就那么几个，
它们的得分排在几百到上千位」的问题。

### 15.3 §5 的 tolerance 松弛几乎没有收益

按 §5 的建议放宽 relevance，把「性能在最优的 δ 以内」都算命中，实测：

| δ | seed 0 | seed 1 | seed 2 |
|---|---:|---:|---:|
| 0.01（现行 `GOLD_GAP_DELTA`） | 2.07% | 1.56% | 1.92% |
| 0.02 | 2.22% | 1.71% | 2.03% |
| 0.05 | 2.36% | 2.15% | 2.27% |

δ 放大五倍，命中率只从约 2.0% 涨到约 2.3%。原因就在 §15.2：top-10 里 observed 模型
本来就只有不到 5%，放宽阈值没有可放宽的对象。

这条是有用的负结果，它同时消掉一个风险。§12 警告「不要根据实验结果反向挑 epsilon」——
在这里挑不出好数字，所以这个诱惑自动消失了。§5 仍然值得做（多阈值一起报，成本为零），
但它不是杠杆。杠杆在给 unobserved 模型打标。

### 15.4 §8 要求的 control，有一个零成本版本

§8 说得对：只从自己的 top-10 里挑模型重测，说服力不够。在做任何 fresh evaluation 之前，
有一个控制现在就能跑。查询节点是 `(数据集, 任务)`，所以可以问：
返回的模型里，有多少在别的数据集上被评测过同一个任务？

| | seed 0 | seed 1 | seed 2 |
|---|---:|---:|---:|
| 我们的 top-10 同任务比例 | 22.4% | 22.0% | 17.2% |
| 从全湖均匀随机取 10 个 | 0.032% | 0.052% | 0.038% |
| 从「被评测过的模型」里随机取 10 个 | 3.36% | 2.48% | 1.95% |
| top-10 全部同任务的查询占比 | 2.4% | 4.0% | 4.2% |
| top-10 一个同任务都没有的查询占比 | 41.1% | 40.2% | 60.2% |

高于全湖随机约 500 倍，高于「同样是被评过的模型」这个更硬的控制约 7–9 倍。
第二个控制才是关键：它排除了「只是偏向热门/被评测过的模型」这个平凡解释。

这个量的边界要写清楚：**它不是性能测量，是任务相关性的必要条件。**
用的是该模型在别处的真实评测记录所属的任务，是观测事实而不是名字相似度或 LLM 判断，
因此不违反 §12 的第二、三条；但它只能说明检索不是在随机返回，不能说明返回的模型好。

后半张表同样要报：四到六成的查询，top-10 里连一个同任务模型都没有。
这是真问题，不能只讲 500 倍那一半。

### 15.5 哪些结论必须靠 fresh evaluation（§14 第 3 条）

现在就能算，不需要重测：top-k 三类组成（§15.2）、`observed_hit1` 与 `top3_hit1`
（F7 已产出，seed 0 是 0.307 / 0.521，含义是「在该数据集有记录的模型里挑出最好那个」的命中率）、
near-optimal@δ（§15.3）、任务相关性控制（§15.4）、以及 §10 的可用性统计
（gated、参数量、library、license 都在 F1 的快照字段里，一次扫描就能出）。

必须重测才能得到：D1 的 success rate、§4 的 utility ratio 与 regret、§6 的 false negative rate、
以及 RQ-D2 / RQ-D3 / RQ-D5。没有捷径，这几条的定义里就含「真实性能」。

### 15.6 三个实验设计（§14 第 4 条）

设计 A：可用性与可运行性审计。 只用快照字段，统计 top-10 里的 unobserved 模型
能不能下载、是否 gated、参数量、`library_name`、license。
科学强度低（不回答性能），计算成本接近零，偏差风险低。
它的价值是作为 B 和 C 的前置：如果 top-10 里有很大一部分根本跑不起来，
后面的抽样协议和替换规则都要跟着改。建议无论如何先做这一条。

**设计 B：单任务 dense-judgment 切片。这是我推荐的最小可行版。**
选一个评测协议已经标准化、能自动跑的任务族。按 F2 的分布，
`Retrieval`（11,922 条边）与 `automatic-speech-recognition`（6,631 条边）是最好的两个候选：
监督占比高、有现成的一键评测流程、模型体积普遍不大。
取该任务的 30–50 个测试查询，每个查询按 §9 的固定协议取若干 unobserved 候选，
加随机对照与已知 gold 做校准，实际跑评测。
科学强度高（真正回答 RQ-D2 与 RQ-D4），成本中等（几百个模型 × 一个数据集的推理），
主要风险是单任务结论不能外推到全湖，这一点必须在论文里写明而不是回避。

设计 C：跨任务 dense-judgment benchmark，论文完整版。
就是 §7 那个 50–200 查询的双层设计，覆盖三到五个任务族，
并按 §8 加入 baseline retriever 的 top-k 作为对照（模型卡片上的 BM25、
纯文本 MiniLM 检索、下载量排序各一条）。
科学强度最高，成本最高，主要风险在 selection bias 与各方法之间不均衡的失败率（见 §15.7）。

三者是递进关系，不是三选一：A 的产出决定 B 的抽样规则，B 的结果决定 C 值不值得投入。

### 15.7 §9 的抽样协议里有一条要现在就定

失败率与方法相关这件事本身是结果，不是需要抹平的噪声。
如果某个方法偏好大模型或 gated 仓库，它的候选就更常跑不了，那是该方法的真实代价。

建议在协议里预先写死两条：替换只在同一个 rank 桶内进行；替换次数按方法分别计入报告。
另外，抽样协议必须在 `z_m` 冻结之后、看到任何 fresh 结果之前固定下来，
写成一个带 sha256 的文件，与 `rf_gold_rules.json` 同等对待。
这个项目已经为 gold 规则做过一次冻结（`rf-gold-2.0`），D 轴的抽样规则应当照办。

### 15.8 §13 的理想结果形态，有一处大概会落空

「72% are previously unevaluated」——实测是 93%，比设想的更极端，这一条会更好看。

「63% of retrieved unlabeled models are within 5% of the best-known performance」——
我判断达不到，理由是 §15.4 的后半：四到六成的查询，top-10 里连一个同任务模型都没有。
任务都不对的候选，性能接近 best-known 的概率很低。

更可能的真实形态是分层的：top-10 含同任务模型的那部分查询 utility 高，
不含的那部分很差。**建议 D 轴从一开始就按「top-10 是否含同任务模型」分层报告，
不要只报一个平均数。** 平均数会把两种完全不同的失败模式混成一个中间值，
而这两种失败对应的改进方向完全不同：前者是排序问题，后者是表示没抓住任务。

### 15.9 一个比 fresh evaluation 便宜得多的中间来源

在花算力重测之前，先看一眼那九成「别处有记录」的模型里，
有多少在同一个 root 下的兄弟数据集上有记录。`glue/sst2` 的查询返回了一个在
`glue/qqp` 上有真实记录的模型，那条记录是测量结果，不是猜测。

它不能代替 fresh evaluation，但有两个用处：给 utility ratio 一个零成本的下界估计；
以及给 §3 的抽样做分层——优先重测那些连兄弟数据集记录都没有的候选，因为它们信息量最大。
F5 的划分已经是按 root 分组的，root 表现成的，这个统计一次 join 就能出。

### 15.10 无论正负都有研究价值的结果（§14 第 6 条）

top-k 三类组成与任务相关性控制这两组数已经拿到，它们无论方向如何都值得报：
前者量化了 A 轴到底在测什么，后者给出检索是否优于随机的第一个有对照的证据。

设计 B 的 fresh evaluation 两个方向都有价值。若 unobserved 候选显著优于随机，
那是 RQ-D5 的正面证据，也是这份文档设想的论文叙事。
若不优于，结论同样清楚：A 轴偏低是真的检索质量问题而不是标注问题，
研究重点应当回到监督扩展那条线（见 [`F6.5guide.md`](F6.5guide.md) §11）。
这两个结论都能写进论文，区别只在写哪一句。

可用性审计若发现 top-10 里有很大比例不可运行，那是产品层面的真问题，
值得单独一小节，而不是当成实验的杂音。

### 15.11 与 F6.5 的关系

F6.5 问的是「监督为什么这么少」，本文档问的是「监督少到这个程度，A 轴还算不算数」。
两者是同一个事实的两面：46,146 个带监督模型对 3,016,439 个候选。

F6.5 §11 的实测已经说明这 1.5% 不是我们抽取能力不足——单靠 HF 的结构化 `model-index`
就有 48,374 个 observed model、1,435,162 条 (模型, 数据集, 任务, 指标) 记录，
与 ModelLens 三个来源合计的 47,062 / 1,623,284 是同一量级。

这正是 D 轴成立的前提。如果稀疏是我们自己造成的，正确做法是去补监督；
如果稀疏是这个领域的客观现实，那就必须改评测。目前的证据支持后者。
