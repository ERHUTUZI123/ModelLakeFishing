### 3.1 为什么验图是单独一个文件

`build_graph_rung.py` 自己一路 assert，但一个「自己检查自己输出」的构建器只能证明这一次运行内部自洽。
`verify_rung_graph.py` 从磁盘把 `.pt` 重新读进来，再和冻结的 CORE 图逐项比对——
图建对了之后被覆盖、被截断、被换成另一份，前者查不出来，后者能。

### 3.2 血缘边的关系类型：存下来，但不改边权

T3（D-37）从 HF 的结构化 `baseModels` 拿到了 `relation`，这正是 CLAUDE.md 里 `r_mm'`
离散有序权重（quantized > adapter > finetune > merge）需要的量。但梯子的六列没带它，
所以这里从 `hf_canon.parquet` join 回来。

**join 回来之后没有写进 `edge_attr`，而是单独存成 `relation_id`。**
原因：CORE 那 42 条血缘边的 `edge_attr` 是 1.0，按计划 §1 第一条不能重算。
只给 HALO 的边写关系权重，等于同一个 `edge_attr` 在两群里含义不同——
在 T5 悄悄改掉图的语义，而整条梯子的前提是 N 是唯一变量。
`--relation-weights` 可以开启加权，留给明确要做这个实验的时候用。

关系分布（16,385 条 HALO 边）：

| relation | 边数 |
|---|---|
| `finetune` | 10,226 |
| `quantized` | 4,360 |
| `adapter` | 1,608 |
| `unknown` | 115 |
| `merge` | 76 |

外加 `check_stage2_contract.py` 单独跑一遍，22 项全过（含在 100K 全图上做一次

### 4.1 划分不变性

计划 §8.3 要求：用 `make_root_aware_splits(split_seed=0)` 在 100K 图和 CORE 图上各跑一次，
test 边集合的 sha256 必须相同。实测：

```
test-edge set identical to CORE's (65968 edges, sha 66c81823cb731063…)
```

这条门能抓到的是 CORE 的边顺序被扰动。HALO 没有监督边，划分只由 CORE 的 312,986 条
`trained_on` 决定，所以两边必然相同；不同就说明复制过程中动了 CORE，而这种错误
在 T8 之前不会有任何别的地方报错，只会表现为一个解释不了的指标漂移。

### 4.2 顺带确认的一件事

`check_stage2_contract` 在 100K 全图上跑了一次完整 forward/backward，**CPU 上 24 秒内完成，没有 OOM**。
这说明 T6 的分块推理（T0 第 4 项）在 100K 这一档不是必需的，是为 R3/R4 准备的。
但这只是 1 层的前向，T6 是 2 层加采样加对比损失，显存行为完全不同，不能据此推断 T6 也没问题。

## 5. 结果与对账

### 5.1 血缘边：和 T3 的预测逐项相符

| 量 | P1 名字匹配 | T3 预测 | T5 实测 |
|---|---|---|---|
| HALO 声明 `base_model` | — | 27,672 | **27,672** |
| 其中在 100K 湖内可解析 | — | 16,385 | **16,385** |
| ├ `core_halo` | — | 606 | **606** |
| ├ `halo_halo` | — | 15,779 | **15,779** |
| └ `core_core`（来自 HALO 声明） | — | 0 | **0** |
| CORE 自带的 `is_base_of` | 42 | （未计入） | **42** |
| **图里的 `is_base_of` 总数** | 42 | — | **16,427** |

T3 的预测是「HALO join 出多少条」，不含 CORE 自己那 42 条，两个数拼起来才是图里的总数。
报告里引用 390× 那个倍数时要说清楚分子是 16,385 还是 16,427（差 0.26%，结论不变）。

join 掉了的两类：

- **10,887 条声明的 base 不在这 100,000 个模型里**（39.3% 的声明）。base 在 HF 上存在，
  只是没被均衡选样选进 HALO，也不在 CORE 里。这是「湖是总体的一个样本」的直接后果，
  不是 bug——R3/R4 把 N 加大时这个数应该下降，可以当一个附带的观测量。
- **400 条自环**：HALO 模型把自己声明成自己的 base。直接丢掉。

### 5.2 血缘图的形状

| 量 | 值 |
|---|---|
| 至少有一条血缘边的模型 | 20,135（占 100K 的 20.1%） |
| 连通分量数 | 3,709 |
| 最大分量 | 159 个模型 |
| 派生数最多的单个 base | 140 个直接派生 |
| HALO 侧血缘覆盖率 | 28.43% |

最大分量 159、最大 hub 140 个直接派生。CLAUDE.md 把 hub 附近过平滑列为三大风险之一，
这两个数是 T8 查 HNSW recall 时的第一批参照系——12K 上没有这个量级的 hub。

### 5.3 冷启动分层：T3 的预测要改

T3 §4.6 用**边数**当了「有血缘的节点数」，两者不是一回事：一条边碰两个节点，
一个 base 带 20 个派生只贡献 1 个 base 节点但 20 个派生节点。实测：

| 层 | 定义 | T3 预测 | **T5 实测** | 差 |
|---|---|---|---|---|
| warm | `trained_on` 度 ≥ 10 | 5,765（5.76%） | **5,765（5.76%）** | 0 |
| cool | 度 1–9 | 24,369（24.37%） | **24,369（24.37%）** | 0 |
| cold | 度 = 0，有血缘 | 16,385（16.39%） | **19,852（19.85%）** | +3,467 |
| frozen | 度 = 0，无血缘 | 53,481（53.48%） | **50,014（50.01%）** | −3,467 |

`warm`/`cool` 全部来自 CORE，是确定值，对上了。`cold`/`frozen` 两层按上面的口径改写。

结论方向不变：**`frozen` 仍然是最大的一层，刚好占一半。** 超过一半的模型既没有性能记录、
也没有可解析的血缘，只能靠自身特征被检索到。这是 T8 冷启动分析的主体。

顺带一个数：CORE 里有 **49 个模型 `trained_on` 度为 0**。它们在 CORE 图里就是这样，
不是这一步引入的。

### 5.4 规模与耗时

| 量 | 计划估计 | 实测 |
|---|---|---|
| 图文件 | ~250 MB | **223 MB**（213 MiB） |
| 建图耗时 | 3–10 分钟 | **13 秒** |
| 出闸门耗时 | 未估 | 24 秒（大头是 100K 全图 forward/backward） |

比估计快得多，因为这一步几乎没有计算：唯一的循环是 69,817 次 hashmap 查找。

## 6. 与计划的偏离

| # | 计划原文 | 实际做法 | 理由 |
|---|---|---|---|
| 1 | `is_base_of` 预估 16,385（只算 HALO join） | 图里是 16,427，含 CORE 自带的 42 条 | CORE 的边按 §1 第一条必须保留；两个数并列报 |
| 2 | 没提 `relation` 怎么进图 | 存成 `relation_id`，`edge_attr` 保持 1.0，加 `--relation-weights` 开关 | 只给 HALO 写关系权重会让 `edge_attr` 在两群里含义不同（§3.2） |
| 3 | 冷启动分层 cold = 血缘边数 | 改成「度 0 且至少被一条血缘边碰到的节点数」 | 边数不是节点数（§5.3） |
| 4 | 建图命令是裸 `python` | 加了 sbatch 脚本 | watGPU 要求预处理在计算节点跑；且 `$HOME` noexec 要 stage 环境 |
| 5 | 没要求 `--canon` | 加了可选 `--canon` | 梯子六列不带 `lineage_relation`，不 join 回来这个量就不在图里，事后只能重建图 |
