## 6. 结果

### 6.1 family vocab：341 → 1,896

HALO 侧 69,817 个模型有 9,292 个不同的 family 字符串，过 `FAMILY_MIN_COUNT=3` 之后新增 1,555 行。

新增行按 HALO 里的模型数排，前十：

| family | HALO 模型数 |
|---|---|
| `roberta` | 1,521 |
| `xlm-roberta` | 962 |
| `distilbert` | 857 |
| `act` | 836 |
| `gpt2` | 619 |
| `deberta-v2` | 589 |
| `translate` | 577 |
| `detr` | 491 |
| `qwen2` | 429 |
| `qwen3` | 378 |

尾部（恰好 3 个模型的）长这样：`1fixed`、`abmil`、`absolutereality`、`aether_v2_7way`、
`age`、`amazon`、`alzheimer`。这些是名字前缀被至少 3 个仓库用过而已，不是真的架构家族。

**F-T4-1：`roberta` / `distilbert` / `gpt2` 是新行，说明 CORE 的 family 命名空间比预期窄。**
CORE 的 vocab 里有 `RoBERTa` 和 `DistilBERT`——来自 `KNOWN_FAMILIES` 那张静态规则表，
被种子化进去了，但 CORE 的 30,183 个模型一个都没落在这两行上。CORE 实际用到的 207 个家族是
`bert`(6,909) / `llama`(1,492) / `vit`(1,308) / `xlm`(1,290) / `deit`(987) / `qwen`(925) 这一套。

这是 T3 的 F-T3-1 那个问题的残余：`family_vocab` 里同时存在两套命名空间，四级解析把 HALO
尽量推向 CORE 那一套（48.47% 命中），剩下的落新行。`roberta` 落新行本身不算错——CORE 里
没有任何模型标成 `roberta`，本来就没有行可共享。但我没法从这里判断 ModelLens 是把 roberta
模型折进了 `bert`，还是它的语料里就没有 roberta。两种情况对 `e_fam` 的影响不同，
如果后面冷启动分析看到 roberta 那一族行为异常，这是第一个要回来查的地方。

T3 预测 vocab 会扩到「约 2,000 行」，实测 1,896。

### 6.2 size bucket 与 family id

| | CORE | HALO | T3 预测 |
|---|---|---|---|
| `size_bucket_id == 0`（参数量未知） | 52.09% | 42.25% | 42.25% |
| `family_id == 0`（Other） | 34.16% | 12.50% | 12.78% |
| 用到的不同 family id | — | 1,691 | — |

`family_id == 0` 实测 12.50%，比 T3 预测的 12.78% 低 0.28 pp。原因是 T3 的预测只按 HALO 自己的
计数算，没算「这个 family 计数不到 3，但 CORE 的 vocab 里已经有这一行」的情况——那些模型
落在 CORE 的行上，不进 Other。差值很小，方向也对。

HALO 的 Other 比例（12.50%）远低于 CORE 自己的 34.16%，`e_fam` 不会塌成一行。

### 6.3 描述符文本分布

计划 §7.3 要的是「两群的 `len(descriptor)` 分布应大致重叠」。

| | 字符 mean | median | std | p10 | p90 | 带 size 子句 | 带 family 子句 |
|---|---|---|---|---|---|---|---|
| CORE | 52.3 | 51 | 20.4 | 27 | 77 | 47.91% | 66.02% |
| HALO | 57.3 | 57 | 15.4 | 38 | 76 | 57.75% | 100.00% |

整体重叠（p90 几乎相同，中位数差 6 个字符），左尾差得明显：CORE 的 p10 是 27 字符，HALO 是 38。
CORE 那条长尾来自 19.35% 的裸名字（`bert-base-uncased`、`#-shots` 这类没有组织前缀的），
HALO 里这类是 0%——HF 上所有仓库都是 `org/name` 形式。

**F-T4-2：family 子句的覆盖率差 34 pp，这条通道 §7.3 的归因清单里没有。**
CORE 的 intake 里 33.98% 的模型没有 family 字符串，`model_descriptor` 遇到空 family 会整段省略
`family <x>`，所以 CORE 只有 66.02% 的描述符带 family 子句，HALO 是 100%。
这比计划列在第一位的 size 子句差异（+9.83 pp）大三倍多，而且是同一个机制：
同一个描述符函数，喂进去的字段覆盖率不同，文本分布照样系统性可分。

**F-T4-3：名字长度的差和整段描述符的差方向相反。**
T3 量的是名字那一半：CORE 38.9 字符，HALO 33.8，HALO 短 5.1。整段描述符反过来，HALO 长 5.0。
原因就是上面两条子句——HALO 的 family 子句 100% 覆盖、size 子句多 9.8 pp，
把名字短掉的那 5 个字符补回来还多。报告里引用「HALO 名字更短」时要说清楚是哪一半，
两个数不矛盾但容易被读成矛盾。

### 6.4 G-B4：可分性 AUC 0.9729，没过门

用逻辑回归拿 `x` 去分类「这一行是 CORE 还是 HALO」，30,183 对 30,183 平衡采样，50/50 train/test：

| 用哪部分特征 | 测试集 AUC |
|---|---|
| 完整 `x`（448 维） | 0.9729 |
| 只用 `e_name`（前 64 维，哈希平均） | 0.7093 |
| 只用 `e_desc`（后 384 维，MiniLM） | 0.9714 |

门是 [0.5, 0.75]。`e_name` 那一半刚好压在上界，`e_desc` 那一半 0.9714。

计划 §7.3 说 AUC > 0.9 时先按四条通道归因再考虑回滚描述符，但那四条（size 覆盖、名字长度、
裸名字、组织集中度）是并列列出来的，没说哪条贡献多少。所以做了子句消融：对同一批抽样行
（每组 6,000）重新生成三种简化描述符再嵌入，family 子句和 size 子句各关一次。

| 描述符内容 | AUC | 相对只有名字的增量 |
|---|---|---|
| 只有名字 | 0.8472 | — |
| 名字 + size 子句 | 0.9313 | +0.084 |
| 名字 + family 子句 | 0.9146 | +0.067 |
| 完整（现状） | 0.9655 | +0.118 |

读法：

1. **地板是 0.847，不是 0.5。** 把描述符退到最保守的形态——只剩清洗过的模型名字，family 和 size
   全丢掉——MiniLM 空间里两群还是能被线性分开。这部分来自 CORE 是 ModelLens 那份基准语料、
   HALO 是 2026 年按配额爬的 HF 均衡样本，两群的命名习惯、组织构成、年代都不一样。回滚描述符改不动它。
2. **流水线自己贡献了 0.118。** 两条子句把 0.847 推到 0.966，且各自的增量（0.084、0.067）
   加起来大于联合增量，说明它们捕捉的是重叠的信息。
3. **计划把 size 覆盖列为「唯一能调的旋钮」，实测 family 子句差不多同一量级**（0.067 vs 0.084），
   而 family 那条 §7.3 根本没列（见 F-T4-2）。

计划 §1 第二条要防的是「流水线人为制造两群之间的差异」，从消融看这一层是干净的——
描述符函数确实是同一个，两条子句贡献 0.118，剩下的 0.847 是湖的真实构成。
门的写法（绝对 AUC ≤ 0.75）预设了两群本来接近同分布，实际不是。

### 6.5 特征健康

- HALO 的 69,817 行全零行 0 个，L2 norm 均值 1.076，范围 [1.013, 1.285]。
  量级是对的：`e_name` 是单位向量的平均，`e_desc` 是未归一化的 MiniLM 输出，拼起来 norm 略大于 1。
- 无 NaN、无 Inf。

## 9. G-B4 怎么处理（按 `T4GPU.md` §8 的 A 方案）

**不回滚描述符。** G-B4 从「绝对 AUC ≤ 0.75」改成报两个数：

| 量 | 值 | 含义 |
|---|---|---|
| 绝对可分性 | 0.9729 | CORE 和 HALO 在特征空间里能被线性分开的程度 |
| 流水线增量 | 0.9655 − 0.8472 = **0.118** | 描述符的 family / size 子句贡献的那部分 |
| 总体基线 | 0.8472 | 只用模型名字时的可分性，两群构成本身的差异 |

理由：能调的只有流水线那 0.118，而且它已经调到最接近 CORE 的一档（D-26 定的只用
`safetensors.total`）；剩下的 0.847 改描述符改不动，改选样要推翻 T2 的 G1–G20。

对下游的两个约束，都要写进报告：

1. **不能说「扛住了 83× 同分布干扰」。** HALO 不是 CORE 的同分布扩充，它是另一批模型。
   能说的是「候选池从 30,183 扩到 100,000 之后 gold@10 掉了多少」，这是一个关于
   检索在更大更杂的湖里表现的陈述，不是一个关于抗同分布干扰的陈述。
2. **冷启动分析要把它列为混杂因素。** `frozen` 层占 HALO 的 53.48%（T3 §4.6），
   而 CORE/HALO 本身可分——观察到的分层差异里有多少来自「冷」、有多少来自「是另一群模型」，
   从现在的设计里分不开。

这两条现在写下来，是因为等到 T8 出了数字再讨论口径，就很难避免顺着数字挑一个说法。

登记为 **D-39**（G-B4 改判为绝对值 + 流水线增量双口径）。
另外把 family 子句覆盖率差登记为 **D-40**，补进 §7.3 的归因清单第一位。
