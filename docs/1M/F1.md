## 1. 结论

枚举完成并以游标耗尽正常终止。**N_full = 3,003,759 条记录，61 个分片，0 重复，0 乱序，墙钟 27.5 分钟。**
湖就是这份爬取，不掺任何其他来源。

F0 的规模估计是 2.89×10⁶，实测 3,003,759，偏差 −3.9%，落在预注册的 ±15% 带内。

三条决定下游形态的实测结果：

**快照自带足够的监督。** `model-index` 里有 208,035 条 (模型, 数据集) 带值记录，覆盖 7,700 个数据集，
其中 2,586 个数据集各有 3 个以上模型。这是本档全部监督与 gold 的唯一来源，见 §5。

**血缘边 859,056 条。** 声明率 29.77%，湖内解析率 96.08%，`relation` 字段有 96% 的覆盖。
风险同时也有了数字：119 个父节点各带 1,000 个以上子模型，最大的一个带 43,346 个。

**真实全量湖比按下载量排序的前缀干净得多。** 计划原先按下载量前 15 万条预计会看到
「最大发布者 24.21%、量化搬运 61.98%」，实测是**最大发布者 2.28%、带量化标签 9.75%**。
那两个数是排序的产物，不是总体的性质。

## 2. 快照口径

这是本档唯一不可复现的输入，因此按窗口而不是按时刻记录。

| 量 | 值（UTC） |
|---|---|
| 枚举开始 | **2026-08-18T18:01:49Z** |
| 枚举结束 | **2026-08-18T18:29:18Z** |
| 墙钟 | 1,648.6 秒 |
| 快照上界：最新一条记录的 `createdAt` | **2026-08-18T18:01:36Z**（`zoarag/EvilPeterPan`） |
| 快照下界：最后一条记录的 `createdAt` | 2022-03-02T23:29:04Z（`albert/albert-base-v1`） |
| `snapshot_date_utc` | 2026-08-18 |

读法：这份快照包含 2026-08-18T18:01:36Z 之前创建、且在随后 27.5 分钟窗口内仍然公开可访问的全部模型。
因为流按 `createdAt` 降序，且游标键是不可变的 `_id`（F0 §2.2），窗口期间新建的模型 `_id` 更大、
落在已经翻过的头部，不会被计入；窗口期间被删除的模型直接从流中消失。
这两条都不会造成「跳过更早的模型」，这正是 F0 选这个排序键的原因。

下界值得单独说明。最后一条是 `albert/albert-base-v1`，`createdAt` 为 2022-03-02T23:29:04Z，
而这个模型实际发布远早于此。HF 在引入 `createdAt` 字段时对既有仓库做了回填，
所有更早的仓库都被压在 2022-03-02 这一天。因此「2022-03 之前没有模型」是字段回填的产物，不是事实，
报告里引用时间分布时要写明这一点。F0 的规模估计按月积分创建率，对这一天上堆积的存量欠采样，
这也是它比实测低 3.9% 的主要原因。

`PROVENANCE.json` 的 `snapshot_window_utc` 字段完整记录了上述四个时间戳，副本在
[`F1_runs/PROVENANCE.json`](F1_runs/PROVENANCE.json)。

## 3. 执行与实测

```bash
python -m scale1m.hf_crawl --sort createdAt --direction -1 \
       --limit 100000000 --v2-fields --shard-size 50000 \
       --out $MLF_DATA_DIR/data1m/candidates_full
```

| 量 | F0 预测 | 实测 |
|---|---|---|
| 页数 | 2,900 | 3,004 |
| 记录数 | 2.89M（±15%） | 3,003,759 |
| 墙钟 | 30–40 分钟 | 27.5 分钟 |
| 落盘 | 约 480 MB | **202 MB** |
| 每条落盘（gz） | 165 B | **67 B** |
| 去重集合内存 | 400–600 MB | 峰值约 163 MB @ 951K，按此外推约 400 MB |
| 重复记录 | — | 0 |
| 重试 | — | 1 次（`ConnectionError`） |
| 限流休眠 | — | 6 次，合计 996 秒 |

限流占了墙钟的 60.4%：匿名额度是 500 请求 / 300 秒固定窗口，每个窗口能翻约 475 页，
实际网络时间只有约 13 分钟。带 token 是否能提高额度仍未测；27.5 分钟不是瓶颈，没有必要测。

落盘只有预测的 42%，原因不是压缩更好，而是真实湖里每条记录携带的元数据本来就少：
只有 28.19% 的模型有 `safetensors`，3.57% 有可解析的 `model-index`。预测里用的 165 B/条
来自一份经过质量门筛选的样本，对全量不适用。

`python -m scale1m.verify_raw --raw <candidates_full> --expect 2460000 --forecast 0`，
退出码 0，完整输出在 [`F1_runs/f1_verify.log`](F1_runs/f1_verify.log)。

| 门 | 判据 | 结果 |
|---|---|---|
| G-F1a | `PROVENANCE.json` 完整，分片只读，每片 sha256 复算一致 | 通过，61/61 分片一致且只读 |
| G-F1b | 枚举以游标耗尽结束；规范化 id 去重后条数不变；总数不低于预注册下界 | 通过：`exhausted_cursor=true`，3,003,759 条唯一 id 去重后仍是 3,003,759，0 重复；下界 2,460,000 |

## 5. 监督与 gold 的来源

湖只用这份爬取，所以监督也只能来自快照自身。唯一带性能数值的字段是 `cardData.model-index`。
测量结果（[`F1_runs/f1_native_supervision.json`](F1_runs/f1_native_supervision.json)）：

| 量 | 值 |
|---|---|
| 有可解析结果的模型 | 107,210（3.57%） |
| (模型, 数据集) 对 | **208,035** |
| (模型, 数据集, 指标) 三元组 | 2,158,375 |
| 不同数据集 | **7,700** |
| 不同 (数据集, 任务) | 8,793 |
| 有 ≥3 个模型的数据集 | **2,586** |
| 有 ≥10 个模型的数据集 | 964 |
| 有 ≥20 / ≥50 个模型的数据集 | 646 / 381 |
| 每个数据集的模型数 p50 / p90 / 最大 | 1 / 15 / 15,436 |

208,035 条带值边、7,700 个数据集节点，规模足以训练与评测。
一半的数据集只有一个模型，所以可用于评测的是 ≥3 那一层的 2,586 个数据集，gold 取组内数值最高者。

三件必须在 F2 处理的事：

**指标不可跨数据集比较。** 出现最多的指标类型是 accuracy 96,859、f1 73,033、mean_reward 58,420，
其后是一整片检索指标（ndcg@k、recall@k，来自 MTEB 提交）。数值范围也不统一：163,999 条落在 [0,100] 之外，
主要是 `mean_reward`。因此边权必须在 (数据集, 指标) 组内归一化后再用，不能直接拿原值。

**强化学习提交占据头部。** 模型数最多的八个数据集里有七个是 RL 玩具环境
（`lunarlander-v2` 15,436、`taxi-v3` 7,857、`frozenlake-v1` 7,510、`cartpole-v1` 5,496 等），
任务分布里 `reinforcement-learning` 以 58,600 条居首。它们是同一门公开课的排行榜提交，
与"给数据集选迁移模型"这件事无关。F2 要决定是整体排除还是单列一层，无论怎么定都要在报告里写明。

**数据集节点需要卡片文本。** `x_d` 从 D0 起就是 `[e_name‖e_card‖e_stats]`，`e_card` 是 MiniLM 跑
`dataset_descriptor()`（名字 + task_categories + tags + description），文本来自 HF 数据集卡片。
快照的模型侧只给出数据集名字，因此要补一次数据集侧的枚举。已在 F1.5 完成，
见 [`F1.5.md`](F1.5.md)：1,008,417 个数据集仓库，查询集口径下 35.50% 的节点拿到真实卡片、
按监督记录加权 59.26%，其余退到该函数已有的名字兜底。

`cardData.datasets` 另外给出 358,524 条 (模型, 数据集) 使用声明，覆盖 59,529 个数据集，但没有数值。
它可以作为一种无权重的关联边，不能当监督用。

## 6. 湖的形状

### 6.1 字段覆盖

| 字段 | 覆盖率 |
|---|---|
| `tags` | 100.00% |
| `library_name` | 49.28% |
| `pipeline_tag` | 34.04% |
| 声明 `base_model`（任一来源） | 29.77% |
| `safetensors.total`（决定 `size_b`） | **28.19%** |
| `cardData.datasets` | 7.48% |
| `model-index` | 3.69% |
| 信息量为零（`layer=dropped`） | **0** |

`tags` 覆盖率 100%，所以「无 pipeline_tag 且无 tags 且无参数量」这个 `dropped` 判据恒为假，
在 300 万条上再次确认（D-27）。判据保留不动，报告里写明它恒为 0。

`size_b` 缺失 71.81% 是本档最需要提前知道的一条：超过七成的模型进 `size_bucket_id = 0`（unknown），
`e_size` 这一维的信息量比任何一档历史实验都低。

### 6.2 分层

| layer | 数量 | 占比 |
|---|---|---|
| `labeled`（有 model-index） | 110,806 | 3.69% |
| `lineage`（有 base_model，无 model-index） | 862,666 | 28.72% |
| `plain`（都没有） | 2,030,287 | 67.59% |
| `dropped` | 0 | 0 |

三分之二的湖既无标注也无可解析血缘，只能靠自身特征。C 轴 `frozen` 层因此是过半总体的问题。

### 6.3 集中度

| 量 | 全量湖实测 | 下载量前 15 万（对照） |
|---|---|---|
| 最大发布者占比 | **2.276%**（`mradermacher`，68,357 个） | 24.21% |
| top-10 发布者占比 | **5.307%** | 40.42% |
| 有效发布者数（1/HHI） | **1,268.4** | 15.1 |
| 不同发布者数 | **597,637** | 25,500（名义） |
| 带量化标签 | **9.75%**（近似口径） | 61.98%（`quantized-conversion`） |

按下载量取前缀会把自动化流水线反复拉取的搬运仓库系统性抬到头部；全站枚举一遍，它们只占个位数百分比。
计划里「真实湖会被一个发布者和量化搬运统治」的预期不成立，相关叙述已按此改写。

量化那一行是标签近似口径（`gguf`/`awq`/`gptq`/`4-bit`/`8-bit`/`exl2`/`mlx`），
与 `source_type` 判据不是一回事，真值等 F2 的标注跑完再报。

## 7. 对下游的预测

把 F2/F4/F5/F8 现在就能算的量写死，防止事后重新叙述。以下都不是闸门。
原始数据在 [`F1_runs/f1_lineage.json`](F1_runs/f1_lineage.json) 与
[`F1_runs/f1_forecast.json`](F1_runs/f1_forecast.json)。

### 7.1 血缘边（F5）

按 F2 将实际使用的规则计算（`lineage_base_of`：`baseModels` 优先、`cardData.base_model` 兜底）：

| 量 | 值 |
|---|---|
| 声明 `base_model` | 894,089（29.77%） |
| 来自 `baseModels`（权威，带 relation） | 837,134 |
| 来自 `cardData.base_model`（兜底） | 56,955 |
| 自指（丢弃） | 2,008 |
| **湖内可解析 ⇒ `is_base_of` 边数** | **859,056** |
| 解析率 | **96.08%** |
| 不同父节点数 | 76,669 |
| 每个父节点的子节点数 p50 / p90 / p99 | 1 / 6 / 118 |
| 子节点超过 1,000 的父节点数 | **119** |
| 最大的一个父节点 | `black-forest-labs/flux.1-dev`，**43,346** 个子模型 |

`relation` 分布：finetune 325,399 / adapter 314,940 / quantized 167,522 / merge 14,669 / 未声明 36,526。
`r_mm'` 的离散有序权重第一次有真实输入，不必从名字猜。

解析率 96.08% 的原因很直接：父模型几乎都在湖内。这也是全量档相对任何抽样湖的结构性优势——
血缘图第一次是完整的，而不是被采样切碎的。

风险在度数分布上：扇出上限会把采样时看到的邻居截断到 (20,20)，但 43,346 个子模型共享一个父节点，
过平滑压力比任何历史档都大。F8 要按层报，并把最大的若干 hub 单独列出来。

### 7.2 描述符（F4）

`model_descriptor` 在 `size_b` 缺失时整段省略 `"<x>B params"`，在 family 为空时省略 `family <x>`。
全量湖只有 28.19% 带 size 子句，因此这两个子句的实际信息量比历史各档都低，
`e_desc` 会更依赖模型名字本身。F4 要报的是全湖描述符的长度分布与子句覆盖率，
不再有「两群是否可分」的问题——湖只有一个总体。

### 7.3 其他

`family` 解析率没有在本阶段算，它依赖 `config.model_type`，属 `hf_canonicalize` 的工作。
可以预期比任何历史档都低，因为元数据更稀疏。

`displacement_quality`（F8）有 110,806 个 `labeled` 模型可用，但 model-index 的数值现在是监督本身，
这个指标的定义要在 F8 重新写，不能照搬。

## 8. 与计划的偏离

| # | 计划原文 | 实际 | 理由 |
|---|---|---|---|
| 1 | N_full = 爬取 ∪ CORE = 3,020,418 | **N_full = 3,003,759，湖只有爬取** | 用户 2026-08-18 定：CORE 当作从未存在。相应地监督与 gold 全部改由 `model-index` 提供，见 §5 |
| 2 | 使用 `--expect` 的默认下界 | `--expect 2460000`，即 F0 估计的 −15% | 把 F0 的预注册区间变成一条可判定的门 |
| 3 | 计划未提 `verify_raw` 的排序检查 | 改为跟随 `PROVENANCE.json` 的排序键 | 原实现写死 `downloads` 降序，对 `createdAt` 流会把每条都判成违例 |
| 4 | 计划未要求在 F1 算血缘与监督 | 增加了 §5 与 §7.1 | 两者都是本档形态的前提，且现在算与后面算成本一样，先写死可防止事后叙述 |

关于第 1 条，代价已经量化并存档在 [`F1_runs/f1_core_dropcost.json`](F1_runs/f1_core_dropcost.json)：
沿用 CORE 会带来 312,986 条监督边与 734 个 held-out 查询，但其中的模型今天只有 44.81% 还在 HF 上；
改用快照自带的 `model-index` 后，监督是 208,035 条边、7,700 个数据集，全部来自同一份快照，
不存在跨快照的存活问题。代价是与 R0/R1/R2 的历史数字不再可比，这一档另立基线。
