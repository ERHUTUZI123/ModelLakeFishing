## 1. 结论

枚举完成并以游标耗尽正常终止。**3,003,759 条记录，61 个分片，0 重复，0 乱序，墙钟 27.5 分钟。**
加上今天已经不在 HF 上、但由冻结图提供特征的 CORE 模型，**N_full = 3,020,418**。

F0 的规模估计是 2.89×10⁶，实测 3,003,759，偏差 −3.9%，落在预注册的 ±15% 带内。

两个与计划假设不同、需要改写下游叙述的实测结果：

真实全量湖比按下载量排序的前缀干净得多。1Mplan §3.3 用 v1 的 15 万条前缀预计真实构成会是
「最大发布者 24.21%、量化搬运 61.98%」，实测全量湖是**最大发布者 2.28%、带量化标签 9.75%**。
那两个数是下载量排序的产物，不是总体的性质。R2 的均衡湖与全量湖之间的分布差距因此比计划预期的小得多。

血缘边从 R2 的 16,385 条涨到 **852,189 条**（按 D-28 剔除以 CORE 为子节点的边之后）。
这是 D-8 第一次在完整的父节点集合上被检验：声明率 29.77%，而其中 **96.08% 能在湖内解析**，
R2 时因为大量父模型不在 100K 湖内，解析率远低于此。同时风险也第一次有了数字：
119 个父节点各带 1,000 个以上的子模型，最大的一个带 43,346 个。

## 2. 快照口径

这是本档唯一不可复现的输入，因此按窗口而不是按时刻记录。

| 量 | 值（UTC） |
|---|---|
| 枚举开始 | 2026-08-18T18:01:49Z |
| 枚举结束 | 2026-08-18T18:29:18Z |
| 墙钟 | 1,648.6 秒 |
| 快照上界：最新一条记录的 `createdAt` | 2026-08-18T18:01:36Z（`zoarag/EvilPeterPan`） |
| 快照下界：最后一条记录的 `createdAt` | 2022-03-02T23:29:04Z（`albert/albert-base-v1`） |
| `snapshot_date_utc` | 2026-08-18 |

读法：这份快照包含 2026-08-18T18:01:36Z 之前创建、且在随后 27.5 分钟窗口内仍然公开可访问的全部模型。
因为流按 `createdAt` 降序，且游标键是不可变的 `_id`（F0 §2.2），窗口期间新建的模型 `_id` 更大、
落在已经翻过的头部，不会被计入；窗口期间被删除的模型直接从流中消失。
这两条都不会造成「跳过更早的模型」，这正是 F0 选这个排序键的原因。

下界值得单独说明。最后一条是 `albert/albert-base-v1`，`createdAt` 为 2022-03-02T23:29:04Z，
而这个模型实际发布远早于此。HF 在引入 `createdAt` 字段时对既有仓库做了回填，
所有更早的仓库都被压在 2022-03-02 这一天。因此「2022-03 之前没有模型」是字段回填的产物，不是事实，
报告里引用时间分布时要写明这一点。F0 的规模估计按月积分创建率，对这一天上堆积的存量欠采样，
这也是它比实测低 3.9% 的主要原因。

`PROVENANCE.json` 里 `snapshot_window_utc` 字段完整记录了上述四个时间戳，副本在
[`F1_runs/PROVENANCE.json`](F1_runs/PROVENANCE.json)。

## 3. 执行与实测

```bash
python -m scale1m.hf_crawl --sort createdAt --direction -1 \
       --limit 100000000 --v2-fields --shard-size 50000 \
       --out $MLF_DATA_DIR/data1m/candidates_full
```

| 量 | F0 预测 | 实测 |
|---|---|---|
| 页数 | 2,900 | 3,004 |
| 记录数 | 2.89M（±15%） | 3,003,759 |
| 墙钟 | 30–40 分钟 | 27.5 分钟 |
| 落盘 | 约 480 MB | **202 MB** |
| 每条落盘（gz） | 165 B（沿用 R2 比例） | **67 B** |
| 去重集合内存 | 400–600 MB | 峰值约 163 MB @ 951K，按此外推约 400 MB |
| 重复记录 | — | 0 |
| 重试 | — | 1 次（`ConnectionError`） |
| 限流休眠 | — | 6 次，合计 996 秒 |

限流占了墙钟的 60.4%：匿名额度是 500 请求 / 300 秒固定窗口，每个窗口能翻约 475 页，
实际网络时间只有约 13 分钟。带 token 是否能提高额度仍未测；本次没有必要测，27.5 分钟不是瓶颈。

落盘只有预测的 42%，原因不是压缩更好，而是**真实湖里每条记录携带的元数据本来就少得多**：
全量湖只有 28.19% 的模型有 `safetensors`，而 R2 的均衡湖是 57.75%，因为 R2 的质量门偏好元数据完整的模型。
这条差异会一路影响 F2 的 family 解析率与 F4 的描述符信息量，见 §5、§6。

## 4. 出闸门判定

`python -m scale1m.verify_raw --raw <candidates_full> --expect 2460000 --forecast 0 --core hgraph_ml_v2.pt`，
退出码 0，完整输出在 [`F1_runs/f1_verify.log`](F1_runs/f1_verify.log)。

| 门 | 判据 | 结果 |
|---|---|---|
| G-F1a | `PROVENANCE.json` 完整，分片只读，每片 sha256 复算一致 | 通过，61/61 分片一致且只读 |
| G-F1b | 枚举以游标耗尽结束；规范化 id 去重后条数不变；总数不低于预注册下界 | 通过：`exhausted_cursor=true`，3,003,759 条唯一 id 去重后仍是 3,003,759，0 重复；下界 2,460,000（F0 估计的 −15%） |
| — | 排序单调性 | `createdAt` 降序违例 0 条 |

`verify_raw` 里的单调性检查原先写死按 `downloads` 降序，会把 `createdAt` 流的每一条都判成违例。
已改为跟随 `PROVENANCE.json` 里记录的排序键与方向，`raw/` 的 v1 快照校验路径不受影响。

`tags` 覆盖率仍是 100%，`dropped` 判据仍然恒为假。D-27 在 300 万条上再次被确认：
HF 给每个仓库自动挂 `region:*`、`license:*` 之类的标签，那个合取式永远不成立。判据保留不动，报告里写明它恒为 0。

### 5.2 分层

| layer | 全量湖 | R2 的均衡 HALO |
|---|---|---|
| `labeled` | 110,806（3.69%） | 9.48% |
| `lineage` | 862,666（28.72%） | 36.19% |

三分之二的全量湖既无标注也无可解析血缘，只能靠自身特征。R2 时这个比例是 54.33%，
当时已经写进报告；全量下它是 67.59%，C 轴 `frozen` 层的重要性还会进一步上升。

### 5.3 集中度，以及对 1Mplan §3.3 的更正

| 量 | v1 的 15 万条下载量前缀 | R2 均衡选样 | **全量湖实测** |
|---|---|---|---|
| 最大发布者占比 | 24.21% | 0.902% | **2.276%**（`mradermacher`，68,357 个） |
| top-10 发布者占比 | 40.42% | 4.045% | **5.307%** |
| 有效发布者数（1/HHI） | 15.1 | 2,889.1 | **1,268.4** |
| 不同发布者数 | 25,500（名义） | — | **597,637** |
| 量化相关 | 61.98%（`quantized-conversion`） | 14.999%（第三方） | **9.75%**（按标签的近似口径） |

1Mplan §3.3 是按 v1 前缀写的，预期全量湖会呈现「一个发布者 24%、量化搬运六成」的形态。
实测不是这样：**那两个数是下载量排序的产物，不是总体的性质**。
按下载量排前 15 万，自动化流水线反复拉取的搬运仓库被系统性抬到头部；把全站枚举一遍，
它们只占个位数百分比。

因此 R2 与全量档之间的分布差距比计划预期的小：最大发布者 0.90% → 2.28%，
top-10 占比 4.05% → 5.31%，有效发布者 2,889 → 1,268。差距真实存在，但不是数量级的。
§3.3 要求的三条措施仍然照做，只是「两个湖差得很远」这句话要按上表改写。

量化那一行是标签近似口径（`gguf`/`awq`/`gptq`/`4-bit`/`8-bit`/`exl2`/`mlx`），
与 R2 的 `source_type=quantized-conversion` 不是同一个判据，不能直接相减。
真值等 F2 的 `annotate_candidates` 跑完再报。

但它是一条应当写进报告的事实——监督核来自一份更早的语料，其中过半的仓库已经不在了。

100,000 行前缀里、特征沿用 R2 的副本，F3 需要在 `LADDER_REPORT.json` 里单独计数并披露。

## 6. 对下游的预测

与 R2 的 `verify_raw --forecast` 同样的用途：把 F2/F4/F5/F8 现在就能算的量写死，防止事后重新叙述。
以下都不是闸门。原始数据在 [`F1_runs/f1_lineage.json`](F1_runs/f1_lineage.json) 与
[`F1_runs/f1_forecast.json`](F1_runs/f1_forecast.json)。

### 6.1 血缘边（F5，D-8 的规模化检验）

按 F2 将实际使用的规则计算（`lineage_base_of`，`baseModels` 优先、`cardData.base_model` 兜底，D-37）：

| 量 | 全量湖 | R2（100K） |
|---|---|---|
| 声明 `base_model` | 894,089（29.77%） | 27,672（39.64%） |
| 来自 `baseModels`（权威，带 relation） | 837,134 | — |
| 来自 `cardData.base_model`（兜底） | 56,955 | — |
| 自指（丢弃） | 2,008 | — |
| **湖内可解析 ⇒ `is_base_of` 边数** | **859,056** | 16,385 |
| 解析率 | **96.08%** | 约 59% |
| 其中父节点在 CORE | 9,394 | 606 |
| 其中子节点在 CORE（按 D-28 必须丢弃） | 6,867 | 0 |
| **D-28 之后的边数** | **852,189** | 16,385 |

相对 R2 是 52 倍，相对 P1 名字精确匹配的 42 条是 20,290 倍。
解析率从约 59% 升到 96.08%，原因很直接：R2 的 100K 湖里大部分父模型根本不在湖内，全量湖里几乎都在。

`relation` 字段这次是有内容的：finetune 325,399 / adapter 314,940 / quantized 167,522 /
merge 14,669 / 未声明 36,526。`r_mm'` 的离散有序权重第一次有了大规模的真实输入，不必从名字猜。

同一份数据给出的风险：

| 量 | 值 |
|---|---|
| 不同父节点数 | 76,669 |
| 每个父节点的子节点数 p50 / p90 / p99 | 1 / 6 / 118 |
| 子节点超过 1,000 的父节点数 | **119** |
| 最大的一个父节点 | `black-forest-labs/flux.1-dev`，**43,346** 个子模型 |

这正是 1Mplan §8 里「hub 度数急剧变大」那条风险的量化形态。扇出上限会把采样时看到的邻居截断到 (20,20)，
T7.5 已经证明它随 N 增值；但 C 轴上 `cold` 层的塌缩（R2 实测层内余弦 0.935）在这种度数分布下只会更严重。
F8 要按层报，并把最大的若干 hub 单独列出来。

### 6.2 描述符的 size 子句（F4，G-B4）

`model_descriptor` 在 `size_b` 缺失时整段省略 `"<x>B params"`，所以覆盖率差异本身就是一条文本可分性通道。

| 群 | 带 size 子句 |
|---|---|
| CORE | 47.91% |
| R2 的均衡 HALO | 57.75%（比 CORE 高 9.83 pp） |
| **全量湖** | **28.19%（比 CORE 低 19.72 pp）** |

方向再次翻转，而且幅度是 R2 的两倍。D-26 仍然成立（不加名字正则兜底），但 G-B4 的归因清单里
这一条的权重会明显上升，报告要按新数字重写，不能沿用 R2 的 +9.83 pp。

### 6.3 其他

`displacement_quality`（F8）在全量湖上有 110,806 个 `layer=labeled` 的模型可用，是 R2 的 6,619 的 16.7 倍。
但按 D-54，本档仍只报挤占者的成分而不报质量，因为 model-index 的数值没有物化。

`family` 解析率（F2）没有在本阶段算，因为它依赖 `config.model_type` 与 CORE 的家族命名空间比对，
属于 `hf_canonicalize` 的工作。可以预期它比 R2 的 48.47% 低，因为全量湖的元数据更稀疏。

## 7. 与计划的偏离

| # | 计划原文 | 实际 | 理由 |
|---|---|---|---|
| 1 | 使用 `--expect` 的默认下界 | `--expect 2460000`，即 F0 估计的 −15% | 把 F0 的预注册区间变成一条可判定的门，而不是事后对照 |
| 2 | 计划未提 `verify_raw` 的排序检查 | 改为跟随 `PROVENANCE.json` 的排序键 | 原实现写死 `downloads` 降序，对 `createdAt` 流会把每条记录都判成违例 |
| 3 | 计划未要求在 F1 算血缘 | 增加了 §6.1 的血缘预测 | 它是本档最大的未知数，且现在算与 F5 算的成本一样，先写死可防止事后叙述 |
| 4 | 计划按 v1 前缀预期分布 | 按实测改写 §5.3，并要求更正 1Mplan §3.3 | v1 的集中度是排序产物，不是总体性质 |
