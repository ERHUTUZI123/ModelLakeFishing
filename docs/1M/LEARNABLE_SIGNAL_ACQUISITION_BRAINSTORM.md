# 可学习信号的采集方案（头脑风暴）

同目录相关文档：[`RESOURCE_SUPERVISION_AT_3M.md`](RESOURCE_SUPERVISION_AT_3M.md)（工业级补标的资源核算）、
[`RESOURCE_E_AXIS_DENSE_REEVALUATION.md`](RESOURCE_E_AXIS_DENSE_REEVALUATION.md)（补评的资源核算）、
[`RECOMMENDATION_UTILITY_EVALUATION_BRAINSTORM.md`](RECOMMENDATION_UTILITY_EVALUATION_BRAINSTORM.md)（效用评估）。
实测来源：[`F1.md`](F1.md)、[`F1.5.md`](F1.5.md)、[`F2.md`](F2.md)、[`F4.md`](F4.md)、[`F5.md`](F5.md)、
[`F6.md`](F6.md)、[`F8.md`](F8.md)、[`F9.md`](F9.md)。

本文档回答一个问题：如果精度的根本约束是可学习信号的总量，那么还能从哪里拿到信号、每一条要花多少钱。
文中新出现的数字是 2026-08-25 在本地对 `data1m/candidates_full`、`data1m/datasets_full`、
`data1m/rf/canon/` 做的一次性扫描得到的，测量方法写在附录 A，尚未固化为仓库里的模块。

---

## 1. 诊断

全量档三个 split seed 的 `gold@10` 平均 0.0598，seed 0 是 0.0700。有三条实测支持
「瓶颈是信号总量而不是规模、索引或容量」这个判断。

候选池不是瓶颈。F8 §2.2 把候选宇宙从 10 万放大到 3,016,439（30 倍），
`gold@10` 只从 0.0706 掉到 0.0700，gold 的中位绝对排名只从 1,736 移到 1,908。
挤在 gold 前面的几乎全是那 46,146 个带监督模型，不是新加进来的无标签长尾。

信号总量在扩档过程中没有增长。

| 档 | 候选模型 | 监督边 | 训练可见的带标签模型 | 占比 |
|---|---:|---:|---:|---:|
| 12K | 12,000 | — | 11,162 | 93% |
| 30K | 30,183 | 312,986 | 26,508 | 88% |
| 100K | 100,000 | 312,986 | 25,379 | 25% |
| 全量 | 3,016,439 | 247,803 | 35,991–39,930 | 1.19%–1.32% |

候选池涨了 30 倍，监督边反而比 100K 档少 20.8%。

信号的构成也基本没有变。247,803 条边里 174,133 条（70.3%）属于 `curated` 类，
来自 `modellens_v2`、`d0_v1_5`、`hf_effective`、`a_ctrl_2000m`、`diverse_zoo` 这些历史语料，
只有 73,670 条来自本档新爬的三百万条快照。模型侧描述符仍然是 12K 档就在用的
`scale.modellens_build_graph.model_descriptor`，数据集侧 `x_d` 仍然是 D0 定下的
`[e_name 64 ‖ e_card 384 ‖ e_stats 10]` 三视图。「从 10K 到 3M 用的是同一份可学习信号」
在代码层面是字面成立的。

### 1.1 诊断需要拆成两个问题

F8 §2.2 同时说明了一件与直觉相反的事：`gold@10` 偏低的直接原因是那 46,146 个带监督模型
内部排序不准，而不是 98.5% 的暗物质挤占了名次。因此「信号不足」实际上是两个可以分开攻的问题，
它们的证据、方案和验收指标都不同。

| | 问题一：排序不准 | 问题二：表示塌缩 |
|---|---|---|
| 现象 | `gold@10 = 0.060`，`observed_hit1 = 0.220` | `cold` 与 `frozen` 共 98.47%，层内平均余弦 0.88–0.93，有效维度 3.0–3.3 |
| 直接成因 | 监督边少、方向 70.3% 由历史来源背书、查询侧只有 20.97% 的节点有真实卡片 | 输入特征只有名字与家族，同 hub 的三万个子模型近乎同一个点（`qwen1.5-0.5b` 子模型两两余弦 0.9863）；无监督节点没有判别性梯度 |
| 需要的信号 | 更多、更准、方向明确的 (模型, 数据集) 性能标签；更强的 `x_d` | 每个节点都有判别性输入；每个节点都有梯度 |
| 验收指标 | `gold@10`、`median rank / N`、`recorded_top3@10` | 层内平均余弦、有效维度、hub 内余弦、`family_diversity@10`、`root_gold@10` |

两件事都要做，但要分别预注册各自的预期指标。用一个 `gold@10` 同时验收两者会得到误导性的结论：
按 F9 §1，我们 top-10 有 95.2% 的槽位在该 query 上根本没有记录，
所以「把未标注的好模型推上来」这件事目前的 gold 量不出来。

## 2. 现在盘上有什么，用了多少

模型侧特征 `x_m [3016439, 448]` 由 `[e_name 64（名字哈希）‖ e_desc 384（MiniLM）]` 构成，
`e_desc` 的输入文本是 `model_descriptor(model_id, family, size_b)`，全湖平均 55.3 个字符。
换句话说，进入模型的模型侧信息只有三样：名字字符串、家族字符串、参数量（71.93% 缺失）。
另有两张 embedding 表 `family_id`（41,056 行）与 `size_bucket_id`。

快照里已经抓下来、但一个比特都没有进入 `x_m` 的字段（全湖 3,003,759 条，2026-08-25 实测）：

| 字段 | 覆盖模型数 | 占比 | 现在用在哪 |
|---|---:|---:|---|
| `tags` | 3,003,759 | 100.00% | 未使用 |
| `author` | 3,003,759 | 100.00% | 未使用 |
| `createdAt` / `lastModified` | 3,003,759 | 100.00% | 未使用 |
| `cardData`（任意字段） | 1,896,326 | 63.13% | 仅 `model-index` 与 `base_model` |
| `downloadsAllTime > 0` | 1,734,072 | 57.73% | 未使用 |
| `downloads > 0` | 1,672,216 | 55.67% | 仅 F9 的 popularity 基线 |
| `library_name` | 1,480,111 | 49.28% | 未使用 |
| `cardData.tags` | 1,178,589 | 39.24% | 未使用 |
| `cardData.license` | 1,076,866 | 35.85% | 仅 F9 的可用性门 |
| `config.model_type` | 1,061,240 | 35.33% | 仅用于推导 `family` |
| `config.architectures` | 1,034,308 | 34.43% | 未使用 |
| `pipeline_tag` | 1,022,496 | 34.04% | 仅 F9 的任务证据 |
| `cardData.language` | 455,140 | 15.15% | 未使用 |
| `gguf` | 195,765 | 6.52% | 未使用 |
| `trendingScore` 非零 | 8,119 | 0.27% | 未使用 |

标签一项单独看：全湖有 389,302 个不同标签、19,484,160 次出现，平均每个模型 6.49 个，
79.17% 的模型至少有一个非 `region:` 标签。按最小出现次数 20 折叠，标签词表是 19,202 项，
与现有 41,056 行的 `family_vocab` 同一量级，做成 embedding 表在工程上没有新问题。

标签按命名空间的分布也说明它不只是文本噪声：

| 命名空间 | 出现次数 | 可以变成什么 |
|---|---:|---|
| 无前缀（`gguf`、`lora`、`peft`、`4-bit`、`merge`、`conversational` 等） | 12,452,682 | 结构化属性 |
| `region:` | 3,003,771 | 无信息，全湖都有 |
| `base_model:` | 1,745,506 | 血缘（已用 `baseModels`） |
| `license:` | 1,077,678 | 结构化属性 |
| `arxiv:` | 733,767 | 论文节点 |
| `dataset:` | 359,265 | 训练数据集声明边 |

## 3. 通道清单

按信号进入系统的位置分成五组。每条通道给出它能触及多少个模型、采集成本、集成成本，
以及它预期改善哪一类指标。标注「实测」的数字来自附录 A 的扫描或已有的 F 系列报告，
其余是估计并注明依据。

### A 组：输入侧，让三百万个模型彼此可区分

这一组针对问题二。共同前提是重跑 F4（本地 712.7 秒）、重建 F5（47.6 秒）、
重训 F6（每 seed 约 7 分钟）、重导出 F7、重测 F8。

**A1 已在盘上的结构化字段。** 把 §2 表里的字段接进 `x_m`，采集成本为零，
全部已经在 `candidates_full` 的 61 个分片里。
建议分两路：高基数的走描述符文本（`architectures`、`library_name`、`pipeline_tag`），
低基数高频的走 embedding 表（`license`、`language`、量化标志、`library_name`）。
收益的量级可以先给一个上界：目前 71.93% 的模型描述符里连参数量子句都没有，只有名字加家族；
接上这批字段后，79.17% 的模型会拿到至少一个此前不存在的判别性符号。

**A2 结构化特征用 embedding 表而不是塞进文本。** 理由是 MiniLM 对
`license:apache-2.0`、`4-bit` 这类标识符的表示不稳定，而离散 id 的行身份是确定的，
并且可以像 `family_id` 一样被契约检查钉住。F5 §5 抓到的 `family_vocab` 少一行就是这类问题，
它不会让任何一步失败，只会让 embedding 表的行身份错位。
代价是 Stage-2 契约要增加新表的双射性检查。

**A3 README 全文。** 这是 `x_m` 里唯一缺失的真正语义。两条路：
一次性下载社区维护的卡片转储 `librarian-bots/model_cards_with_metadata`
（实测 747,323 行、1.31 GB，字段含 `modelId`、`card` 全文、`tags`、`pipeline_tag`），
或者自己抓 `https://huggingface.co/{id}/raw/main/README.md`。
前者一次下载即可，但覆盖率与时效必须先核（见 §6）；后者需要三百万次请求，
按 F1 实测的匿名限流 500 请求 / 300 秒推算约 20.8 天，带 token 的额度尚未实测。
集成成本方面，MiniLM 输入上限 256 token，全文必须截断，截断策略决定实际拿到多少信号；
按 F4 实测的 4,900 rec/s 与 55.3 字符外推，截断到 256 token 后编码速率大致降到
500–600 rec/s，全湖约 90 分钟，本地可承受。

**A4 文件清单（`siblings`）。** HF 列表端点支持 `expand[]=siblings`，实测 payload 只增加 16%
（同一页 100 条：316,950 → 368,394 字节），平均每个模型 10.5 个文件。
因此「重爬一遍全湖并带上文件清单」的成本约等于 F1 那次的 27.5 分钟与 202 MB。
文件名直接给出量化级别（`*.Q4_K_M.gguf`）、是否是 LoRA（`adapter_config.json`）、
分片数、是否带 ONNX / CoreML / OpenVINO 导出、是否带分词器。
这一条直接打的是 hub 过平滑：`qwen1.5-0.5b` 的 32,534 个子模型在文件清单上彼此不同，
而在当前的名字加家族描述符上几乎相同。

**A5 `transformersInfo` 与 `inferenceProviderMapping`（同一次重爬）。**
实测两者都是列表端点接受的 `expand[]` 字段，四个小字段合计只让 payload 增加 4%。
`transformersInfo` 给出 `auto_model` 类与推导出的 `pipeline_tag`，
可以补上目前缺 `pipeline_tag` 的 65.96%；`inferenceProviderMapping` 给出部署状态、
任务与实测延迟，是 F9 第二层可用性门的权威版本。
经实测，`usedStorage`、`availableInferenceProviders`、`securityRepoStatus` 在列表端点返回 400，
不能用这条路拿。

**A6 safetensors 头部。** 用 HTTP Range 取权重文件的前若干 KB，得到全部张量名、形状与 dtype，
由此得到精确的隐藏维度、层数、词表大小与量化 dtype。846,829 个模型有 safetensors。
成本是每个模型约两次 range 请求（先读 8 字节头长，再读头），瓶颈是请求数而不是流量。
建议只对血缘 hub 代表与 `warm`、`cool` 两层做，不做全湖。

**A7 `config.json` 全文。** 比 A6 便宜，单次请求、通常 1–5 KB，
只需要对 `config` 未随 API 返回的 65.57% 抓。三百万次请求的限流问题与 A3 相同。

**A8 分词器指纹。** `tokenizer.json` 通常几 MB，全湖不可行；
对每个血缘 hub 的代表模型抓一份，可以给出语言与词表覆盖的判别特征。

**A9 权重级指纹。** 下载权重算低秩摘要或参数统计。传输代价与 E 轴同量级
（16,915 个模型即 73.5 TB），全湖是 PB 级。不建议作为覆盖性方案，
只在 C6 的定向评测里顺带产出。

### B 组：图结构，给暗物质接上边

这一组同时服务问题一与问题二：新边既让消息传递触及暗物质，也可能把监督沿新路径传播。
下表的「可达」是实测：分母是 2,970,293 个零监督模型，
「与监督相连」指该模型通过这条通道与至少一个带监督模型共享一个节点。

| 通道 | 携带该信号的零监督模型 | 其中与监督相连 | 采集成本 |
|---|---:|---:|---|
| B1 作者节点 | 2,599,329（组内不止一个模型） | 217,643（7.33%） | 0 |
| B2 arXiv 论文节点 | 643,986（21.68%） | 478,887（16.12%） | 约 180 次 arXiv API 请求（取摘要） |
| B3 声明的训练数据集边 | 200,915（6.76%） | 78,052（2.63%） | 0 |
| 三条合计（去重） | — | 715,832（24.10%） | — |

**B1 作者节点。** 全湖 597,636 个不同作者，100% 覆盖，中位组大小为 1，
373,612 个作者只有一个模型，最大的作者有 68,357 个模型，12,344 个作者组含至少一个带监督模型。
成本为零，但它会引入一个新的 hub：68,357 个模型挂在一个节点上比现有最大的血缘 hub
（`flux.1-dev` 的 43,346 个）还大，必须施加与监督边同样的度数上限。

**B2 arXiv 论文节点。** 全湖 18,047 个不同 arXiv id，其中 1,155 个的关联模型里含带监督模型。
只做节点与边是零成本；再花约 180 次 arXiv API 请求（按 100 个 id 一批）取回摘要，
就能给 643,986 个此前只有名字的模型注入一段真实的主题文本。
按「每单位成本触及的暗物质」算，这是清单里最划算的一条。

**B3 声明的训练数据集边。** 224,974 个模型声明了训练数据集
（`cardData.datasets` 与 `dataset:` 标签的并集），共 359,265 条声明，
其中 244,606 条（68.1%）能解析到真实的 HF 数据集仓库，
144,729 个模型（占全湖 4.82%）由此至少获得一条可解析的数据集边。
42,235 个可解析的不同名字里只有 3,610 个已经是数据集节点。
这条边必须作为新的关系类型 `declared_trained_on` 存在，不能并进 `trained_on`：
它表达的是「训练于」而不是性能，混进去会污染 gold 的语义，
并且会制造训练集到查询集的直接泄漏路径。

**B4 血缘边的关系类型。** `relation` 已经在盘上（finetune 325,400 / adapter 314,944 /
quantized 167,522 / merge 14,669 / 未声明 36,530），但消息传递目前只用拓扑。
把 relation 作为边特征接进去，成本为零，
而且它是让同一个 hub 下的子模型彼此可区分的最直接手段之一。

**B5 Spaces 共现边。** 列表端点接受 `expand[]=spaces`，可在同一次重爬里拿。
它给出「哪些模型被同一个应用使用」，是一条与血缘、作者都不同的关系。收益量级尚未测。

**B6 标签共现二部图。** 把出现次数不少于 20 的 19,202 个标签作为节点。
零成本，但需要度数上限，否则 `safetensors`（1,343,469 个模型）会变成一个吞掉全图的超级节点。

**B7 兄弟边。** 同一个 `base_model` 的子模型之间目前只能通过父节点二跳相连。
显式建边会让 hub 内部的边数爆炸（`flux.1-dev` 的 43,346 个子模型两两成边是 9.4 亿条），
所以只能采样。这条通道更适合放在损失函数里（见 E2）而不是放进图里。

### C 组：目标侧，新的性能标签

**C1 `mteb/results`。** 实测 8,800,356 行、298 MB，
字段是 `(model_name, model_revision, task_name, split, language, subset, score, is_public, trained_on)`。
一次下载即可，是清单里最可能显著改变监督规模的一条——现有全部监督也才 247,803 条边。
关键的未知量是它与现有边的重叠：MTEB 的结果本来就会写进模型卡片的 `model-index`，
而 `hf_model_index` 与 `modellens_v2` 两个来源都大量含 MTEB 记录。
因此 P0 的第一件事是测重叠，在测出来之前不要把 880 万行当成 880 万条新监督。
附带价值是 `trained_on` 字段直接标出了训练集污染，这是我们现有六个来源都没有的。

**C2 Open LLM Leaderboard 结果。** `open-llm-leaderboard-old/results` 与
`open-llm-leaderboard/{org}__{model}-details` 系列。
datasets-server 对前者报 0 行，说明它不是可直接转 parquet 的表，需要按仓库文件枚举；
后者是每个模型一个仓库，需要先枚举再抓。成本以请求数计，不需要 GPU。

**C3 Open ASR Leaderboard 结果表。** 注意 `hf-audio/open-asr-leaderboard` 实测 26.4 GB，
那是评测用的音频数据而不是结果表；要找的是结果仓库。

**C4 其它排行榜。** Chatbot Arena Elo、OpenCompass、HELM。
HELM 需要单独说明：E 轴实测它的 510 个查询里 0 个能解析成可下载的 HF 数据集仓库，
所以 HELM 的结果可以作为监督进来，但它对应的查询节点拿不到真实的 `x_d` 卡片文本。

**C5 从卡片正文抽取评测表。** 747,323 份卡片里有相当一部分把结果写成 Markdown 表格
而不是结构化的 `model-index`。用小模型抽取，成本按 747K 份乘约 1K token 计约 7.5 亿 token。
产出是伪标签，必须单列为一个来源，与人工核验的样本对账后再决定是否进 gold。
`rf-gold-2.0` 已经要求 A 轴数字能按来源拆分，这条通道正好需要这个能力。

**C6 定向新评测。** 不追求覆盖率，追求每 GPU-hour 的信息量。血缘的度数分布使这件事可行：

| 评测对象 | 覆盖的子模型 | 占有父模型的比例 | 占全湖 |
|---|---:|---:|---:|
| top 10 个父节点 | 185,984 | 20.85% | 6.19% |
| top 200 个父节点 | 469,846 | 52.67% | 15.64% |
| top 1,000 个父节点 | 640,491 | 71.80% | 21.32% |
| top 2,000 个父节点 | 684,581 | 76.74% | 22.79% |

按 E 轴实测的 0.175 GPU-hours 每次评测，1,000 个父节点各评 3 个任务是 3,000 次评测、
约 525 GPU-hours。对照 [`RESOURCE_SUPERVISION_AT_3M.md`](RESOURCE_SUPERVISION_AT_3M.md)
的全湖 25% 覆盖需要 371,000 GPU-hours，这是三个数量级的差别。

这条通道依赖一个尚未验证的假设：子模型的性能与父模型相关，且相关程度依 relation 类型而定。
量化与 adapter 大致保留父模型的能力，finetune 与 merge 不一定。
先验证再投入的做法是：取 200 个父节点，每个父节点抽 5 个不同 relation 的子模型，
共 1,200 次评测、约 210 GPU-hours，测出按 relation 分类的性能差分布。
若差的方差过大，这条通道就退化为「只给父节点加标签」，覆盖收益不成立。
传输成本上有一处对我们有利：adapter 与量化子模型都远小于父模型，
所以子模型那一侧的传输远低于按每模型 4.35 GB 的均值估计。

**C7 时间后验，零成本。** F9 §8 已经冻结了 `t0_recommendations.parquet`（15,580 行）。
之后每次重爬快照，新增的 `model-index` 记录就是免费的新标签，
并且因为 `t0` 在它们出现之前就冻结了，它们同时是独立的验证证据。
需要先约定「多久抓一次」与「多少条新记录算够」。

**C8 不确定性采样。** 在已训练好的表示上，挑选「我们排得高但没有记录」且「同任务证据强」的
(query, model) 对去评测。F9 §6 给出了这条路的上界参照：`random_task_pool` 在已知任务、
候选池只有几十到几千个的条件下拿到 `recorded_gold@10 = 0.2349`，
说明先判对任务再缩小候选集的空间很大。

### D 组：数据集侧，查询侧同样饥饿

问题一的一半在查询侧。18,729 个数据集节点里只有 3,928 个（20.97%）用上了真实卡片，
其余是名字文本；`e_stats` 的最后两列（`has_content`）从 D0 起就恒为 0。

**D1 扩张数据集节点集合。** B3 的 42,235 个可解析声明名字里只有 3,610 个是现有节点。
把可解析的名字都建成节点，数据集侧规模会从 18,729 涨到五万量级，
而且新节点更可能有真实卡片：全站 1,008,416 个数据集仓库里 360,674 个带描述文本。

**D2 别名表。** E 轴实测约 100 条人工别名可以把查询到 HF 仓库的解析率从 23.2% 提到约 50%
（`flores200-devtest → facebook/flores`、`ntrex128 → davidstap/NTREX` 这一类）。
同一张表既服务补评，也服务 `e_card` 的卡片匹配。必须在看到任何精度数字之前冻结，
否则它就变成了按结果挑数据集。

**D3 数据集内容视图。** datasets-server 的 `/first-rows` 端点可以免费取回每个数据集的前若干行。
按当前 18,729 个节点算是 18,729 次请求，按 D1 扩张后是五万量级。
这会第一次把 `has_content` 从 0 变成真实值，也是 `x_d` 侧最大的一块未开采信号。
需要先测有多少数据集启用了 viewer。

**D4 数据集卡片的结构化字段。** `task_categories`、`task_ids`、`size_categories`、
`language`、`multilinguality`、`source_datasets` 已经在 F1.5 的抓取里，
目前只作为 `e_card` 的文本输入，没有做成离散特征。零成本。

### E 组：目标函数，让信号变成每个节点的梯度

这一组不采集任何新数据，但它决定采集来的信号能不能变成梯度。
按 F6 实测每个 seed 约 7 分钟，六个配置乘 3 个 split seed 乘 3 个 init seed 共 54 次全湖训练，
合计约 6–8 GPU-hours。

- E1 无监督均匀性或方差约束，直接对抗 98.47% 的塌缩。
- E2 同 hub 负样本。F8 §10 指出这是目前唯一剩下的路，因为 `num_layers` 已经是 1，减不动了。
- E3 掩码属性预测：遮住 tag、architecture、license 或 size 桶再预测。每个节点都有梯度，
  且预测目标就是 A1 新接进来的那些字段，与 A 组天然配套。
- E4 模型与卡片文本的对比学习：模型节点嵌入对齐其 README 嵌入，依赖 A3。
- E5 血缘链路预测：892,081 条正样本，零采集成本。
- E6 输入残差或跳连，防止单层 GNN 把输入的差异抹平。
- E7 数据集侧类别特征修复与共享投影的偏置检查，两项都在 F8 的未决清单里。

A、B、C、D 与 E 的关系需要写清楚：前四组提供信号，E 提供把信号变成每个节点梯度的机制。
只做前四组而不动目标函数，新特征仍可能被平滑掉；只做 E 而不加信号，
均匀性项会把内容上本来就没有差别的节点推开，得到的是噪声而不是语义。
这两种失败模式在实验设计上要能分辨，办法是把 E 组单独作为一个消融臂先跑一次。

## 5. 验证协议

每条通道单独 A/B，用同一套 harness（`scale1m/eval_rf.py` 与 `scale/global_metrics.py`），
同一批查询，三个 split seed。理由是 F8 实测 seed 之间 `gold@10` 在 0.040 到 0.070 之间，
单 seed 的差异会淹没多数单通道的效果。

按 §1.1 分开预注册：

| 通道组 | 主指标 | 次要指标 |
|---|---|---|
| A、B、E | 层内平均余弦、有效维度、`qwen1.5-0.5b` 子模型两两余弦、`family_diversity@10` | `root_gold@10`、`same_task_evidence@10` |
| C、D | `gold@10`、`median rank / N`、`recorded_top3@10` | `observed_hit1`、`record_coverage@10` |

三条硬性有效性要求：

新监督来源必须在合并之后重新做 root-aware 划分。新来源会带进测试划分里已有的
(模型, 数据集) 对，沿用旧划分就是直接泄漏。`mteb/results` 的 `trained_on` 字段
还要单独用来标出训练集污染的记录。

跨版本的 `gold@10` 不可直接比较。gold 由该节点上分数最高的模型定义，
加入新来源会改变 gold 本身。要么固定一个「评测用监督集」不再变动、新来源只进训练，
要么两套口径都报并写明哪个数字对应哪套监督。这一条如果不先定下来，
后面所有的对比都会失去意义。

`declared_trained_on` 边不进 gold，伪标签来源单列。
`rf-gold-2.0` 已经要求 A 轴数字能按来源拆分，新增来源要延续这个义务。

## 6. 风险与未决

新通道会制造新的 hub。最大的作者有 68,357 个模型，`safetensors` 标签挂着 1,343,469 个模型，
两者都大于现有最大的血缘 hub（43,346）。作者边与标签边都要有度数上限，
上限要在合并之后只施加一次。F2 §9 已经踩过「截断两次」的坑，做法可以照搬。

卡片转储的覆盖可能偏向已经不暗的那一部分。`librarian-bots/model_cards_with_metadata`
有 747,323 行，对应我们 3,003,759 条快照是 24.9% 的上限，
但它的抽取时间与选择规则未知，很可能偏向下载量高、时间较早的模型，
也就是已经有监督的那一批。P0 必须测两件事：与我们快照的 id 交集有多大，
以及这个交集在 `warm`、`cool`、`cold`、`frozen` 四层上的分布。
如果它压倒性地落在 `warm` 与 `cool`，这条通道对问题二没有帮助。

`mteb/results` 与现有边可能高度重叠。MTEB 的结果本来就写进模型卡片，
而 `hf_model_index` 与 `modellens_v2` 都含大量 MTEB 记录。
880 万行不等于 880 万条新监督，重叠测出来之前不要用这个数字讲结论。

更多信号不必然提升 `gold@10`。F8 §2.2 已经说明瓶颈在带监督模型之间的排序。
A 组与 B 组主要改善的是塌缩、冷启动与列表多样性，把它们的预期写成 `gold@10` 的提升
会导致一次预注册失败。这就是 §1.1 要分开验收的原因。

时间口径不一致。湖快照是 2026-08-18，卡片转储与各排行榜结果各有自己的时间。
模型在两个时间点之间可能被删除、改名或换 revision。
F7.2 已经量化过这个方向的代价：我们 top-10 里 29% 的模型已从 HF 下架。
新来源要逐条记录来源快照日期，`in_snapshot` 的做法要延续。

许可与合规。转载第三方结果集要看各自的许可。arXiv 摘要、HF 数据集卡片、
排行榜结果的许可不一致，需要逐个记录，并在报告里写明哪些结果来自可再分发的来源。

限流额度未实测。F1 那次是匿名的，500 请求 / 300 秒。
A3、A6、A7 这三条以请求数为瓶颈的通道，可行性完全取决于带 token 的额度，
而这个数至今没有测过。P0 应该用一次一千请求的小批量测出实际额度再排期。

尚未回答的问题。每条通道单独的效果、通道之间是互补还是冗余、
以及「信号量到多少才不塌缩」，都没有实验依据。
`RESOURCE_SUPERVISION_AT_3M.md` 已经写明没有任何实验建立过标签数量的阈值。
本文档同样不承诺阈值，它承诺的是一份按成本排序的通道清单和各自可测的收益上界。
