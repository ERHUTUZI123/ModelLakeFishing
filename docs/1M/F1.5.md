## 2. `x_d` 的构造没有变

需要先澄清一件此前在计划里写错的事：历史各档的 `x_d` 不是 probe network 嵌入。
`hgraph_ml_v2.pt` 的 `xd0_meta` 记的是 `has_content_view=False`、`probe_views="DEFERRED (D0-v1 scope note)"`，
即那条路当年就没有启用。实际构造从 D0 起就是同一个三视图拼接：

```
x_d (458) = [ e_name 64 (哈希, seed 43) ‖ e_card 384 (MiniLM) ‖ e_stats 10 ]
similar_to = e_card 上的余弦 KNN, k=20
```

`e_card` 的文本来自 [`dataset_descriptor.py`](../../scale1m/dataset_descriptor.py) 的
`dataset_descriptor()`：`名字 + task_categories + tags(≤10) + description(≤400 字符)`，
全部字段都是 HF 数据集卡片的字段；缺卡片时退化为名字本身。
ModelLens 各档（12K / 30K / 100K）走的是同一个公式，只是文本取自语料里现成的 `desc` 列。

所以本阶段不是引入新方法，而是**把 `e_card` 的文本源从已消失的语料换回 D0 当年用的 HF 卡片**。
`dataset_descriptor()` 可以原样复用，字段一一对应。
`e_stats` 也不受影响，它只依赖监督边（边数、`value_norm` 的均值/标准差/最小/最大、root 大小、`gold_evaluable`），
这些 F1 的 208,035 条监督边都能算；D0 多出的 `n_runs` 求和本档没有，填 1；`has_content` 恒 0，`--content` 那条路不启用。

## 3. 数据集索引枚举

```bash
python -m scale1m.hf_crawl_datasets --out $MLF_DATA_DIR/data1m/datasets_full
```

新建模块 [`scale1m/hf_crawl_datasets.py`](../../scale1m/hf_crawl_datasets.py)，
沿用模型侧的分片、断点续爬、限流退避与 `PROVENANCE` 体例，只换端点与字段集。

选择枚举全站而不是按 id 逐个取，理由是成本：匿名限流 500 请求 / 300 秒，
7,700 次单点请求约需 16 个窗口（一小时以上），而按每页 1,000 条枚举整个索引只要约 1,009 个请求。
枚举还额外回答了一个单点请求答不了的问题——哪些名字根本不是 HF 仓库。

| 量 | 实测 |
|---|---|
| 记录数 | 1,008,417 |
| 页数 | 1,009 |
| 墙钟 | 411.5 秒（6.9 分钟） |
| 落盘 | 82 MB（11 分片，gz） |
| 重复 | 0 |
| 重试 | 0 |
| 限流休眠 | 2 次，合计 200 秒 |
| 终止方式 | 游标耗尽 |

字段集是 `dataset_descriptor()` 需要的那些加上流行度与时间信号：
`description`（截断到 1,000 字符）、`tags`、`cardData` 的 `task_categories`/`task_ids`/`language`/
`size_categories`/`license`/`multilinguality`/`source_datasets`，以及 `author`、`downloads`、`likes`、
`createdAt`、`lastModified`。

### 3.1 快照口径

| 量 | 值（UTC） |
|---|---|
| 枚举开始 | 2026-08-18T21:32:36Z |
| 枚举结束 | 2026-08-18T21:39:27Z |
| 最新一个数据集的 `createdAt` | 2026-08-18T21:31:50Z |
| 最旧一个数据集的 `createdAt` | 2022-03-02T23:29:22Z |

排序与游标性质与模型侧相同：`createdAt` 降序，游标键是不可变的 `_id`，因此枚举期间新建的仓库落在已翻过的头部、
不被计入，已存在的不会被跳过。下界同样是 HF 的 `createdAt` 回填日（2022-03-02），不是真实的最早发布时间。

模型快照与数据集快照相隔约 3 小时（18:29 与 21:39），两者仍属同一天、同一份封闭世界，
但报告里两个窗口分别记录，不合并成一个时刻。

## 4. 匹配策略与命中率

`model-index` 里的数据集名是作者手写的，形态不一：有的是完整仓库 id（`openai/gsm8k`），
有的是裸的历史名（`glue`），有的根本不是数据集（`lunarlander-v2`）。因此匹配分三种情况处理。

先看三种匹配各自的量（8,793 个节点）：

| 匹配方式 | 节点数 | 占比 |
|---|---|---|
| id 完全相同 | 2,353 | 26.76% |
| 仅基名相同且索引内唯一 | 659 | 7.49% |
| 基名相同但索引内有多个候选 | 1,626 | 18.49% |
| 完全没有 | 4,155 | 47.25% |

基名回退需要再分一次。659 条里有 **85 条（12.9%）原名带属主前缀**，
例如 `abhiprd20/maithili_sentiment_8k` 匹配到了 `abhiprd2000/maithili_sentiment_8k`，
`alexandreteles/told_br_binary_sm` 匹配到了 `inctdd/told_br_binary_sm`——这是**另一个仓库**，
把它的卡片挂到这个节点上是错误归属。剩下 574 条原名是裸名，属于历史规范名的正常解析。

歧义那 1,626 条可以用「取下载量最高的候选」全部解开，命中率会从 33.29% 升到 52.75%，
但抽样看这个做法不可靠：`a` 会从 116 个候选里挑一个，`abdshhayan/mbpp` 会被解成
`google-research-datasets/mbpp`。多出来的覆盖率是用错误归属换来的。

**定案策略**：

| | 处理 |
|---|---|
| id 完全相同 | 采用（2,353） |
| 基名相同、且原名是裸名、且索引内唯一 | 采用（574） |
| 基名相同但原名带不同属主 | 不采用（85） |
| 基名有多个候选 | 不采用（1,626），不按下载量猜 |
| 无匹配 | 不采用（4,155） |

不采用的一律退到 `dataset_descriptor()` 已有的兜底路径，即「清洗后的名字 + 任务」文本。
每个节点的来源记在 `dataset_cards.parquet` 的 `card_source` 列，取值为
`hf_card` / `name_only` / `name_only_ambiguous` / `name_only_cross_owner_rejected`，
便于 F4 之后在报告里按来源分层。

### 4.1 定案策略下的覆盖率

| 口径 | 节点数 | 有 HF 卡片 | 其中有描述文本 | 按监督记录加权 |
|---|---|---|---|---|
| 全部节点 | 8,793 | 2,927（33.29%） | 2,079（23.64%） | 54.18% |
| 排除 RL 任务 | 8,006 | 2,904（36.27%） | 2,064（25.78%） | 58.56% |
| **查询集：排除 RL 且模型数 ≥3** | 3,231 | 1,147（35.50%） | 857（26.52%） | **59.26%** |
| 排除 RL 且模型数 ≥10 | 1,535 | 537（34.98%） | 410（26.71%） | 60.08% |
| 排除 RL 且模型数 ≥20 | 1,176 | 416（35.37%） | 301（25.60%） | 59.10% |

按节点数看命中率稳定在 33–36%，按监督记录数看是 54–60%，说明**卡片命中的节点系统性地更"重"**：
它们承载的监督边多于平均。这对 `e_card` 的实际作用是好消息——训练里权重高的那些数据集节点，
更可能有真实描述。

带描述文本的比例（约 24–27%）低于有卡片的比例（约 33–36%），差额是那些仓库存在但描述为空的节点，
它们仍能拿到 `tags` 与 `task_categories`，`dataset_descriptor()` 会用这两项加名字组文本。
匹配上的描述平均长度 514.9 字符，而描述符只取前 400 字符，所以截断是常态而不是例外。

### 4.2 没匹配上的是些什么

4,155 个未匹配节点里，按节点数只有 748 个的任务字段是强化学习，
但**按模型数计有 61.03% 属于 RL 环境**：`taxi-v3`（7,857 个模型）、
`frozenlake-v1-4x4-no_slippery`（7,510）、`spaceinvadersnoframeskip-v4`（5,393）、
`pixelcopter-ple-v0`（3,800）、`pandareachdense-v3`（2,184）等。这些是 Gym/Gymnasium 的环境名，
HF 上没有对应的数据集仓库，匹配不上是正确行为而不是缺陷。它们按 D-59 已经排除出查询集。

其余未匹配的多是作者自造的名字、内部路径、或者已被删除的仓库。这部分只能用名字文本，
在报告里按 `card_source` 分层披露。

## 6. 与计划的偏离

| # | 计划原文 | 实际 | 理由 |
|---|---|---|---|
| 1 | 「对 7,700 个数据集 id 调 HF datasets API」 | 枚举全部 1,008,417 个数据集仓库再做本地 join | 7,700 次单点请求要 16 个限流窗口（一小时以上），枚举只要 1,009 个请求、6.9 分钟。枚举还能回答「哪些名字不是 HF 仓库」 |
| 2 | 计划称历史各档的 `x_d` 是 probe network 嵌入、与本档不可比 | 更正：历史各档从 D0 起就是 `[e_name‖e_card‖e_stats]`，probe views 从未启用（`xd0_meta` 记为 DEFERRED） | 见 §2。方法本身没有变，只是 `e_card` 的文本换回 HF 卡片，可比性比原先写的强 |
| 3 | 计划未规定匹配歧义怎么处理 | 定案为不按下载量猜，跨属主的基名匹配也不采用 | 多出来的 19 个百分点覆盖率是用错误归属换的，见 §4 |
| 4 | 计划预期「不到一分钟」 | 6.9 分钟 | 原估计基于 7,700 个 id，实际是全量枚举 |

## 8. 扩展执行：合并后的全部数据集节点（2026-08-19）

上游 [`F2.md`](F2.md) §9 把监督扩展到六个来源后，数据集节点从 8,793 涨到 18,729，
新增的那些也需要 `e_card`。这一节记录扩展匹配的结果。数据集索引没有重爬，
沿用 §3 的那份 1,008,417 条快照，只是在本地重做了 join。

匹配逻辑抽成了模块 [`scale1m/match_dataset_cards.py`](../../scale1m/match_dataset_cards.py)，
在 §4 的两级之外增加了第三级：形如 `a/b` 的名字若整体匹配不上，再用 `a` 试一次。
历史图里 D0 系的节点有 94% 是 `数据集/配置` 形式（`ag_news/default`、`ai2_arc/arc-challenge`），
而数据集卡片描述的是整个数据集、对所有配置通用。这一级单独记为 `hf_card_via_parent`，
不与精确匹配合并计数，因为 `a/b` 在语法上无法区分「属主/名字」与「数据集/配置」。

### 8.1 覆盖率

| 口径 | 节点 | 有卡片 | 占比 | 边 | 按边加权覆盖 |
|---|---|---|---|---|---|
| 全部合并节点 | 18,729 | 3,928 | 20.97% | 247,803 | 27.25% |
| 查询集（合格 gold 节点） | 7,859 | 1,437 | **18.28%** | 228,348 | **27.87%** |
| 查询集，模型数 ≥10 | 3,450 | 694 | 20.12% | 206,257 | 29.21% |

`card_source` 分布：`hf_card` 3,621、`hf_card_via_parent` 307、`name_only_ambiguous` 2,463、
`name_only_cross_owner_rejected` 529、`name_only` 11,809。

### 8.2 覆盖率按来源差异极大，原因可指认

| gold 来源 | 查询节点 | 有卡片 | 占比 | 按边加权 |
|---|---|---|---|---|
| `hf_effective` | 75 | 75 | 100.00% | 100.00% |
| `hf_model_index` | 1,878 | 908 | 48.35% | 66.37% |
| `a_ctrl_2000m` | 65 | 12 | 18.46% | 21.77% |
| `d0_v1_5` | 1,143 | 197 | 17.24% | 36.10% |
| `diverse_zoo` | 17 | 2 | 11.76% | 3.34% |
| `modellens_v2` | 4,681 | 243 | **5.19%** | **2.83%** |

`modellens_v2` 的 5.19% 不是匹配规则不够好，而是它的数据集名根本不是 HF 仓库：
抽样是 `17 places`、`ace 2004`、`[bird-sql][bird-sql] (dev)`、`2wikimqa_test` 这一类，
它们是 ModelLens 自己的基准标识，只有 13% 带斜杠。任何匹配规则都救不回来，
这些节点只能用名字文本，属于该来源的固有性质。

`d0_v1_5` 从 1.22% 升到 17.24%，正是第三级 parent 查找的作用；剩下的多数落进
`name_only_ambiguous`，因为 `ag_news`、`ai2_arc` 这类经典数据集在今天的 HF 上有大量分叉，
基名不唯一，按 §4 的纪律不猜。

### 8.3 对下游的影响

合并历史监督把查询节点从 2,041 提到 7,859（3.85 倍），但新增的这批节点里只有约 12% 能拿到真实卡片，
因此**评测集变大的同时，数据集侧表示的平均质量下降了**：查询集的卡片覆盖从纯快照口径的 35.50%
降到 18.28%。这不是回退，两种口径衡量的是不同的东西，但报告里必须一起给。

F8 的分层因此需要两个轴而不是一个：`card_source`（数据集侧表示强弱）与 `gold_source`
（标注来自哪次测量）。只按其中一个分层会把两种效应混在一起。
