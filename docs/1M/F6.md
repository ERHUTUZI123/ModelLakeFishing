## 2. 与 F6GPU 外推的差距

两条外推都偏保守，方向一致地高估了成本。

| 项 | F6GPU §5.2 外推 | 实测 | |
|---|---:|---:|---|
| 25 epoch 墙钟 | 约 43 分钟 | **7.1 分钟** | 快 6.1 倍 |
| 峰值显存 | 约 52 GB | **38.0 GB** | 低 27% |

时间那条的错因是把 100K 档的 108.5 秒当成了 GPU 饱和态。100K 的全图前向只占 1.7 GB 显存，
H200 大部分时间没吃满，因此每个节点的成本在 3M 上反而下降，线性外推必然偏高。
显存那条的错因是把 1.737 GB 整体乘以 30.16，而其中 CUDA 上下文与模型参数这一部分不随 N 变化。

有一个内部一致性可以对上：1 epoch 的冒烟作业 `1515703` 用时 37.1 秒，25 epoch 用时 426.4 秒，
差值 389 秒除以 24 个 epoch 得 16.2 秒，反推训练后的评测尾部约 21 秒。两个数互相解释得通。
冒烟的峰值显存 37.991 GB 与正式跑的 38.0 GB 几乎相同，也印证了显存由每步的全图前向决定、
与 epoch 数无关。

## 3. 监督在全量湖上的稀疏度

`train.log` 里 L1 全湖 logQ 的那行给出了一个此前没有的量：整个候选池里有多少模型带训练可见的监督边。

| seed | 带标签模型 | 占全湖 | 最大出度 |
|---:|---:|---:|---:|
| 0 | 37,755 | 1.25% | 1,291 |
| 1 | 39,930 | 1.32% | 1,236 |
| 2 | 35,991 | 1.19% | 950 |

放进历史序列看，这是一个数量级的变化：

| 档 | 带标签模型 / 湖 | 占比 |
|---|---|---:|
| 12K | 11,162 / 12,000 | 93% |
| 30K | 26,508 / 30,183 | 88% |
| 100K | 25,379 / 100,000 | 25% |
| 全量 | 37,755 / 3,016,439 | 1.25% |

采样 softmax 的负样本从这个分布里取，`q_head` 从 100K 档的 0.0006 降到 0.0001。
1Mplan §6 预注册的 `gold@10 ∈ [0.005, 0.15]` 面对的是这个稀疏度，
F8 报数字时应当把这一列一并列出，否则读者无从判断难度。

## 4. 训练内产出的 held-out 数字

`MANIFEST.json` 的 `train_row` 里有 harness 在测试划分上算出的数，它们不是本档的验收口径，
但可以作为「训练确实学到了东西」的旁证。

| seed | `tau_macro` | `head hit@10` | `head ndcg@10` | 计分数据集 |
|---:|---:|---:|---:|---:|
| 0 | 0.0903 | 0.7625 | 0.8092 | 1,558 |
| 1 | 0.0233 | 0.7251 | 0.7977 | 1,153 |
| 2 | 0.0461 | 0.7498 | 0.7768 | 1,595 |

100K 档同一口径是 `tau_macro` 0.077–0.217、`ndcg@10` 0.928–0.948。两档不能并排比较：
监督集换了（六源合并），数据集节点换了，候选池差 30 倍。

`head` 这一族是按每个数据集已观测到的模型算的命中率，历史上查出过它被泄漏抬高
（见 `top1-global-provenance-fix` 的记录），所以 `hit@10 = 0.76` 不是全局 `gold@10`，
不能用它讲结论。全局口径由 F8 的 `scale/global_metrics.py` 给出。

`mean_cos`、`z_m_pr`、`z_d_pr`、`density`、`pd_density`、`dm_hnsw_recall@50` 在
`train_row` 里是 NaN，这是本次显式启用 `--skip-diagnostics` 的结果（§8），
不是训练中出现了 NaN。三份 manifest 的 `no_nan` 都是 true。

该副本已删除并用单一进程从零重传，重传后 `meta.json` 记录的每个文件逐一复算，8/8 命中。

校验过程中发现 F5 留下的一处元数据缺陷：`meta.json` 把 `GRAPH_REPORT.json` 记成了

| | 修正前 | 修正后 |
|---|---|---|
| `GRAPH_REPORT.json` 条目 | `e2d8bf03…` | `53081ab8…` |

本地与远端两份都已修正，F6GPU §6 里预写的 `meta.json` 摘要 `82cb04a7…` 因此不再适用，

## 8. 与计划的偏离

| # | 计划原文 | 实际 | 理由 |
|---|---|---|---|
| 1 | 先 500K 冒烟与三 seed，再全量（1Mplan §5 F6） | 直接跑全量：契约检查 → 1 epoch 冒烟 → 三 seed | 500K 档的图还不存在，`build_graph_rf.py` 没有子采样参数；而「全量跑不跑得动」只有全量冒烟能回答 |
| 2 | 训练内诊断照常产出 | 加 `--skip-diagnostics` | `dataset_to_model_hnsw_recall` 会在 3M 个向量上建一次 HNSW，等于把 F7 的活提前做一遍并要求远端已装 `hnswlib`；`per_dataset_density` 是按数据集节点的 Python 循环，每轮全扫监督边。被跳过的 `mean_cos` / 有效维度由 F8 的 C 轴重算 |
| 3 | 数据集侧任务类别沿用历史做法 | 按 F6GPU §4 的选项 1 照现状跑 | 用户要求排入无人值守依赖链、不等冒烟结果人工提交。代价见下 |
| 4 | `git_head` 非空即算 as-run 代码对账通过 | 形式通过，实质无效 | 见下 |
| 5 | checkpoint 留在远端不下载 | 已回收到本地 `F6_runs/` | 单份 11.6 MB，三个 run 合计 169 MB，回收成本可忽略，且便于 F7 在本地做行序核对 |

第 3 条的代价要写进 F8：RF 图的 `xd0_meta` 是 `num_task_types=1`、`n_class_buckets=1`、
`num_arities=1`，对应三列节点属性全为 0，而 100K 档同一位置是 196 / 7 / 5。
`ablation._ds_kwargs()` 把这三个数直接传给 `HeteroGraphSAGE` 建 `nn.Embedding`，
所以本档里数据集侧这三张表各只有一行，等价于一个共享的可学习偏置。
训练不报错、梯度非零、机制门照常通过，因此它不会以失败的形式暴露出来。
结论是：RF 档与 100K 档之间的差别不止 N，跨档比较必须写明这一项。

第 4 条的具体形态：`metadata/resolved_config.json` 里 `git_head` 是 `7d3457a4…`，
那是远端 bundle 停留的旧 commit，不含 F5/F6 的任何代码，`git_tracked_dirty` 为 true。
`metadata/uncommitted.patch` 只覆盖四个 tracked 文件（`checkpoint.py`、`test_checkpoint.py`、
`train_rung.py`、`check_stage2_contract.py`），而 `graph_store.py`、`train_rung_rf.sbatch`、
`embed_lake_rf.py` 在远端是未跟踪文件，不在 patch 里。
也就是说，单凭 manifest 无法复原本次运行的代码，只能依赖 F6GPU 执行反馈 §2 记的那张 SHA-256 表。
补救办法是把本地这批文件提交推送，并在本文件里补记对应 commit。

## 10. 关于 checkpoint 的两点

`best.pt` 不是择优保存的。配置里 `early_stop=False`，没有验证指标，
`save_best` 做的是把最后一个 epoch 的 checkpoint 重新写一份，
所以 `best.pt` 与 `checkpoint_epoch_24.pt` 的 `model` state_dict 逐张量相等（已复核），
只是重新 pickle 后字节不同。seed 0 的 loss 最低点其实在 epoch 22（16.136，末轮是 16.629）。
F7 用 `last.pt` 或 `best.pt` 都可以，但不要理解成做过模型选择。

`checkpoints_written` 与 `checkpoints_retained` 不同是设计使然：`--ckpt-keep 3` 只保留最新的
三个编号 checkpoint，epoch 4 与 9 写过之后被裁掉，`best.pt` 与 `last.pt` 不参与裁剪。
