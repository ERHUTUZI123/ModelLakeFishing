# F6 监督稀疏问题：与 ModelLens 的监督构造差异及待分析问题

## 1. 当前观察

F6 已经在完整模型湖上完成训练。当前模型湖规模为：

* 模型节点：**3,016,439**
* 带监督的模型：**37,755**
* 带监督模型占比：**1.25%**
* `trained_on` 监督边：**247,803**

历史上随着模型湖扩大，带监督模型比例快速下降：

| 档位   |        带监督模型 / 模型湖 |        占比 |
| ---- | -----------------: | --------: |
| 12K  |    11,162 / 12,000 |       93% |
| 30K  |    26,508 / 30,183 |       88% |
| 100K |   25,379 / 100,000 |       25% |
| Full | 37,755 / 3,016,439 | **1.25%** |

这里最值得关注的不是监督模型绝对数量没有增加，而是：

> 从 100K 扩到约 3M 时，候选模型规模增加了约 30 倍，但带监督模型只从 25,379 增加到 37,755，约增加 1.49 倍。

也就是说，新加入的约 290 万个模型几乎全部来自没有公开 benchmark observation 的长尾。

这使当前 Full Lake setting 与之前 12K、30K、100K 的 setting 有了本质区别。

---

## 2. 当前需要思考的问题

最直接的问题是：

> 当只有 1.25% 的模型节点直接带有监督时，当前 GraphSAGE / retrieval representation training 是否仍然能有效地塑造整个 3M 模型空间？

这里不要预设答案是“肯定不行”，但需要认真分析监督信号是怎样传播到剩余 98.75% 模型上的。

尤其要区分以下几类信号：

1. 直接的 `trained_on` / benchmark supervision；
2. `is_base_of` lineage 边；
3. model metadata；
4. architecture / family 信息；
5. model name / card embedding；
6. 图结构中的 message passing；
7. 其他 contrastive / structural objective。

需要确认当前 F6 objective 中：

* 哪些 loss 真正受到监督边驱动；
* unlabeled model 是否只是作为 message-passing 中间节点；
* lineage / similarity 边是否本身提供了足够强的约束；
* 当监督节点比例从 25% 降到 1.25% 时，representation learning 的机制是否发生了质变。

---

## 3. 不要把 ModelLens 的 47K 模型与我们的 3M 模型直接比较

一个很容易产生误解的地方是：

> ModelLens 看起来拥有非常密集的监督，而我们只有 1.25% 的模型有监督。

但两边的 model universe 并不相同。

ModelLens 最终语料大约包含：

* **47,062 个模型**
* **9,682 个数据集**
* **1,623,284 条 model–dataset/task/metric performance interactions**

它的 model universe 本身主要就是：

> 可以从公开 benchmark、leaderboard 或模型文档中抽取到 evaluation record 的模型。

也就是说，ModelLens 并没有先收集 Hugging Face 上几百万模型，然后发现其中只有约 1% 有标签，再在整个湖上训练。

它实际上是在一个 **evaluation-rich observed subset** 上构造训练语料。

如果简单地把 ModelLens 的约 47K observed models 放到我们当前 3.016M 的全湖分母里：

```text
47,062 / 3,016,439 ≈ 1.56%
```

这个比例其实和我们的：

```text
37,755 / 3,016,439 ≈ 1.25%
```

并没有数量级差异。

因此：

> ModelLens 并没有真正解决“全 Hugging Face 模型中只有约 1–2% 有 benchmark supervision”的问题。

它主要是避免把其余几百万无监督模型作为训练 population。

---

## 4. 真正值得比较的是：每个 observed model 能挖出多少监督

我们当前：

```text
247,803 supervised edges
37,755 labeled models
```

平均：

```text
247,803 / 37,755 ≈ 6.6
```

条监督边 / labeled model。

ModelLens：

```text
1,623,284 interactions
47,062 models
```

平均：

```text
1,623,284 / 47,062 ≈ 34.5
```

条 evaluation interaction / model。

也就是说，即使只比较已经存在 supervision 的模型，ModelLens 的监督密度仍大约是我们的 **5×**。

这个差异需要进一步解释。

## 5. ModelLens 的 supervision 是怎么获得的

根据 ModelLens 论文，其 evaluation records 主要来自三大来源：

### 5.1 Hugging Face Model Hub

这是最大的来源。

ModelLens 不只读取规范化的 structured metadata，而是使用多层 extraction：

1. `.eval_results/` 中的结构化 evaluation 文件；
2. model card 中的标准 `model-index` metadata；
3. README / model card 中的人类可读 benchmark tables。

第三项尤其值得关注。

很多 Hugging Face 模型并不会规范填写：

```yaml
model-index:
```

但 README 中可能存在：

```text
| Benchmark | Accuracy | F1 |
|-----------|----------|----|
| MMLU      | 68.2     | ...|
| HellaSwag | 82.4     | ...|
```

ModelLens 会进一步把这类 Markdown 表格解析为结构化：

```text
(model, dataset, task, metric, score)
```

记录。

论文描述中，这一部分使用了 LLM-assisted extraction。

因此它能获取大量我们当前 structured pipeline 可能没有捕获到的 evaluation observations。

---

### 5.2 Open LLM Leaderboard

Leaderboard 是另一个非常重要的 supervision source。

它的特点不是覆盖特别多模型，而是：

> 每个进入 leaderboard 的模型会被统一跑大量 benchmark。

因此它天然形成一个相对稠密的 performance matrix。

ModelLens 报告：

* 约 **3,495 个模型**
* 约 **147K 条 interactions**

平均每个模型约：

```text
147,000 / 3,495 ≈ 42
```

条 observation。

所以少量 leaderboard 模型就能贡献大量监督边。

---

### 5.3 PapersWithCode

ModelLens 还从 PapersWithCode 获取：

* 模型；
* benchmark dataset；
* task；
* metric；
* reported score。

这一来源规模较小，但可以进一步补充 Hugging Face 本身没有规范记录的 evaluation。

---

## 6. 当前 pipeline 与 ModelLens 的核心差异

我们目前已经做了六源监督合并，最终得到：

```text
247,803 edges
37,755 labeled models
18,729 dataset-task nodes
```

但从目前结果看，和 ModelLens 最大的潜在 coverage gap 不是：

> 我们少发现了几倍数量的 labeled models。

实际上 ModelLens 约 47K observed models，我们已经有约 38K，差距并不巨大。

真正巨大的差异可能是：

> 对已经有 evaluation 的模型，我们每个模型只提取了约 6.6 条 supervision，而 ModelLens 提取到了约 34.5 条。

因此接下来应该重点研究：

### 问题 A：我们缺失的 observation 到底在哪里？

例如：

* README Markdown benchmark tables；
* 非标准 model card 格式；
* `.eval_results/`；
* leaderboard datasets；
* PapersWithCode；
* HELM / OpenCompass / LiveBench 等外部 benchmark source；
* 同一 dataset 下不同 metric / split / config 是否被我们过度压缩。

## 7. 一个尤其需要警惕的问题：我们的 ground truth 语义和 ModelLens interaction 并不完全一样

不要直接假设：

```text
1.62M ModelLens interactions
```

就等价于：

```text
1.62M 我们定义下可训练的 supervised edges
```

需要逐项检查双方的过滤和归一化。

例如我们当前会：

* 只保留 bounded metric whitelist；
* 对一个 dataset node 选择单一主 metric；
* 处理 metric direction；
* 去重；
* 排除某些 RL observation；
* 排除 placeholder dataset；
* 按 `(dataset, task)` 建节点；
* 对监督边有自己的 upper bound / filtering。

而 ModelLens 的 interaction 定义可能更宽。

因此需要拆成两个问题：

1. **ModelLens raw extraction 为什么能拿到这么多 observation？**
2. **如果完全应用我们的 gold / edge definition，这些 observation 最后还能留下多少？**

第二个问题非常重要。

否则容易错误地把 extraction coverage 问题和 supervision-definition 问题混在一起。

## 9. 与 F7/F8 的关系

目前不要因为 1.25% supervision 就提前认定 F6 失败。

F7/F8 仍然应该按预注册方案运行，因为现在最需要知道的是：

> 在真实 3M candidate lake + 1.25% labeled-model coverage 下，现有方法实际还能保留多少 retrieval signal？

如果性能显著下降，需要进一步判断原因属于：

1. candidate-set dilution；
2. supervision sparsity；
3. graph message-passing dilution；
4. dataset-side representation 变化；
5. supervision extraction coverage 不足；
6. train/test distribution 改变；
7. ANN / retrieval 本身的 scaling effect。

因此当前目标不是立刻“修算法”，而是：

> 先把 ModelLens 的 supervision construction 与我们的 pipeline 做严格 apples-to-apples 对齐，再判断 1.25% 到底是自然的全湖现实，还是我们漏掉了大量本来可以获得的监督。

## 10. 最终希望得到的结论

请最后尽量明确回答三个问题：

1. **为什么 ModelLens 可以得到约 1.62M 条 supervision，而我们目前只有约 248K？**
2. **这个差距中，有多少来自 model universe 定义不同，有多少来自 extraction coverage 不同，有多少来自 edge definition / filtering 不同？**
3. **在不改变研究问题“million-scale real model lake retrieval”的前提下，哪些 supervision 可以合理补回来，哪些不能为了提高数字而人为引入？**

## 11. Claude 的想法

本节是对 §1–§10 的回应。§8 要求「不要只根据文档猜，尽量从当前代码确认」，所以下面每个数都来自
F2 的产物或一次对 2026-08-18 快照的重新解析，脚本与 `canonicalize_rf.py` 用的是同一个
`parse_model_index` / `to_float` / `normalize_name`。

结论先说：**这份文档的核心推断需要修正。ModelLens 的监督密度不是我们的 5 倍，
抽取覆盖率上我们与它基本持平；那 5 倍全部来自我们自己定的边粒度。**

### 11.1 先修三个数

`train.log` 里的 37,755 是训练可见的带标签模型数，也就是 root-aware 划分把约两成边移到
验证与测试之后剩下的那部分。监督集本身要从 `supervision_merged.parquet` 读。

| 量 | 文档中 | 实际 | 来源 |
|---|---:|---:|---|
| 带监督模型 | 37,755 | **46,146** | `supervision_merged.parquet` 去重 |
| 占全湖 | 1.25% | **1.53%** | 46,146 / 3,016,439 |
| 每个带标签模型的边 | 6.6 | **5.37** | 247,803 / 46,146 |

文档里的 6.6 是用「全部边」除以「训练可见模型」，分子分母不在同一口径上。
修正后的 1.53% 与 §3 算出的 ModelLens 折算比例 1.56% 几乎相等，两边的
observed-model 覆盖率其实就是同一个数。

### 11.2 抽取覆盖率：实测结果与 §4 的推断相反

我把 61 个快照分片重跑了一遍，只统计 `cardData.model-index`，不含 README 表格、
不含 leaderboard、不含 PapersWithCode：

| 量 | 实测 |
|---|---:|
| 原始指标行 | 2,158,375 |
| 数值可解析的行 | 2,097,081 |
| 去重后的 (模型, 数据集, 任务, 指标) 记录 | 1,435,162 |
| 至少有一条可用记录的模型 | 48,374 |
| 每个 observed model 的记录数 | 29.7 |

与 ModelLens 论文报告的数字并列：

| | ModelLens（三个来源） | 我们（仅 HF model-index） |
|---|---:|---:|
| observed models | 47,062 | 48,374 |
| interactions / records | 1,623,284 | 1,435,162 |
| 每模型 | 34.5 | 29.7 |

也就是说，单靠 HF 的结构化 `model-index`，我们的原始观测密度已经是 ModelLens
全部三个来源合计的 86%。README 表格的 LLM 抽取、Open LLM Leaderboard、PapersWithCode
这三项加起来最多值 1.16 倍，不是 5 倍。§4 那句「即使只比较已经存在 supervision 的模型，
ModelLens 的监督密度仍大约是我们的 5×」在原始记录这一层不成立。

### 11.3 5 倍差距的实际来源：我们自己的三条规则

同样的 1,435,162 条记录，经过我们的规则后变成 74,346 条边：

| 步骤 | 记录/边 | 相对上一步 |
|---|---:|---:|
| 去重后的 (模型, 数据集, 任务, 指标) 记录 | 1,435,162 | — |
| 每个 (数据集, 任务) 节点只用一个主指标 | 143,478 | **1/10.0** |
| 每节点 200 条上限 | 74,346 | 1/1.93 |

更干净的证据是在 ModelLens 自己的语料上做同一件事——同一批数据，只换定义
（数字来自 `docs/scale/P0/P0_EXECUTION.md` 与 `P1/P1_EXECUTION.md`）：

| 步骤 | 行/边 | 模型 |
|---|---:|---:|
| 语料原始行 | 1,807,133 | 47,242 |
| 有界指标白名单（@k 感知） | 972,215 | — |
| 每节点一个主指标 → 可训练边 | 312,986 | 30,183 |

从 1,807,133 到 312,986 是 5.77 倍，而 34.5 ÷ 6.6 ≈ 5.2，两个比值说的是同一件事。
模型数从 47,242 掉到 30,183 也不是抽取问题：有 17,059 个模型只在无界或未白名单的指标上
被测过（perplexity、`cosine_*`、`pass@k`、`quasi_exact_match`），按我们的语义表产不出
[0,1] 的边权。

所以 §10 三个问题的答案是：

1. 差距的来源是边的定义，不是抽取能力。我们把「一个模型在一个 (数据集, 任务) 上的所有指标」
   压成一条边，ModelLens 保留每个 (数据集, 任务, 指标)。
2. 拆开看：model universe 的贡献接近零（48,374 对 47,062）；extraction coverage 约 1.16 倍；
   edge definition 约 19 倍（主指标 10.0 × 上限 1.93）。
3. 见 §11.7 与 §11.8。

### 11.4 §8 的研究计划应当重排

按上面的结果，8.1 的 coverage audit 与 8.2 的 source gap 表能挖出的东西有限，
而且其中一大块可以现在就判掉。

一个可以立刻验证的例子：快照里有 107,115 个模型带 `model-index` 区块，
但只有 48,374 个有可解析的数值。差额 58,741 个模型平均只有 1.03 行，其中
58,616 行（99.8%）是 `reinforcement-learning` 任务的 `mean_reward`，值形如
`"11.05 +/- 5.90"`：

```text
danamr/rl_course_vizdoom_health_gathering_supreme  doom_health_gathering_supreme  mean_reward  "11.05 +/- 5.90"
SepehrB1/ppo-LunarLander-v3                        lunarlander-v3                 mean_reward  "273.06 +/- 24.95"
```

这是 HuggingFace 深度强化学习课程的作业提交。把 `"x +/- y"` 解析出来技术上不难，
能给图加约 5.9 万个模型和 6 万条边，但按 D-59 与 D-61，RL 的 `mean_reward` 既不进 gold
也不进查询集，所以它只会让边数好看，不会让评测集变强。这一条建议直接判定为不做。

### 11.5 README 表格抽取值不值得做

值，但要先把预期定在正确的量级。上界是 §11.2 的 1.16 倍原始记录，而这些记录还要再过
我们的指标语义表（`unknown` 类目前占 25.62% 的记录）与主指标规则。乐观估计，
最终能变成边的部分远小于 1.16 倍，很可能落在 5–15% 的边数增量。

它真正的价值不在边数，而在触达一批目前完全没有记录的模型——那些写了 README 表格
但没写 `model-index` 的作者。这个人数是可测的，而且不需要 LLM 就能先估：
统计快照里 README 含 Markdown 表格且表头命中常见 benchmark 名、同时 `model-index` 为空的模型数。
建议把这个计数作为 8.2 的第一步，用它决定要不要投入 LLM 抽取，而不是反过来。

### 11.6 真正的选择是节点粒度，不是数据量

把 §11.3 换个说法：同一批 1,435,162 条测量，两种切法。

| | 节点 = (数据集, 任务) | 节点 = (数据集, 任务, 指标) |
|---|---|---|
| 我们现在 | 7,944 个节点 / 143,478 条边（HF 源） | — |
| ModelLens | — | 约一个数量级更多的节点，约 10 倍边 |
| 一次查询问的是 | 「这个数据集上哪个模型最好」 | 「这个数据集上按这个指标哪个模型最好」 |

信息量是一样的，差别在目标函数能看到多少、以及一次「查询」意味着什么。
我个人认为 (数据集, 任务) 更接近产品要回答的问题，但这是可以争的，不是对错问题。

如果要改，有一条必须先说清楚：**按指标拆节点会让 `gold@10` 变好看，而那不是变强。**
节点变多、每个节点模型数≥3 的更多、每个查询问的问题更窄，三件事都往上推数字。
拆完之后的 `gold@10` 不能与现在的数字并排比较。这属于 `rf_gold_rules.json` 的版本变更
（`rf-gold-3.0`），要重跑 F2 起的全部阶段，并且新旧两套数字都要报。

### 11.7 §8.4：现在的设计已经是「核心上学、全湖投影」

先回答文档提的那个问题，因为它可以从代码直接确认，不需要新实验。

`l1l3b_config()` 里 `lambda_global = 1.0`、`global_mode = "lake"`。
`train.py` 的循环每一步做一次全图前向（`z_full = model(g_graph)`），
L1 的全湖 logQ 采样 softmax 从全部 3,016,439 个模型里抽负样本，
而正样本只来自监督边。也就是说：

* 无标签模型确实参与 message passing，也确实作为负样本进入目标函数；
* 但没有任何一条 loss 项以无标签模型为正样本；
* `M_train` 与 `M_lake` 在实现上本来就不相等，相等的是 `M_index` 与 `M_lake`。

所以文档设想的那条替代路径（在 supervision-rich core 上学 compatibility space，
再用 metadata / lineage 把全湖投影进去）就是当前架构在做的事，
区别只在负样本是从全湖抽的而不是从 core 抽的。这不需要改方案。

真正没有答案的是「supervision dilution 是否存在、有多大」。这个可以用一次零训练成本的
消融测出来，而且 §3.5 的检索侧曲线本来就要建子采样索引，加一档即可：

> 用同一份 `z_m`，把候选池限制到那 46,146 个带监督的模型建一个索引，
> 与全 3M 的索引比 `median rank / N` 和 `gold@10`。

两者的差值就把 candidate-set dilution 与 supervision sparsity 分开了：
如果限制候选池后指标大幅回升，问题主要在候选池被无标签模型稀释；
如果没怎么回升，问题在表示本身没学好，扩监督才是对的方向。
这条建议我认为应当写进 F8 的 A 轴，它比 §9 列的七个可能原因中的前三个都更容易判定。

### 11.8 不应该为了数字补回来的三样

RL 的 `"mean ± std"`（§11.4）：解析出来只增加边数，不增加可用查询。

模型作者自报的 README benchmark 表格，在没有统一评测协议时跨模型不可比。
ModelLens 用 LLM 抽取同样继承这个问题，它的 1.62M 里有多大比例是自报值、
论文没有拆开报。如果我们要做这一项，抽出来的边应当带独立的 `source` 标记，
并且 F8 要能按「有无自报边」各报一遍。

按指标拆节点之后，拿新的 `gold@10` 与 100K 档或与本次 F6/F8 的数字并排。
理由见 §11.6。

### 11.9 建议的先后

同意 §9：不要因为 1.53% 就提前认定 F6 失败，F7/F8 按预注册方案跑。理由是我们现在
连「表示在 3M 候选池上还剩多少信号」都没有测过，任何补监督的决定都缺一个基线。

在此基础上建议三步：

1. F7/F8 照原计划执行，A 轴按 `rf-gold-2.0` 的报告义务同时报全体候选与仅存活候选。
2. 在 F8 里加 §11.7 的候选池消融。它零训练成本，直接回答「稀释还是稀疏」。
3. 拿到 1 与 2 的数字之后，再讨论 `rf-gold-3.0` 要不要按指标拆节点，
   以及 README 抽取值不值得投入。先做 §11.5 那个不需要 LLM 的计数来定优先级。

### 11.10 需要留意的一处口径差异

§3 引用的 ModelLens 数字是 47,062 模型 / 9,682 数据集 / 1,623,284 interactions，
出自论文；我们 P0/P1 固化下来的 HF v2 语料是 47,242 模型 / 10,479 数据集 / 1,807,133 行。
两套数相差 1–11%，方向一致但不完全相同。做逐项对齐时应当以固化语料为准并注明版本，
论文数字只用于叙述背景。这与 P4 那条纪律是同一条：拿公开件复现出来的数字，
报告时要写明是「可复现 release 版」的口径。
