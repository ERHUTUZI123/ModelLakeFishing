## §1 v1 为什么必须废弃（不是"再爬多一点"能修的）

### 1.1 `sort=downloads` 定义的不是总体，是排行榜

| 观测量 | v1 前 15 万 | 说明 |
|---|---|---|
| 最大发布者占比 | **24.21%**（`mradermacher`） | 前二名 `mradermacher`+`RichardErkhov` = **32.18%** |
| 有效发布者数（1/HHI） | **15.1** | 25,500 个发布者，等价于只有 15 个 |
| `quantized-conversion` 占比 | **61.98%** | 六成是别人权重的重新打包 |
| `text-generation-chat` 占比 | **50.77%** | 而 translation 0.61%、summarization 0.13% |
| 任务分布归一化熵 | **0.601** | 18 个 supertask，实际信息量只有 60% |
| 语种判不出（unknown） | **40.88%** | 见 F-T2-13：v1 的字段裁剪把 `cardData.language` 丢了 |
| 元数据质量通过率 | **70.45%** | v2 阈值 0.35 下 |
| 最大家族占比 | **17.90%** | 有效家族数 31.1 |

**这些不是"样本量不够"，是采样机制本身的产物。** 下载计数器奖励的是"被 pip 拉取的次数"，
而量化搬运仓库天然被自动化流水线反复拉取。再往下爬 100 万条，只会让 `mradermacher` 的绝对数变大。

### 1.2 对下游的具体伤害

- **建图**：一个作者的 14,061 个 GGUF 仓库共享 `e_name` 的组织 token，且各自通过 `base_model` 指回原模型
  ⇒ hub 附近过平滑（CLAUDE.md 三大风险之三）在 100K 上会比 12K 严重得多。
- **表示学习**：61.98% 的样本是同一批权重的不同封装，对比损失的负样本大量是"同一个模型"。
- **检索评测**：任务分布塌在 text-generation 上，跨任务检索能力无法测量。
- **冷启动分层**：`layer` 与 `source_type` 高度共线，C 轴的归因说不清。

## §2 v2 设计：发现与选样分离

```
多源候选发现 (hf_crawl --plan)         ← 允许有偏，目标是覆盖
        ↓  537,025 条唯一候选
标注 (annotate_candidates)             ← 权威元数据优先，每个标签带来源
        ↓  supertask / language / family / source_type / quality / dup-key
配额选样 (select_balanced_halo)        ← 不允许有偏，硬配额 + 硬上限
        ↓  69,817 条
出闸门 (verify_raw --selected)         ← G1-G20，全部按实际总体计算
        ↓
分布报告 (report_distribution)         ← v1 / 池 / 选出 三方对照
```

**一句话原则：发现阶段可以有偏，选样阶段不可以。** v1 的错误就是把这两件事合成了一步。

### 2.1 新增/重写的代码

| 文件 | 角色 |

### 2.2 复用而非重造

`arch_family` 直接调用既有的 `dataset_embed.utils.fetch_metadata._infer_one_family` ——
就是产出 CORE `family_id` 的那套规则，所以 CORE 与 HALO 的架构家族可比。
它与本档新增的血缘 `family_id`/`canonical_root_id` 是**两个不同的问题**（「这是什么架构」vs「这是谁的派生」），
两个字段都保留，不互相覆盖。

## §4 标注阶段（Step 3–5, 10–12）

### 4.1 权威优先，启发式必须自报家门

每个 `*_of()` 返回 `(值, 来源, 置信度)`。实测来源分布（537,025 条）：

| 维度 | 来源分布 |
|---|---|
| supertask | `pipeline_tag` 76.2% / `config.model_type` 5.4% / `tags` 2.9% / `library_name` 0.9% / **无信号 14.5%** |
| 语种 | `cardData.language` 42.3% / `tags` 0.9% / `supertask_neutral`（真·语种无关）19.5% / **无 37.4%** |
| 家族 | `baseModels` 38.7% / `arch+stem` 5.4% / `author+stem` 3.3% / `declared_descendant` 2.8% / `cardData.base_model` 0.6% / **未解析 49.3%** |

**仓库名正则从不被允许覆盖权威元数据**：`size_b` 的 `safetensors` 与名字正则是**两个字段**，
名字来源的值标记为 `name_heuristic`，D-26 规定建图侧只用 `safetensors`。

### 4.2 家族构造（Step 4 的六级优先序）

1. `baseModels.relation`（权威） 2. `cardData.base_model` 3. 已知量化/适配器关系
4. `model_type` + 归一化仓库名干 5. `author` + 干 6. 未解析单例

**家族 = 血缘闭包的连通分量**，`canonical_root` 是分量里唯一确定的一个成员（无父者中字典序最小；全环则成员中最小）。
> **F-T2-16：作者真的会声明环。** 逐节点各自沿链上溯会让同一分量的成员走到**不同**的"根"，家族当场分裂。
> 单测 `test_cyclic_base_model_declaration_terminates` 钉住这条。

**通用词干绝不合并**：`model`/`chat`/`base`/`lora` 等 26 个词干与长度 < 4 的干一律不参与第 4/5 级判据。

### 4.3 搬运方评分（Step 9，通用而非点名）

由聚合量算出：仓库数、量化占比、上游作者数、原创占比、词干重复率。
单测 `test_mirror_score_is_generic_not_a_username_list` **断言源码里不出现任何具体用户名**。
537K 池中识别出的搬运方占 14.94%，选出后降到 **2.61%**。

## §5 选样阶段（Step 6, 8, 11, 13）

### 5.1 🔴 分母修正（v1.1，本档最重要的一次返工）

**错误做法（初版）**：选样过程中判 `text_generation_count <= 0.15 × requested_target`。
**为什么错**：`--target` 写大就能买到更宽的绝对上限；而如果这一轮又没跑满 target，
按**实际产出**算的份额就已经越界了。约束不稳定、可被参数操纵。

**修正**：所有百分比上限都是**最终选出总体**的份额。做法是把上限按工作规模 `N` 参数化，
再**二分搜索满足 `achieved(N) ≥ N` 的最大 `N`**：

- `achieved(N)` 随 N 单调不减（N 越大绝对上限越松），`achieved(N) − N` 随 N 递减
  ⇒ `achieved(N) ≥ N` 在 N 上单调，二分给出**精确**的可行最大值。
- 在该不动点上，每个上限**按构造**就是实际产出的正确份额；
- 出闸门再用**真实计数**独立复核一遍，不信任搜索结果。

单测 `test_caps_hold_as_shares_of_the_actual_population_not_the_request`
用同一个池分别请求 400 和 4000，断言两者都满足 1.5% 的**自身**份额。

### 5.2 语种规则的分母（Step 7）

「英语侧 ≥ 75%」是关于**语种构成**的断言，分母因此是**可归属语种的总体**（除 `language-neutral` 外的全部）。

> **F-T2-17：把 ViT 计入英语份额会让规则与任务均衡直接冲突。**
> 语种无关的 5 个 supertask（图像分类/检测分割/图像生成/音频分类/表格时序RL）在任务配额下合计就要 >25%，
> 与「非英语侧 ≤25%」互斥。实测：按全体作分母时，均衡 HALO 卡在 **~60,200** 上不去；
> 改用可归属分母后，**69,817 一次探测即可行**。

英语floor 与 unknown 上限都实现为**每一步都成立的运行不变式**（动态分母），不是事后检查。

### 5.3 官方量化 vs 第三方搬运（Step 10）

`Qwen/Qwen3-8B-GGUF`（第一方发布）与 `somebody/Qwen3-8B-i1-GGUF`（第三方重打包）不是同一类总体。
判据是结构性的：**量化仓库的作者是否等于其 base model 的作者**。

- `official-quantized`：池中 6,438 条（1.20%），选出 2.59%
- `quantized-conversion`（第三方）：15% 硬上限，选出 **14.999%**
- 两者合计另设 20% 硬上限，选出 **17.585%** —— 拆分不能被用来偷偷抬高总量

### 5.4 text-generation：15% 目标 / 18% 硬顶

`max_share` 是配额分配用的**目标**，`hard_ceiling` 是任何阶段都不可越过的**硬顶**，G8 按实际总体检查。
实测选出 **18.000%**（顶到硬顶），任务配额偏差最坏 3.39%。

### 5.5 算法

配额感知加权轮转，五轴同时跟踪（task / language / family_size / source_type / popularity）：
每步取跨轴缺口比最大的桶 → 沿该桶的分数序前进直到某候选满足**全部**上限 → 录取。
桶取不出候选就关闭并重分配。第二阶段放松**轴目标**至硬顶，
**但作者/搬运方/家族/近重复/top-10 五类上限从不放松**。
本次：严格阶段 42,808 + 放松阶段 27,009 = 69,817。

确定性：`sha1(model_id|seed)` 打破平局，无任何依赖 set/dict 迭代序的地方。**G19 复跑逐条 id 相同。**

### 5.6 🔴 CORE 必须先从候选池里剔除

> **F-T2-23（差点造出一个 98,108 的湖）**：候选池按任务/语种发现，自然会捞到 CORE 的成员 ——
> 池里有 **7,372** 条 CORE 模型。第一次选样没有排除它们，**69,817 条里有 1,892 条已经在 CORE 中**，
> 于是 `CORE ∪ HALO` 只有 **98,108** 个 distinct 模型，而 R2 的定义是 100,000。
> 20 条闸门**一条都不会报警** —— G1 只查 HALO 内部重复。
>
> 修法：`--exclude-core <hgraph_ml_v2.pt>`，在质量门之前把 CORE 成员从池中剔除。
> 剔除后 `CORE ∩ HALO = 0`，`|CORE ∪ HALO| = 100,000`（已实测断言）。
> **这条现在写进 §6.5 的验收清单，也写进 `100kplan §6.2` 的 `build_ladder` 断言。**

## §7 v2 过程中抓到的错误（留痕）

### 🔴 F-T2-18：`param_scale_bucket(NaN)` 落进 `>=90B`

`size_b` 缺失经 pandas 后是 `float('nan')`，而 `nan < 0.1` 等一切比较**全为假**，
于是穿过所有分支落到最后一档 `>=90B`。**实测后果：16,267 个互不相关的模型被并进同一个近重复组。**

### 🔴 F-T2-19：`canonical_root or stem` 里 NaN 是真值

缺失的根经 pandas 后是 `nan`，`nan or stem` 返回 `nan`，`str(nan)` = `"nan"`
⇒ **所有单例塌到同一个字符串根上**。

两条合起来把近重复容量从**应有的 288,432 压到 71,322**，直接让 69,817 的目标"看起来"不可达。
修复后一次探测即可行。单测 `test_missing_size_is_unknown_not_the_top_bucket`、
`test_missing_root_falls_back_to_stem_not_the_string_nan` 钉住。

### 🟠 F-T2-20：精确去重键对未量化模型也生效，白白砍掉 3→2

`near_duplicate_key_exact = key + "|" + bits`，未量化模型 `bits` 为 NaN → `"na"`，
于是它们的上限被静默从 3 降到 2。Step 5 说的是"同 base + 同量化方法 + 同位宽 ≤ 1–2"，**只针对量化**。
修复后未量化模型的精确键含自身 id（该上限对其不生效）。**实测多出约 8,000 的可用容量。**

### 🔴 F-T2-21：上限用 requested target 当分母（本档最重要的返工）

见 §5.1。初版把 `≤ 0.15 × target` 写进选样过程，导致：
① 把 target 写大就能买到更宽的限制；② 跑不满 target 时按实际产出算已经越界。
初版还配了一个"目标自适应下调"循环，它会**向下螺旋**（69,817 → 64,588 → 62,122 → 60,847 → 60,202），
把一个本可行的问题误判为不可行。改为二分搜索可行最大值后消失。

### 🟠 F-T2-22：`library=` 参数被 HF 静默忽略

`library=timm` 返回的是全局下载榜首（MiniLM/bert），不是 timm 模型。必须用 `filter=timm`。
**不报错、不为空**，只是悄悄不过滤。

### 🟠 F-T2-13：v1 的字段裁剪把 `cardData.language` 丢了

v1 的 `KEEP_CARD` 只留 `base_model`/`datasets`/`model-index`，
**v1 的 15 万条里 `cardData.language` 数量为 0**，语种只能从 tags 里的裸语种码猜。
而裸 `^[a-z]{2,3}$` 正则会误收 `trl`/`sft`/`tf`/`jax`/`mms`/`mtp`。
v2 补上 `language` 字段，并改用 ISO-639 白名单。
> **因此 §6.3 里 v1 的 40.88% unknown 语种，部分是 v1 爬取的字段缺失，不全是总体性质。这一条必须一起说。**

## §8 已知局限与未被元数据支持的结论

1. **家族未解析率 49.05% 未改善。** HF 上只有 38.7% 的候选有 `baseModels`。选出总体里近半数模型
   没有可解析的血缘父节点 —— 这些是 `unresolved_singleton`，**已显式标记**（G17），但它们对
   T5 的 `is_base_of` 边与 T8 的 C 轴 `cold` 层没有贡献。
2. **`english-primary` 39.55% 低于指令的 55–60% 目标。** 原因是元数据而非选样：
   池的可归属语种构成是 english 25.95% / multi 13.18% / non-english 12.52% / **unknown 48.35%** ——
   大多数英语模型根本不声明 `language: en`。硬性 75% 英语侧底线已满足，但"英语为主 55–60%"
   在不使用仓库名猜测的前提下**不可达**。已在 `halo_quotas.json` 里把目标下调到实测可达值并附定量说明。
3. **`official-derivative` 4.89%，低于 20% 目标。** 池中供给只有 10,015 条（1.87%）——
   它要求 `relation=finetune` **且**与 base 同作者，而大多数同作者派生根本不声明 base_model。
   这是 Step 10 明说的「元数据无法可靠区分时报告不确定性，而不是编造分类」。
4. **v1 与 v2 的"before/after"不是纯粹的总体对比。** v2 多了 6 个字段，任务/语种/来源的判定能力更强。
   已量化：`config.model_type` 在 v2 中只解决了 5.4% 的任务判定，所以任务分布的改善**主要来自总体**；
   但语种的改善**有相当部分来自字段补全**（见 F-T2-13）。
5. **`popularity` 的 `long-tail` 只有 11.13%（目标 25%）。** 长尾模型元数据差，被质量门与配额联合挤出。
   这是设计内的取舍（Step 12 要求 ≥95% 通过质量门），但要写明：**这个湖不是 HF 的均匀样本，
   它是"元数据可用"那一层的均衡样本**。
6. **快照不可复现。** `2026-08-03 (UTC)`。R3/R4 续爬时游标建在可变的 `downloads` 上，前缀嵌套只是近似（F-T2-9）。
