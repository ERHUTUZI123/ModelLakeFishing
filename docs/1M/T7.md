## 1. 为什么是两次前向，而不是一次

| 产物 | 怎么算的 | 干什么用 |
|---|---|---|
| `z_m.npy` / `z_d.npy` | **全图**前向 | 建 HNSW、上线服务。服务时每条边都合法存在 |
| `z_m_eval.npy` / `z_d_eval.npy` | **test-split** 前向 | 🔴 **只有这一份能用来报 `gold@K`** |

held-out 前向里，被查询的那个数据集**看不到自己的 `trained_on` 边**。
这不是洁癖：P4 用全图 `z_d` 打过分，每个 held-out 查询都看见了自己的监督边，
`gold@10` 从 0.42 虚高到 **0.61**。

所以 §10 的 **G-D2 是一个不等式**而不是一句提醒：

```python
assert gold10(z_eval) < gold10(z_full)
```

它断言「无泄漏的那个数应该更小」。两份嵌入一旦被用反，这条会**响**，而不是安静地给出一个更好看的数字。

## 2. 绑定检查：T7 的第一道闸，也是最便宜的一道

checkpoint 里记着它训练时那张图的 sha256。**导出时图对不上就直接停**，在花任何算力之前。

这条不是假想出来的。100K 图在 2026-08-14 为了带上血缘关系类型被重建过
（[`T6more.md`](T6more.md) §1.8 / D-44），`hgraph_100k.pt` 这个**路径上的文件已经换了**：

```text
7fbc3c47ca66227c…   2026-08-11 训练用的那张（现已归档为 hgraph_100k_norel_7fbc3c47.pt）
16f3521482a8efd6…   现行，带 relation_id
```

⇒ **8-11 那批 100K checkpoint 不能拿去对着今天这个路径导出。** 负例实测（本地）：

```text
IncompatibleCheckpoint: checkpoint was trained on graph 00ac2434… but
stage1BuildTransferGraph/hgraph_ml_v2.pt hashes to e6ae2dfe…
Exporting across a rebuild silently mislabels every embedding; …
```

`split_seed` 同理，从 **binding 里读**，不从命令行默认值推——
checkpoint 自己知道它是从哪个划分里 held out 出来的，
用 CLI 默认值重新推一遍，正是「导出时悄悄在训练边上评测」的经典路径。

## 3. 六道门

- **G-D3 的探针是随机位置 + 全表复核**，不是查表头。只查前几行的话，一个越界一位的前缀 bug 能安然通过。

## 5. 🔴 两条科学门的判定：一条失败，一条被违反

T7 自己的六道门 7 个 run 全过（§6）。**但 T7 的产出正是 G-C2 和 G-D5 的输入，这两条现在有判定了。**

### 5.1 🔴 G-C2 锚点没复现 —— 而且不是划分噪声

| | gold@10 | split_seed | 查询数 |
|---|---:|---:|---:|
| P3 存档（`P3_EXECUTION.md`，改造前） | **0.4159** | 0 | 517 |
| 本次 `R2_12k_s0_e25` | **0.3868** | 0 | 517 |
| 差 | **−0.0291（−7.0%）** | | |

**关键在于：split_seed 相同、查询数相同（517）、gold 候选集相同。**
所以这 −0.029 **不可能**是划分噪声——那是我们唯一测出来的噪声源（§4 三个 seed 的 sd=0.0206）。
而且 0.4159 **落在三个 seed 的观测区间 [0.3488, 0.3868] 之外**。

**⇒ G-C2 判为不通过。** 按 [`T6GPU.md`](T6GPU.md) §8 问题 2 预先写死的处置：
「**明显偏低 ⇒ 逐个关 T0 开关重跑定位（`--fanout` / `--sparse-M` / `--contrast-n-neg`），不改配置去凑**」。

**为什么会这样，有一个先前就存在的线索**：[`T0.md`](T0.md) 的 **§4「T0.3 出闸门」和 §5「终裁与回填」至今是「_(填充中)_」**。
也就是说 `100kplan.md` §3 T0.3 要求的两件事——

- 🔴 锚点门：12K 上 3 seeds，`gold@10` 与改造前基线 bootstrap CI 重叠（= **G-A1**）
- D-14 的 A/B 对拍表（全 N² 对比损失 vs `n_neg=256` vs `n_neg=1024`，各 3 seeds，= **G-A4**）

——**从来没有被执行过**，而同一节写着「**T0 不过，不许碰 watGPU**」。
**本次 T7 的 12K 三个 seed，实际上是 G-A1 的第一次执行，而它失败了。**

差异的候选来源（按嫌疑排序，**未验证，不要当结论**）：

1. **T0 的四个开关**——P3 那 0.4159 是在开关全关的情况下测的；本次全开。
   D-14 早就把「采样负例」标为「**改动冠军配置**」并强制要求 A/B，正是防这一手。
2. **采样后端换了**——P3 那台机器没有 `pyg-lib`，走的是纯 Python `LightLinkLoader`（全邻域）；
   本次装上了 `pyg-lib 0.8.0`，走 PyG 的 `LinkNeighborLoader` + 扇出。**这是换了采样器，不只是换了参数。**
3. 环境（torch 2.12+cu130 / H200）与 run-to-run 非确定性——已知存在（[`T6more.md`](T6more.md) §3.4⑦ 实测首个 epoch loss 抖动 0.26），但没有 `gold@10` 口径的噪声带。

**建议的定位实验**（便宜：12K 训练约 93 秒，导出在 CPU 上约 20 秒）：

| # | 配置 | 回答什么 |
|---|---|---|
| A | 四个开关**全关**，seed 0/1/2 | 是不是 T0 改造造成的 |
| B | 只开 `--contrast-n-neg 256`，seed 0/1/2 | D-14 那一项单独的代价（补上欠的 A/B 表） |
| C | 只开 `--fanout`，seed 0/1/2 | 采样器/扇出的代价 |

**我没有擅自开跑**——这是 T0 的返工，属于新的一轮实验设计，需要你点头。
D-14 已经预先规定了结论走向：「**若采样版显著更差：改用 B 方案（分块 logsumexp，数学等价、只省显存），
或把子图上限压得更小。不许默默接受退化。**」

### 5.2 🟠 G-D5 单调性被违反（幅度很小，但口径干净）

§12 的 G-D5 要求 `gold@10(100K) ≤ gold@10(30K) ≤ gold@10(12K)`：

| N | gold@10 | 查询数 |
|---:|---:|---:|
| 12,000 | 0.3868 | 517 |
| 30,183 | 0.2030 | 734 |
| 100,000 | **0.2071** | 734 |

**100K 比 30K 高 +0.0041。** 这一对**可以直接比**——它们的 held-out 查询集都是 **734 个，同一批**
（12K 的 517 是另一批，不能直接相减）。

G-D5 的原话是「🔴 **上升 = 泄漏或采样偏置，不许当好消息报**」。照办：**记为违反，不作正面叙述。**
两点缓和事实一并写清，但不用来开脱：

- 幅度 0.0041，**远小于**同一档三个 seed 的散布（100K 三 seed 0.172–0.265，跨度 0.093）⇒ 很可能在噪声内；
- 泄漏门 G-D2 在这两个 run 上都通过（100K s0：held-out 0.2071 vs 全图 0.3134，间距 0.106），
  铁律 3 的 G-D1 也过（候选池确为 100,000），G-D3 行序在 100K 上真查并通过。

⇒ **不是「已排除泄漏」，而是「T7 能查的两个泄漏面都干净」。** 真正的裁决要等 T8 把三档放在**同一查询口径**下重算。

### 7.1 🔑 GPU 作业排不进去 ⇒ 改成 CPU 作业，3 分半跑完

第一次提交（`1511025`）申请了 GPU，**排了 4 个多小时一次没跑上**，最后 reason 变成
`ReqNodeNotAvail, May be reserved for other job`，预约起跑被推到**次日 02:47**。

原因不是节点 pin。这个集群按组划分 GRES，我们能碰的只有两类，**当时全都进不去**：

| GRES | 节点 | 状态 |
|---|---|---|
| `a2laytongpu` | watgpu708 / 808 | GPU 全满，808 后来还被别的作业预留 |
| `schoolgpu` | watgpu308 | 8 张空 4 张，但 **32 个 CPU 全被占**，`--cpus-per-task=8` 进不去 |

**⇒ 放开 pin 也没用。改掉的应该是 `--gres`，不是 `--nodelist`。**

导出这件事本来就不需要 GPU：它是**一次前向 + 建索引**，而且冠军配置 `num_layers=1`，
分块闭包只有 1 跳、很便宜；而这些节点的 **CPU 几乎是闲的**（watgpu808 288 核只占了 28）。
于是取消 GPU 作业，改提 `--cpus-per-task=16 --mem=160G`、**不要 GPU、不 pin 节点**：

```text
提交后 45 秒内就在 watgpu108 上跑起来，全部七个 run 用时 3 分 29 秒（COMPLETED 0:0）。
```

**数字与 GPU 版完全等价**——同一份 checkpoint、同一条确定性前向路径；
唯一受影响的是 HNSW 延迟的绝对值（换了 CPU），而那本来就不是 B 轴的正式数字（见 §9）。

> **教训值得记进 runbook**：作业排不动时，先问「这一步真的需要 GPU 吗」，
> 再去动 pin 或等预约。这次的答案是不需要，代价从「等 8 小时」变成「3 分半」。
