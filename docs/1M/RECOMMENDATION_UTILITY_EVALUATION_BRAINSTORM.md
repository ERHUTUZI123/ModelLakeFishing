# 模型推荐“好不好用”的低资源评估思路

## 1. 问题重定义

当前 `gold@10` 回答的是：

> 对一个 dataset–task query，历史 record 中分数最高的模型是否出现在推荐前十名？

它不是“推荐精度”的完整定义。一个没有该数据集 record 的模型会被计为 miss，但这个模型可能尚未被评测，也可能实际优于历史 gold。当前标签空间应按三种状态理解：

1. **已知较好**：在该 query 上存在 record，并达到 gold 或可接受区间；
2. **已知较差或不适用**：存在可比较 record，或违反明确的任务、模态、许可和资源约束；
3. **未知**：在该 query 上没有 record，现有数据无法判断其实际性能。

因此，`gold@10` 是“历史最优记录的召回率”，可以作为一个有意义的下界指标，但不能把 `1 - gold@10` 解释为错误率。

## 2. 现有证据已经说明了什么

F8 三个 split seed 的平均 `gold@10` 为 **0.0598**。对 top-10 返回结果的事后构成审计显示：

| Top-10 槽位构成 | seed 0 | seed 1 | seed 2 |
|---|---:|---:|---:|
| 该 query 的历史 best | 1.98% | 1.32% | 1.84% |
| 在该 query 上有 record，但低于 best | 2.78% | 4.67% | 2.34% |
| 在该 query 上无 record，但在其他 query 上有 record | 92.20% | 90.73% | 95.17% |
| 全湖任何 query 上都无 record | 3.05% | 3.28% | 0.65% |

这意味着 F8 计为 miss 的结果中，大部分属于“未知”，不是已经证明的错误。只有约 3.3% 的推荐槽位能根据现有同-query record 明确判断为低于历史 best；即便如此，“低于 best”也不必然表示实际不可用。

现有数据还提供了一个不需要运行模型的相关性控制。对每个 query，检查推荐模型是否在其他地方拥有同任务 record：

| 候选来源 | 同任务 record 占比 |
|---|---:|
| 我们的 top-10 | **17.2%–22.4%** |
| 全湖均匀随机 | 0.032%–0.052% |
| 仅从有评测记录的模型中随机 | 1.95%–3.36% |

我们的 top-10 在这一代理指标上约为全湖随机的 **500 倍**，也是“有记录模型随机基线”的 **7–9 倍**。该结果说明推荐并非随机噪声，而且与 query 的任务语义有关。它仍不能证明无 record 模型在目标数据集上的实际性能。

相关资源核算见 [`RESOURCE_E_AXIS_DENSE_REEVALUATION.md`](RESOURCE_E_AXIS_DENSE_REEVALUATION.md)。全量补评约需要 73.5 TB 传输和 5,300 GPU-hours，不适合作为当前评估方案。

## 3. 建议把评估拆成四层

### 3.1 第一层：历史记录恢复

保留现有指标，但给它准确命名：

- `recorded_gold@10`：历史 best 是否进入前十；
- `recorded_top3@10`：历史前三是否至少有一个进入前十；
- `median_recorded_gold_rank / N`：历史 best 在全湖中的归一化排名；
- `record_coverage@10`：前十中有多少模型在当前 query 上有 record；
- `unknown_on_query@10`：前十中有多少模型在当前 query 上没有 record。

这一层衡量“对已知证据的恢复能力”，不对未知候选作负面判断。报告中应将 `recorded_gold@10` 与 `unknown_on_query@10` 并列，避免读者把未知槽位自动理解为错误。

### 3.2 第二层：无需运行模型的可用性门

“推荐拿过去能不能用”首先包含一些可从元数据判断的硬条件。可以对 top-10 逐项检查：

- 任务和模态是否匹配；
- 模型仓库当前是否存在且可访问；
- license 是否允许目标使用场景；
- framework、输入输出接口和推理类型是否兼容；
- 参数规模、量化形式和上下文长度是否满足给定资源约束；
- 是否有足够的 model card、配置或使用说明；
- 是否为同一 parent、同一量化版本或同一发布流水线的大量重复结果。

由此可以定义：

| 指标 | 含义 |
|---|---|
| `hard_constraint_pass@k` | 前 k 个结果中满足全部明确硬约束的比例 |
| `at_least_one_feasible@k` | 每个 query 的前 k 中是否至少存在一个可直接尝试的模型 |
| `available@k` | 仓库仍可获取且非 disabled/private 的比例 |
| `documented@k` | 具有最低限度配置和使用说明的比例 |
| `family_diversity@k` | 前 k 中不同 family 或 lineage root 的数量 |
| `duplicate_variant_rate@k` | 被同一 parent 或近重复发布占据的槽位比例 |

这些指标不能替代真实性能，但它们直接覆盖用户是否能够下载、加载、理解和部署推荐结果。

### 3.3 第三层：小规模盲审的决策效用

无需运行模型，可以用有限人工审查判断“推荐列表是否值得拿去试”。建议从三个 split seed 去重后的 query 中做分层抽样，覆盖：

- 不同 task family；
- query 深度 `3–4`、`5–9`、`≥10`；
- 有 card 与 name-only query；
- warm/cool/cold/frozen 推荐构成；
- 有历史 gold 与大量未知候选的情况。

每个 query 只展示必要的 dataset 描述、使用约束以及候选模型的 model card 摘要。隐藏候选来源和排序方法，让审查者比较：

1. 我们的 top-5；
2. 元数据文本检索基线；
3. popularity/download 基线；
4. 同任务有 record 的随机基线。

审查者不判断“谁在数据集上分数最高”，只回答更低成本且可审计的问题：

- 是否明显匹配任务和模态；
- 是否存在明确不可用的结果；
- 如果只能选择一个模型先试，会选哪个列表中的候选；
- 推荐是否提供了有意义的备选方案，而非十个近重复模型；
- 列表是否包含足够信息支持下一步决策。

建议输出以下指标：

- `human_acceptable@5`：被判定为值得尝试的候选比例；
- `at_least_one_acceptable@5`：前五中至少一个候选值得尝试的 query 比例；
- `pairwise_preference_win_rate`：我们的列表相对各基线的盲选胜率；
- `clear_failure@5`：任务、模态、许可或接口明显不符的比例；
- 审查者一致率及分歧区间。

人工评估应冻结 query 抽样、展示字段和 rubric，再开始打分。它评估的是决策支持价值，不应被表述为 benchmark 性能验证。

### 3.4 第四层：低成本的时间后验验证

可以利用未来自然出现的 record，而不主动运行全量模型：

1. 在时间 `t0` 冻结 query、top-k 排名和候选信息；
2. 定期只抓取新增或更新的 `model-index`；
3. 找出 `t0` 时未知、在 `t1` 获得同-query record 的推荐模型；
4. 比较这些新披露模型与 `t0` 历史 gold 的相对位置；
5. 同时对当时未被推荐的同任务模型建立对照。

这相当于一个 prospective shadow evaluation。它不需要下载或运行模型，并且新 record 在排名生成时尚不可见，能减少训练标签复用问题。限制是作者自报偏差、record 更新慢，以及只有一部分 query 会获得后验标签。

## 4. 用区间表达未知，而不是强行给单一精度

在标签不完整时，可以报告可识别区间：

- **保守下界**：只有历史 gold 或人工明确接受的结果算有效；
- **已知失败率**：只有违反硬约束或有直接反证的结果算失败；
- **未知比例**：没有足够证据判断的结果单列；
- **人工估计值**：从分层盲审样本估计未知结果中的可接受比例，并报告置信区间。

例如，若一个 top-10 列表含 1 个历史 gold、1 个已知不适用模型和 8 个未知模型，现有证据不是“精度 10%”，而是：

- 已确认可接受率下界：10%；
- 已确认失败率：10%；
- 未知：80%。

对未知部分做分层人工审查后，才可以估计整体 utility，而不是将未知全部归入错误或正确。

## 5. 一个可作为主表的 Utility Scorecard

主表可以同时放置以下五类证据：

| 维度 | 建议主指标 | 回答的问题 |
|---|---|---|
| 已知效果恢复 | `recorded_gold@10`、`recorded_top3@10` | 是否找回历史上已知较强的模型？ |
| 任务相关性 | `same_task_evidence@10` 及相对随机倍数 | 推荐是否与 query 的任务生态相关？ |
| 基本可用性 | `hard_constraint_pass@5`、`at_least_one_feasible@5` | 推荐能否被用户实际获取和尝试？ |
| 决策效用 | `human_acceptable@5`、盲选胜率 | 人在有限信息下是否愿意优先尝试这些结果？ |
| 覆盖与风险 | unknown、availability、重复率、family diversity | 结果的不确定性和失败模式是什么？ |

`gold@10` 不再单独承担“系统好不好”的结论。它与可用性、人工偏好和未知比例共同构成推荐效用证据。

## 6. 当前最可行的最小版本

在不下载和运行新模型的前提下，第一版可以只做三件事：

1. **整理现有零成本指标。** 从已有 F7/F8 产物报告 `recorded_gold@10`、top-10 四类构成、`same_task_evidence@10`、availability 和 family/lineage 重复率。
2. **建立小规模盲审。** 冻结一个分层 query 样本，对我们的 top-5 与三个廉价基线做元数据级人工比较；记录“至少一个值得尝试”、明显错误和列表偏好。
3. **冻结时间后验列表。** 保存当前未知推荐，后续只消费自然新增的 `model-index`，逐步积累独立于当前训练标签的验证证据。

该方案不能证明未知模型的真实性能，但可以回答一个更现实的问题：

> 在不承担全量重新评测成本的条件下，系统是否比简单基线更稳定地给出相关、可获取、约束匹配、值得优先尝试且具有合理多样性的候选列表？

## 7. 应避免的表述

- 不将 `gold@10 = 7%` 写成“推荐正确率只有 7%”。
- 不将无同-query record 的模型自动判为错误。
- 不因为模型在其他任务上有 record 就声称其在当前 query 上表现良好。
- 不把 model-card 人工判断写成实际 benchmark 性能。
- 不用 popularity、下载量或有无 record 作为质量真值；它们只能作为基线或证据特征。
- 不提出全湖补 benchmark 作为当前工作的必要条件。
- 不给未知候选填入人为伪分数后再计算一个看似精确的单一指标。

## 8. 面向导师的简短表述

> 当前 `gold@10` 衡量的是历史记录覆盖，不等于推荐正确率。我们的 top-10 中约 93% 在目标数据集上没有 record，因此大部分 miss 的真实质量未知；与此同时，推荐结果具有同任务评测证据的比例比全湖随机高约 500 倍，说明系统已经学到明显的任务相关性。由于全量补评需要几十 TB 数据传输和数千 GPU-hours，更现实的评估方式是把历史 gold 恢复、硬约束满足、列表多样性、小规模盲审偏好和未来自然新增 record 组合成一张 utility scorecard。它不能把未知变成真值，但能够回答推荐列表是否比廉价基线更值得用户优先尝试。
