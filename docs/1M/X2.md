## 1. 结论

**P2b 的 task 先验在 3M 上是真的，而且量级与 X1 的预测一致：`gold@10` 从 0.0598 到 0.3009，5.0 倍。**
三个 split seed、全部 3,016,439 个模型的候选池、α=β=1（v6 采纳的权重）、零训练零重建索引。

| 排序（全湖，α=β=1） | seed 0 | seed 1 | seed 2 | 均值 | 相对基线 |
|---|---:|---:|---:|---:|---:|
| 纯 MIPS（本轴的对照） | 0.0700 | 0.0399 | 0.0696 | **0.0598** | 1.00× |
| ＋「单组」先验（v6 原样移植的实际效果，见 §3） | 0.1232 | 0.1127 | 0.0940 | 0.1100 | 1.84× |
| ＋task 先验 β=0.5 | 0.2914 | 0.3174 | 0.2464 | 0.2851 | 4.77× |
| **＋task 先验 β=1（v6 采纳值）** | **0.3132** | **0.3356** | **0.2539** | **0.3009** | **5.03×** |
| ＋task 先验 β=2 | 0.3087 | 0.3400 | 0.2558 | 0.3015 | 5.04× |
| β→∞ 端点（下界，§5） | 0.3338 | 0.3322 | 0.2301 | 0.2987 | 4.99× |

三件事值得单独拎出来。

**一、审计说的「约 30 行适配」不够，因为 v6 sidecar 读的那一列在这张图上恒为 0。**
`build_prior_sidecar.py` 的 task 分组来自 `data["dataset"].task_type_id`。
全量档的这一列是 `build_graph_rf.py:238` 写死的 `np.zeros(n_d)`，`meta.json` 里
`num_task_types: 1`、`task_type_vocab: {"Other": 0}`（100K 档是 196 个）。
**原样移植会把 18,729 个数据集节点全部塞进一个 task 组，先验退化成「谁在任何地方的记录都好」。**
那条退化先验就是表里第二行：`gold@10` = 0.1100，只有正确分组的 36%。
适配后的 task 分组改从 `dataset_nodes_merged.parquet` 的 `task` 列（归一后 2,198 组）来，
sidecar 的 `prior_sidecar_s*_meta.json` 里记了用的是哪一个源。

**二、这 5 倍里，「有记录」占 1.84 倍，「同哪个任务」占剩下的 2.7 倍。**
上面那条退化先验正好是审计 §6 那句警告的定量版本：
`gold@10` 奖励「有记录」，而不是任务语义。现在两者被分开量到了——
只知道「谁有记录」就能拿到 1.84×，再知道「记录在哪个任务上」才拿到 5.03×。
这与 X1 §7 测到的「纯元数据 `pipeline_tag` 过滤只有 0.023」不矛盾：
值钱的不是模型声明了什么任务，是它**在同任务的数据集上被评过**。

**三、α（sibling）项在这个协议下是死的，代码里断言了。**
X1 §9 已经测到 root-aware 下有训练可见兄弟的查询是 0；这里把它变成 P 轴的一条断言
（`n_sib == 0`，否则直接失败），所以报表里不写重复的 α 列。
S2 要有数字必须换协议，那是 §8 的顺序 3。

## 2. 做了什么

### 2.1 `build_prior_sidecar.py`：三处适配，D0 路径逐数组不变

| 适配 | 为什么 |
|---|---|
| `--graph-store` 走 `scale1m.graph_store.load_sharded`，id 表读 parquet | 全量档的图是目录不是单文件 `.pt`；`x_model.npy` 5.4 GB，mmap 而不是读进内存 |
| `--split-seed` 只保留 train+val 边 | D0 的 sidecar 建在整张图上，靠 `serving_rerank._prior` 的 `dd == d` 跳过来保证合法性。那对 sibling 先验够用（被排除的集合恰好是 {D}），对**在 held-out 划分上测 task 先验**不够：D 的同任务组里还有别的 test 数据集，整图 sidecar 会把它们的标签一起交出去 |
| `--task-nodes` 在图的 task id 退化时提供分组 | §1 的第一条 |

`--split-seed` 的边集取 `test_data` 的 message 图（按 `d0_splits` 的构造就是 train ∪ val），
并断言没有一条幸存边落在 test 侧的数据集上。三个 seed 分别是
198,216 / 196,912 / 196,124 条，与 [`X1.md`](X1.md) §7 的可见边数逐 seed 相同。

**回归**：用未加 `--split-seed` 的旧调用重建 `d0_L1L3b` 的 sidecar，
与 2026-07-20 那份 `prior_sidecar.npz` **五个数组逐一 `array_equal`**。
D0 的行为没有任何改变；顺带确认 D0 的 root 也来自 `unique_dataset_id.root`
（新代码优先用该列），与旧代码「按第一个 `/` 切」得到的 421 个 root 完全一致。

### 2.2 `eval_rf.py`：新增 P 轴

```
python -m ModelLakeFishing.stage3HNSW.build_prior_sidecar --graph-store <...>/hgraph_rf \
    --export <...>/RF_full_s0_e25 --split-seed 0 --task-nodes <...>/dataset_nodes_merged.parquet
python -m scale1m.eval_rf --axis p        # 53.5 s，三 seed
python -m scale1m.eval_rf --axis pinf     # 11.8 s，β→∞ 端点
```

两条设计决定：

**P 是独立的一轴，不是 A 轴里的一列。** A 轴的数字被 F8.md 与 1Mplan 的门禁表逐个引用；
融合改的是排序，不是嵌入也不是索引，所以它挨着 A 而不是进 A——
重排过的 `gold@10` 绝不能被当成检索数字。报告写进 `X2_PRIOR_FUSION.json`，
`F8_REPORT.json` 一个字节没动。

**排名在全湖上算，不在检索池里算。** `serving_rerank.py` 的 `POOL = 512` 会把上限钉在 `gold@512`
（X1 §6）。全湖计算把「先验有没有用」和「第一阶段要检索多深」这两个问题分开，
前者是本轴要答的，后者留给部署时定 `POOL`。
`minmax` 也按 `serving_rerank` 的口径在全湖上做，不是池内重标定。

## 5. β 扫描与它的端点

`gold@10` 对 β 的曲线是：0（纯 MIPS）0.0598 → 0.5 的 0.2851 → 1 的 0.3009 → 2 的 0.3015。
β=1 到 β=2 之间已经基本走平，单个 seed 上还会小幅上下（seed 0 是 0.3132 → 0.3087）。
只看这四个点无法判断 β=1 是峰还是途中的一站，所以另算了端点。

**β→∞ 是可以精确算的，不需要再扫一遍全湖。** β 一大，带先验的模型就与不带的整个分开
（收缩后的 boost 聚在中点 0.5 附近，而 `minmax(mips)` 的上界是 1），
融合序收敛到「先按先验、再拿 `minmax(mips)` 打破平局」。这个极限只由池内信息决定：

| | seed 0 | seed 1 | seed 2 |
|---|---:|---:|---:|
| `gold@10` 下界 | 0.3338 | 0.3322 | 0.2301 |
| `gold@10` 上界 | 0.3755 | 0.3886 | 0.6238 |
| gold 落在同任务池内的查询 | 1,004 | 803 | 687 |
| 落在池内时的中位名次 | 9 | 13 | 6 |

（下界只数「gold 在池内且池内名次 ≤ k」；上界再加上「gold 不在池内、但池比 k 还小」
那些无法只由池内信息判定的查询。seed 2 的上界很松，因为它的池普遍太小。）

下界均值 0.2987，与 β=2 的 0.3015 基本重合——**β 扫描在 β≈1 就已经到顶，v6 采纳的 α=β=1 在 3M 上仍然是对的**。

这条端点还说明另一件事，而且不太舒服：
**在采纳权重下，融合分数基本就是 task 先验，检索嵌入贡献的主要是打破平局。**
β→∞ 下界 0.2987、β=1 是 0.3009、X1 §1 的「只用先验排序」是 0.3014——三个数落在同一处。
也就是说这 5 倍是先验带来的，不是先验与嵌入的协同。
嵌入在另外那件事上仍然不可替代：30%–57% 的查询 gold 根本不在同任务池里
（X1 的天花板 0.4307–0.6964），先验对它们一分不给，能排的只有嵌入。

## 7. 实现上的两点

**P 轴比 X1 的测量六快两个数量级（53.5 s 对 4,981 s），差别只在一处写法。**
X1 每个模型块都物化 `sc[:, flat_q]`（`[C, P]` float32，约 154 MB）再比较；
P 轴保持 `[C, b]` 不动，用 `fused.unsqueeze(2) > T.unsqueeze(0)` 直接广播成 `[C, b, 3]` 的布尔，
因为每个查询每条排序其实只需要三个阈值（gold、top-3 里融合分最高的那个、near 里最高的那个），
名次的 `min` 等价于对融合分最大的那个探针取名次。显存流量从每块每变体 154 MB 降到 38 MB。
X1 的测量六如果要再跑，值得照这个改写。

**task 先验的稀疏性没有被利用，但可以。** boost 只在约 4 万个模型上非零，
所以 `#{m : fused(m) > F}` 可以拆成「全湖 `mips` 超过某个标量」减去「池内超过该标量」再加「池内融合分超过」，
只有第一项要扫全湖。本轴没走这条路（直接稠密散射更不容易写错），
但 §5 的 β→∞ 端点正是靠这个分解在 11.8 秒内算出来的。

## 8. 没做的，以及本轮改变了什么

顺序 3–5 一件没动：

| 顺序 | 事情 | 状态 |
|---|---|---|
| 3 | 预注册 node-level 第二协议，跑 S2 | 未开始。本轴把 α 项失效变成了断言，**S2 在 root-aware 下没有任何数字可报**，要数字必须换协议 |
| 4 | 混合提议分布 + `global_n_datasets=128`，三 seed 重训 | 未开始，需要 watGPU |
| 5 | 查询集加 `gold_eligible` 过滤 | 未开始（一小时） |

本轮结果对后面的影响：

- **审计 §5 的更正 1 现在必须做了。** [`F9.md`](F9.md) §6 写「两阶段服务的第二阶段（metric-aware reranker）……
  目前尚未实现」。它在 D0 上 2026-07-19 就实现了，现在在 3M 上也实测了。这句话要改，
  但改的是 F9 的执行记录，不在本次范围内，登记在这里。
- **顺序 3 的价值被本轮抬高了。** 融合的 5 倍全部来自 task 通道，而 sibling 通道在当前唯一报告的协议下
  连触发都不触发；X1 §9 又测到 66%–78% 的查询落在同根 ≥2 节点的根内。
  这是目前唯一一条「已知有信号、但被协议按定义清零」的通道。
- **要报这条通道，必须连 §4 一起报。** 尤其是参数量中位数 2.4 B → 7.6 B 这一行，
  它不在审计的预判里，是本轮新测到的代价。
