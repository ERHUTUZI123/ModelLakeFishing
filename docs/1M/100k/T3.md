### 2.1 `build_ladder` 为什么几乎全是断言

行序错位**在任何地方都不会抛异常**，只会悄悄改写"哪个模型拥有哪一行嵌入"。
CLAUDE.md 把它列为三大风险之首。所以这个文件在 concat **之前**先做四项检查：

```python
assert len(halo) == n - n_core                    # HALO 规模
assert not (core_id_set & set(halo.id_norm))      # 🔴 CORE∩HALO=0（D-35）
assert halo.id_norm.nunique() == len(halo)        # HALO 内部无重复
assert not (set(halo.id_norm) - set(canon.index)) # canon 覆盖全部 HALO
```
concat 之后再做四项：`len==n`、`mappedID==range(n)`、**CORE 前缀逐项相等**、全表 id 去重后仍是 n。

单测 `test_ladder_refuses_a_halo_that_overlaps_core` 专门钉住 D-35 那个
「G1–G20 全绿但湖仍然是错的」的漏洞。

## §4 结果与对账

### 4.1 `layer` 分布 —— 与 v1 口径的预测**大幅不同**（F-T3-2）

| layer | v1 前缀预测（作废） | **v2 实测** | 差 |
|---|---|---|---|
| `labeled`（有 model-index） | 1,642（2.35%） | **6,619（9.48%）** | **×4.0** |
| `lineage`（有 base，无 model-index） | 42,109（60.31%） | **25,268（36.19%）** | ×0.60 |
| `plain` | 26,066（37.33%） | **37,930（54.33%）** | ×1.46 |
| `dropped` | 0 | **0** | 恒空（D-27 在 v2 上再次确认） |

两个方向相反的力，正是 T2 回填计划时预告过的那一对：

- **`labeled` 涨 4 倍** —— 均衡选样的质量门偏好有结构化元数据的模型，`model-index` 覆盖率从
  池的 7.57% 升到选出的 9.48%。⇒ **T8 §11.1 的 `displacement_quality` 样本基数从 1,642 变成 6,619**，
  从"只能给定性结论"升级为"可以给带分母的定量结论"。
- **`lineage` 掉四成** —— 近重复上限（同一 `(root, task, scale, lang, format)` 至多 3 条）
  **主动削掉**同一根下的密集派生，而那些正是 `base_model` 声明最密集的一群。

> 🔴 **`plain` 过半（54.33%）是必须写进报告的一条**：v2 的 HALO 里超过一半的模型既无标注也无可解析血缘。
> 它们对 T5 的 `is_base_of` 边与 T8 的 `cold` 层零贡献，只能靠自身特征。

### 4.4 `family` —— 🔴 本档最重要的发现（F-T3-1）

**计划原文**：「复用 `attributes.py` 的既有 family 推断（名字前缀 + tags 兜底）」。
两处都不准确：
1. 真正的函数是 `dataset_embed/utils/fetch_metadata.py::_infer_one_family`，**只看名字，没有 tags 兜底**；
2. **更要命的是它和 CORE 不在同一个命名空间。**

CORE 的家族字符串来自 ModelLens 的 `model_profile.family`，实测长这样：
`bert`(6,909) / `llama`(1,492) / `vit`(1,308) / `xlm`(1,290) / `deit`(987) / `qwen`(925) —— **全是 HF `config.model_type` 的取值**。
而 `_infer_one_family` 返回的是规则表的取值：`BERT` / `LLaMA` / `ViT` / `Qwen`。
`family_vocab`（341 行）里**两套都在**：`KNOWN_FAMILIES` 被种子化在前（`LLaMA` = id 2），
ModelLens 的小写串在后面动态录入。

⇒ **HALO 的每一个 llama 会拿到 `LLaMA` 行，CORE 的每一个 llama 待在 `llama` 行。
同一个架构，两行嵌入，零共享，且没有任何地方会报错。**

实测覆盖率（"落进 CORE 真正用过的 207 个家族"）：

| 策略 | 落进 CORE-used |
|---|---|
| 计划原文：`_infer_one_family` 原样 | 🔴 **0.64%** |
| 仅小写化 | 33.98% |
| 仅 `config.model_type` | 29.63% |
| ✅ **四级解析（采用）** | **48.47%** |

**采用的四级解析**（`family_of`，每行记录 `family_source`）：

1. `config.model_type` 且 CORE 用过 → 用它（**权威 + 同命名空间**）
2. 否则 小写化 `_infer_one_family` 且 CORE 用过 → 用它
3. 否则 `config.model_type` 非空 → 用它（新行，但落在正确的命名空间里）
4. 否则 小写化的规则输出（最后手段）

全 537K 候选上的来源分布：
`name_rule|new` 187,138 / `name_rule|core_used` 147,409 / `config.model_type|core_used` 109,228 / `config.model_type|new` 93,250。

**HALO 侧的家族统计**：

| 量 | 值 | CORE 参照 |
|---|---|---|
| 不同家族数 | **9,292** | 207（被用到的） |
| `family == "other"`（规则层） | **0.23%** | — |
| **`family_id == 0` 预测**（过 `FAMILY_MIN_COUNT=3` 折叠后） | **12.78%** | CORE **34.16%** |
| 落进 CORE 用过的家族 | **48.47%** | — |
| 成员数 ≥ 3 的家族 | 1,663 个，覆盖 87.45% | — |

⇒ **远低于 §6.3 的 80% 警戒线，也低于 CORE 自己的 34.16%。** `e_fam` 不会塌成一行。
但**另一半（51.53%）的 HALO 会新建 vocab 行**，T4 的 `load_or_update_family_vocab` 是 append-only，
会把 `family_vocab` 从 341 行扩到 **约 2,000 行**（1,663 个 ≥3 的家族里有相当部分是新的）。
**这不违反铁律 1**（CORE 已有行的 id 绝不移位，T4 有断言），但 checkpoint 与 vocab 的绑定必须同步更新。

### 4.5 `lineage_base` 的来源 —— 计划写的字段会丢掉 95% 的信号（F-T3-4）

计划 §6.1 写的是 `cardData.base_model`。实测在 537K 候选上：

| 来源 | 命中 |
|---|---|
| `baseModels`（HF 结构化，带 `relation`） | **234,445** |
| `cardData.base_model`（作者手打字符串） | **12,713** |
| 无 | 289,867 |

**只用 `cardData.base_model` 会丢掉 94.9% 的血缘声明。** 实现按 T2 的既定纪律
（权威优先）改为 `baseModels` → `cardData.base_model`，并逐行记录 `lineage_source` 与 `lineage_relation`。
`relation` 顺带解决了 CLAUDE.md 里 `r_mm'` 的离散有序权重（quantized > adapter > finetune > merge）
在 T5 需要的那个量 —— **不必再从名字猜**。

### 4.6 冷启动分层预测（T8 §11.3）—— 后两档全变（F-T3-6）

| 层 | 定义 | v1 前缀预测（作废） | **v2 实测预测** |
|---|---|---|---|
| warm | `trained_on` 度 ≥ 10 | 5,765（5.76%） | **5,765（5.76%）** |
| cool | 度 1–9 | 24,369（24.37%） | **24,369（24.37%）** |
| cold | 度 = 0 **有血缘** | 26,297（26.30%） | **16,385（16.39%）** |

`warm`/`cool` 完全来自 CORE，是确定值不变。`cold`/`frozen` 随 §4.2 一起改写：

"`frozen` 层能否被检索到、是否塌缩"从一个次要问题变成**过半总体的问题**。
