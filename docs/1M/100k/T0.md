## §1 T0.1 基线（对照组）—— 含一次过程失败

### 1.1 原计划与它的失败

原计划按 `100kplan §3.1`：改造**之前**先把 seed 1/2 跑掉，进程在编辑任何 `.py` 之前就完成全部 import，以此隔离。
（本仓库**不是 git 仓库** —— `git status` 报 `not a git repository` —— 所以 `git worktree` 隔离不可用，进程级隔离是唯一手段。）

**这两个 run 在跑了约 1 小时后被会话 teardown 杀掉，没有写出任何产物。** 隔离窗口就此丢失。

### 1.2 补救：把"等价性"从假设变成实测

不假装隔离还在。改用一个**更强**的检验：

> P3 的 `ml_sub_L1L3b` 是一份**改造前、未被触碰**的存档（seed 0，gold@10 = 0.4159）。
> 用**改造后的代码 + 全部开关关闭**重跑 seed 0，如果复现它，"默认路径 = 历史路径"就是实测结论而不是论证。

这比原计划的隔离更有说服力：原计划只能保证对照组干净，这个做法直接检验了"改造没有污染默认路径"本身。

同时逐条核对了训练路径上**无条件**（不受开关保护）的改动，确认它们不改变 RNG 流与数值：

| 无条件改动 | 为什么不影响 |
|---|---|
| `high_performer_membership` 先收集 (row, col) 再一次性赋值 | topk 选出的位置完全相同，dense 分支仍是 `M[rows, cols] = 1.0` |
| `train.py` 把 `batch_contrastive_masks` 调用移到 rank 损失之后 | 该函数**不消耗 RNG**，全局 RNG 流顺序不变 |
| `_pos_ids` 统一列访问 | dense 分支返回的就是原表达式 `(M[:, d] > 0).nonzero().flatten()` |
| `mine_*` 的 `k` 计算改写 | L1L3b 的 `hard_mine_epoch=0`，这条路径根本不执行 |
| `global_positive_density` / `per_dataset_density` 分块 | 训练与评测**之后**才算；同 generator ⇒ 同抽样 |
| `five_metric_eval` rank 计数重写 | 已用 P3 存档逐位复现（§3⑤） |

## §3 逐项改造与实测

### ① 🔴 扇出上限 loader

**改哪**：[`stage2TrainGraphSAGE/sampling.py`](../../stage2TrainGraphSAGE/sampling.py)
`build_csr` / `_sample_neighbours`（新增）、`LightLinkLoader.__init__` / `_khop_closure_fanout`（新增）、`make_link_loader(fanout=...)`

**改法**：
1. **CSR 预建**：每个关系按 `src` 排序 + `ptr` 前缀和，邻居查找从 `torch.isin(src, tensor(sorted(cur)))` 的 **O(E) 全表扫描**变成一次切片 `nbr[ptr[v]:ptr[v+1]]`。正反两张（`_csr` src→dst / `_csc` dst→src），因为闭包本来就双向走。
2. **只扩 frontier，不扩 visited**：原实现每一跳都对**整个已访问集合**重新求邻域；新实现只扩当前跳新增的节点。
3. **每节点每关系方向 ≤ `fanout[hop]` 个邻居**，无放回抽样 ⇒ 子图大小是 `seeds × fanout × 关系方向数` 的函数，**与 N 无关**。
4. **血缘更大扇出**：`fanout_lineage` 默认 `2×fanout`（`(10,10)` ⇒ `(20,20)`），与 CLAUDE.md Step 4 给血缘更低丢弃率同源 —— 冷启动模型只有这一条边。

**实测（真实 12K 图，`batch_size=1024`，`num_hops=1`）**：

| | 无上限（历史） | `fanout=(10,10)` |
|---|---|---|
| 子图 model 节点 | **9,741 / 12,000（81%）** | 2,752 |
| 子图 dataset 节点 | 2,248 / 3,000 | 1,904 |
| `[B,B]` 掩码（bool，×2 张） | 90.5 MB | 7.2 MB |
| `[B,B]` 相似度（fp32） | 362 MB | 28.9 MB |
| 正样本对数 | 1,373,812 | 145,342 |

> **发现 F-2（关键）**：**一个 batch 就吃掉了 81% 的湖**。这不是"100K 才会有的问题"——
> 12K 上它已经发生，只是 12K 的 81% 还装得下。100K 上同样的比例就是 8 万节点的子图，
> `[B,B]` 单张 fp32 相似度矩阵 25.6 GB。**扇出上限不是优化，是 100K 能不能跑的前提。**

> **发现 F-3（偏离计划）**：`100kplan §3.2①` 把单测上界写成 `128×(1+2+4)`。
> 该式只在**单关系单方向**下成立；本图有 5 个关系、闭包双向走，每跳真实分支因子是 `R×k`（R=10）。
> `test_fanout_bounded` 用的是诚实上界 `seeds×(1+Rk+(Rk)²)`，并同时断言"远小于全闭包"。
> **计划里的那个式子应当修正**（已回填 `100kplan`）。

**单测**：`test_build_csr_matches_edge_index`、`test_fanout_bounded`、`test_fanout_preserves_supervision`（监督边完整且 `n_id` 反查回全局 id 逐项相等）、`test_fanout_lineage_gets_higher_cap`

### ② 🔴 稀疏 `M`

**改哪**：[`losses.py`](../../stage2TrainGraphSAGE/losses.py) 新增 `SparseMembership`；`high_performer_membership(sparse=)`、`topk_membership(sparse=)`、`pool_membership_by_root`、`global_positive_density`、`per_dataset_density`、`_pos_ids`（新增，统一 `M[:, d]` 的两种表示）

**改法**：`SparseMembership` 同时持有 **CSC**（dataset → 高性能模型，服务 `M[:, d]`）和 **CSR**（model → 它拔尖的 dataset，服务 `M[n_id]`），
对外暴露训练/评测路径实际用到的全部访问式（`M[:,d]` / `M[n_id]` / `M[cand,d]` / `M[m,d]` / `M.sum(0)` / `.to(device)`），
**调用点不需要分支判断表示**。`.to_dense()` 是等价性预言机。

`pool_membership_by_root` 的 python 逐 root 循环 → 一次 `scatter_reduce_(amax)` 进紧凑 `[N_m, N_root]` 再 gather 回来；稀疏输入则直接在 nnz 上展开，**全程不分配稠密块**。

`global_positive_density` 的采样分支原来一次性物化 `M[i]`（200,000 × N_dataset）——
**12K 上就是 2.4 GB，100K 上 7.7 GB**，正是 P3 两个 OOM 之一。改成 `pair_chunk` 分块，峰值与 `n_sample` 无关。

**实测（真实 12K 图，train-visible `M`）**：

| | dense | sparse |
|---|---|---|
| 形状 | (12000, 3000) | 同 |
| 内存 | **137.3 MB** | **0.42 MB**（327×） |
| nnz / 密度 | — | 19,771 / 5.49×10⁻⁴ |
| `to_dense()` 与 dense 逐元素相等 | — | ✅ |
| 构建耗时 | 1.2 s | 0.9 s |

> 100K × 9,603 稠密是 3.84 GB、1M 是 38.4 GB；按本档实测密度外推，稀疏侧分别约 **12 MB / 120 MB**。

**单测**：`test_sparse_M_equivalence`（逐访问式）、`test_sparse_M_dedupes_repeated_pairs`（重复 `trained_on` 边不能把 1.0 变成 2）、`test_sparse_M_memory_is_a_real_saving`、`test_pool_membership_by_root_equivalence`（对照字面参考实现）、`test_pool_membership_singleton_roots_unchanged`、`test_density_diagnostics_agree`（同 generator ⇒ 同抽样 ⇒ 同估计；分块大小不改变答案）

### ③ 🔴 对比损失采样负例（**D-14 改动冠军配置**）

**改哪**：`losses.contrastive_loss_sampled`（新增）、`sampling.batch_positive_pairs`（新增）、`train.train(contrast_n_neg=)`

**为什么不是"只换个负样本采样"**：原 `contrastive_loss` 会同时活着 5 张 `[B,B]`（`sim` / `weight` / `logits` / `log_prob` + 2 张掩码）。
掩码本身也是 `[B,B]` —— 所以**光换负例不够，正样本掩码也得稀疏化**。

- `batch_positive_pairs`：由 `M` 的 batch 行块直接生成 **(ai, bi) 索引对**，按 dataset 分组展开、去对角、**去重**（一对模型在 3 个 dataset 上共同拔尖仍然只算 1 个正样本 —— 与布尔掩码语义一致），并支持 `max_per_dataset` 上限防止 hub dataset 独吞。
- `contrastive_loss_sampled`：分母 = 该锚点的全部正样本 ∪ `n_neg` 个 batch 内均匀采样负例；同 hub 非正样本仍然乘 `hard_neg_weight`；自身与被采到的正样本从负例侧屏蔽后由正样本侧精确补回（不重复计数）。

**关键设计（让 D-14 成为干净的单变量对拍）**：`n_neg=None` 表示"全 batch 都是负例"，此时该函数与稠密 `contrastive_loss` **数学恒等**，单测断言 `abs < 1e-5`。
⇒ A/B 两行之间**唯一的差别就是采样本身**，不掺杂稀疏化重写带来的任何差异。

**单测**：`test_batch_positive_pairs_matches_dense_mask`（dense/sparse M 两路都与 `batch_contrastive_masks` 的 `pos_mask` 逐元素相等）、`test_contrastive_sampled_equals_dense_when_not_sampling`、`test_contrastive_sampled_hard_negative_weight_matters`、`test_contrastive_sampled_is_bounded_and_differentiable`、`test_contrastive_sampled_approaches_exact_as_n_neg_grows`、`test_batch_positive_pairs_cap`

**A/B 结果见 §4.3。**

### ④ 🔴 分块推理

**改哪**：新文件 [`stage2TrainGraphSAGE/inference.py`](../../stage2TrainGraphSAGE/inference.py)；`export_ours --chunked-infer`、`ablation.train_eval_one(cfg["infer_chunk"])`

**改法**：对每块种子节点取**完整 `num_layers` 跳闭包**（不抽样 —— 抽样属于训练，不属于服务），在导出子图上前向，只取种子行。
L 层 GraphSAGE 的输出恰好只依赖 L 跳邻域，而 L 跳闭包的导出子图包含该邻域用到的每一条边 ⇒ **精确**，差异只来自浮点重结合。

🔴 **行序**：写回一律 `out[nt][seed] = block`（**全局 id**），绝不用块偏移。
`test_chunked_forward_row_order_is_by_global_id` 用不整除的 `chunk_size=37` 逐行比对，并额外断言"第 i 行不等于第 j 行"（否则全塌缩时行序错位也能蒙混过关）。

**实测（真实 12K 图，冠军配置 `num_layers=1`，`chunk=4000`，随机初始化模型）**：

| 图 | 节点类型 | 形状 | `max\|Δ\|` vs 整图前向 | 判定（阈值 1e-5） |
|---|---|---|---|---|
| 全图 | model | (12000, 128) | **2.086×10⁻⁷** | ✅ |
| 全图 | dataset | (3000, 128) | **8.941×10⁻⁸** | ✅ |
| test split | model | (12000, 128) | **1.937×10⁻⁷** | ✅ |
| test split | dataset | (3000, 128) | **1.043×10⁻⁷** | ✅ |

**⇒ G-A2 通过（余量 ~50 倍）。**

**单测**：`test_chunked_forward_matches_full`（chunk ∈ {1, 7, 128, 10000}）、`test_chunked_forward_row_order_is_by_global_id`、`test_chunked_forward_one_layer`

### ⑤ 🔴 流式打分

**改哪**：`scale/global_metrics.py` 新增 `from_embeddings_streaming`；`top1_eval.five_metric_eval` 的 rank 计数重写 + `device=` / `expect_n=`；`export_ours --stream-scores`

**改法**：一个查询的三个 rank（gold / top3 / gap）只依赖**少数几个 probe 模型**的分数。
先算 probe 分数，再**分块流过候选宇宙**统计"严格更好的模型数"，全程不保存完整分数向量，也不再有 `{query: [N]}` 字典。

`five_metric_eval` 同时把 `gold_rank` 与 `gap_rank` 合并成一次分块比较（原来是两趟 + 一个 python `min` 生成器）。

> **发现 F-4（差点算错一名）**：probe 分数走 gather 路径、分块分数走 matmul 路径，
> 同一个模型的两个结果可能**差最后一位**，于是 **probe 会"超过它自己"**，rank 整体 +1。
> 首轮实现就是这么挂的（`assert 345 == 346`）。
> 修法不是放宽容差，而是回到定义：rank 数的是**严格更好**的模型，**没有任何模型严格好过它自己**，
> 所以显式屏蔽对角线。**这一类 bug 在 12K 上只错 1 名，在 100K 上仍然只错 1 名 —— 它不会随规模自己暴露出来，只能靠逐查询对账抓。**

**实测（P3 真实产物，517 个 held-out 查询）**：

| 检查 | 结果 |
|---|---|
| 重写后的 `five_metric_eval` vs P3 存档 `export_report.json` | gold@1 `0.09477756286266925`、gold@10 `0.4158607350096712`、gold-gap@10 `0.5087040618955513`、median gold rank 21 —— **逐位相同** |
| `from_embeddings_streaming` vs `from_embeddings` | **0 / 517** 逐查询 rank 不一致 |
| `five_metric_eval` vs `global_metrics` | **0 / 517** `gold_rank` 不一致 |

**⇒ G-A3 通过。**

**铁律 3 的落点**：`five_metric_eval(..., expect_n=N)` 与 `export_ours --expect-n N` 两处断言，`scale_switches` 回写进 `export_report.json`。

**单测**：`test_streaming_metrics_equal_dense`（3 组分块尺寸，逐查询字典整体相等）、`test_streaming_matches_five_metric_eval`、`test_five_metric_expect_n_fires`、`test_five_metric_gpu_cpu_rank_parity`（有 CUDA 时）

### ⑦ 🟠 HNSW 多线程 + 落盘 + iso-recall

**改哪**：`export_ours.build_hnsw` 增 `threads` / `iso_recall` / `n_query` / `K` / `latency_reps` / `warmup`；新增 `tune_ef_for_recall`；新增 `--hnsw-threads` / `--ef-construction` / `--hnsw-M` / `--iso-recall`；落盘 `ef_tuning.json`（`idx.save_index` 本来就有）。

**iso-recall 协议**（`100kplan §11.2`，比数字更重要）：先倍增再二分出**满足 recall@50 ≥ target 的最小 `ef_search`**，**然后**才计时；计时阶段 `set_num_threads(1)`、逐查询、warmup 100 次丢弃、正式 1000 次、报 p50/p95/p99。
不这么做，"你只是把 recall 调低换速度"一句就打穿。

**实测（P3 真实 `z_m`，12,000 模型，M=32，ef_construction=200，8 线程建索引）**：

| 项 | 值 |
|---|---|
| 建索引 | 207.4 ms |
| 索引内存（估） | 8.8 MB |
| iso-recall 目标 | 0.99 |
| **二分出的 `ef_search`** | **50**（= K，已是下界；trace 只有一步就命中） |
| 实测 recall@50 | **0.9916** |
| p50 / p95 / p99（单线程） | **0.027 / 0.038 / 0.044 ms** |

> 12K 上 `ef_search` 一步就撞到下界 `ef = K = 50`，说明**这一档还没有到 ANN 需要付出代价的规模**。
> 这正是 R2/R3/R4 要做的事：iso-recall 曲线只有在 N 拉开之后才有斜率。**12K 的这一行是曲线的左端点，不是结论。**

**单测**：`test_tune_ef_for_recall`（返回的 ef 确实达标，且所有被探测过的失败 ef 都严格小于它 —— 即它真是搜索得到的最小值）
