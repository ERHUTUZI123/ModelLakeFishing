# 冻结版 F7.2 密集推荐评测资源需求

## 目的

F7.2 用于回答 `gold@10` 无法回答的问题：在目标数据集上没有历史 record 的推荐模型，是否确实是有用的推荐。该协议针对每个 query，使用统一评测流程比较四组候选：推荐得到但未观测的模型、已有 record 的校准模型、全湖随机对照，以及同任务随机对照。

评测范围于 2026 年 8 月 21 日冻结，冻结发生在任何新评测结果产生之前。该工作随后被移出当前范围，可执行 manifest 和实现代码已经删除。下列计数仍可由保留的 F7/F8 导出、合并监督、数据集卡片表及 `RESOURCE_E_AXIS_DENSE_REEVALUATION.md` 中的详细资源审计复算。

## 冻结范围

| 项目 | 冻结数量 |
|---|---:|
| 三个 split seed 去重后的测试 query | 3,794 |
| 能解析到可下载 Hugging Face 数据集仓库的 query | 880（23.2%） |
| 至少保留一个可评测候选的 query | 864 |
| 四组对照均完整的 query | 748 |
| 可用性过滤前的 manifest 行数 | 36,358 |
| 涉及的不同模型 | 19,735 |
| 不同数据集仓库 | 586 |
| 可执行的模型—query 评测 | **30,333** |
| 可执行行中涉及的不同模型 | **16,915** |

其余 2,914 个 query 使用 benchmark 别名、缺少 owner 的名字或私有 evaluator 标签。预先冻结约 100 个常见别名的人工映射表，可将数据集解析率从 23.2% 提高到约 50%，但无法恢复只出现一次的长尾标识符。

## 所需资源

### 计算、传输与存储

| 资源 | 需求 | 证据状态 |
|---|---:|---|
| 评测作业 | **30,333** 次模型—query 评测 | 冻结范围实测 |
| 不同模型获取数 | **16,915** | 冻结范围实测 |
| 模型传输 | **73.5 TB 下界** | 由快照参数元数据推导；缺失大小仅按 0.3B 参数计 |
| GPU 计算 | **约 5,300 GPU-hours** | 根据各任务族单次评测时间估算 |
| 计算风险上界 | 约 **8,700 GPU-hours** | 若 7B+ 生成模型的成本为基准估算三倍 |
| 100 MB/s 持续带宽下的传输时间 | **至少 8.5 天** | 假设全程满速且没有限流 |
| 临时存储 | 持续可用的数 TB 空间 | 滚动下载可以避免同时保存全部 73.5 TB |
| 结果与 provenance 存储 | 数万行结果及其日志、配置和 checksum | 相对模型存储很小，但审计必需 |

73.5 TB 是下界。只有 43% 的入选模型公开参数量；其中 2,182 个超过 1B 参数，1,133 个超过 7B。匿名 Hugging Face 流量存在限速，gated 仓库还需要逐项授权。

### 任务评测系统

| 任务族 | 评测数 | 所需评测路径 | GPU-hours |
|---|---:|---|---:|
| Embedding / MTEB 类 | 11,831 | 标准化 MTEB 任务执行与指标归一化 | 1,577 |
| 需要微调或未分类 | 11,001 | 冻结的适配协议与重新测量的对照组 | 1,834 |
| Generation | 5,040 | 数据集专用 prompt、解码参数、停止规则与指标 | 1,680 |
| ASR | 2,461 | 音频加载、转写、文本规范化与 WER | 205 |
| 合计 | **30,333** | — | **约 5,300** |

需要微调的任务不能直接静默替换为 linear probe，因为两者定义了不同于历史 record 的指标。Generation 任务需要逐数据集确定解码协议，也是计算成本中不确定性最大的部分。

### 工程与访问条件

除 GPU 配额外，执行还需要：

- 支持断点续传并校验 checksum 的模型和数据集获取服务；
- Hugging Face 凭据，以及 14 个 gated 数据集仓库和 gated 模型的授权；
- 按任务族冻结的运行环境，固定模型、tokenizer、音频、数据集和 metric 依赖；
- 对代码缺失、revision 不兼容、自定义模型实现和 OOM 的失败分类；
- 保留 query、候选角色、模型 revision、数据集 revision、指标方向、硬件和失败原因的结果 schema；
- 作业调度、缓存、重试上限和滚动删除策略；
- 评测开始前对约 100 个数据集别名进行人工审查；
- generation 与 adaptation 协议的领域决策；
- 验证同一 query 的四组对照使用相同指标和预处理的质量控制。

## 最小可辩护子集

ASR 和 embedding 任务拥有最标准化的现成 harness。仅运行这两个任务族仍需要：

| 项目 | 需求 |
|---|---:|
| 评测数 | **14,292** |
| 四组对照完整的 query | **367** |
| 模型传输 | **19.7 TB** |
| GPU 计算 | **约 1,780 GPU-hours** |

该子集可以对两个任务族给出受控结果，但不能支持 generation、fine-tuning 或无法解析数据集上的全湖推荐质量结论。

## 墙钟时间含义

在持续满载的理想条件下，完整估算工作量需要：

| 专用计算资源 | 仅计算的墙钟时间 |
|---|---:|
| 1 张 GPU | 约 7.3 个月 |
| 4 张 GPU | 约 1.8 个月 |
| 8 张 GPU | 约 27 天 |

这些时间不包括 73.5 TB 下载、排队、gated 授权、失败重试和工程时间。即使能获得更多 GPU，网络和存储仍是独立瓶颈。

## 现有产物在无需该预算时能证明什么

现有零成本审计显示，top-10 中约 93% 的结果在目标 query 上没有 record，只有很小一部分已知低于历史 best。推荐模型在其他地方拥有同任务证据的比例为 17.2%–22.4%；全湖随机为 0.032%–0.052%，仅从有评测模型中随机为 1.95%–3.36%。

这些对照证明推荐具有非随机的任务相关性，但不能证明未观测推荐在目标数据集上的实际性能。

## 资源缺口说明

F7.2 的阻塞项不是检索实现，而是评测基础设施，以及对**数十 TB 模型数据、数千 GPU-hours、多套任务专用 benchmark 系统、gated 数据权限和持续工程支持**的长期访问。当前项目可以报告历史 record 恢复率和零成本相关性对照，但在缺少上述资源时，无法对未观测推荐的真实质量给出受控的全湖结论。
