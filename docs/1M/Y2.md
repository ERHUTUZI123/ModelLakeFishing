# Y2：HNSW 小池召回 + task 先验重排计划

> 状态：已执行的论文外探索。本实验不修改 X6 baseline，结果暂不纳入论文。

依据：[`X2.md`](X2.md) 的 task 先验、[`X4.md`](X4.md) 的 GD 表示、[`X5.md`](X5.md) 的
eligible-query 口径和 [`X6_baselines_not_finished.md`](X6_baselines_not_finished.md) 的 3M 候选池。

## 1. 要回答的问题

X2 证明 task 先验能显著改善 F6 的排序，但它的全池版需要处理 3,016,439 个模型。
Y2 只回答：

> 先用 X4-GD/HNSW 召回 1,000 个模型，再在这个小池中应用 task 先验，能否保留全池先验排序至少 90% 的 `gold@10`？

不测兄弟先验。X5/X6 的 root-aware split 下，test root 的兄弟也被整体 held out，
X2 已断言该通道在此协议下为空。

## 2. 必须先纠正的参照系

`0.3009` 是 **F6 嵌入 + task 先验**，其稠密对照是 `0.0598`；它不是 X4-GD（`0.1427`）
叠加先验的结果。因此 Y2 首先要在 X4-GD 上重算全池 task-prior 参照，不能用 `0.3009`
直接充当分母。

同时，X2 的稠密分数使用“全池 min--max”归一化，这一步本身就需要全池扫描。
Y2 改用不需要查看全池的固定变换：

```text
dense(q,m) = (cos(z_q, z_m) + 1) / 2
score(q,m) = dense(q,m) + task_prior(q,m)
```

`z_q` 和 `z_m` 已 L2-normalized，因此 `dense` 固定落在 `[0,1]`。task 先验保留 X2 的 shrink `k=5` 和
权重 `beta=1`。Y2 不扫融合权重。全池参照与小池实验都使用这一个分数，才能直接比较。

## 3. 固定口径

| 项 | 固定值 |
|---|---|
| 表示 | X4-GD 的 `z_m_eval` / `z_d_eval` |
| 候选池 | 3,016,439 个模型 |
| 查询 | X5 `gold_eligible`；seed 0/1/2 为 1,476 / 1,101 / 1,545 |
| 主指标 | `gold@10`，同时报告 `gold@1`、`top3@10`、median gold rank |
| task 先验 | X2 定义，shrink `k=5`；对 test query 只读 train+val 边 |
| 第一阶段池 | 固定 `K=1000`，不扫 K |
| 排名 | 主分数降序；并列时用 X6 的固定、标签无关 tie-break |
| 硬件报告 | 记录 CPU/GPU、HNSW 线程数、`ef_search`；同一延迟表不混用不同硬件 |

## 4. 实验步骤

### Y2-A：重算 X4-GD 的全池参照

在全部 3M 模型上计算三行：

1. `G_dense`：纯 X4-GD，必须精确复现 0.1355 / 0.1417 / 0.1508，均值 0.1427。
2. `G_full_task`：使用 §2 固定分数的 X4-GD + task 先验，作为 Y2 的全池参照。
3. `P_task_only`：只用 task 先验，用于判断融合结果是否实际忽略了稠密分数。

若 `G_full_task <= G_dense`，立即停止 Y2：先验在 X4-GD 上没有增益，没有必要建小池版。

### Y2-B：先做 exact top-1000，不立即建 HNSW

用精确内积取得 X4-GD 的 top-1000，只在这 1,000 个模型上加 task 先验并返回 top-10，记为
`G_exact1000_task`。这一行先把“池截断造成的损失”与“HNSW 近似造成的损失”分开，
可以避免在稠密 top-1000 本身就不够时无效建索引。

同时报告：

- `G_exact1000_task.gold@10 / G_full_task.gold@10` 的三 seed 值与均值；
- gold 是否在稠密 top-1000 中（first-stage ceiling）；
- `G_full_task` 的 top-10 有多少成员已在稠密 top-1000 中。

若三 seed 平均保留率低于 90%，Y2 判否并停止：问题是第一阶段没有召回先验偏好的模型，
不是 HNSW 近似误差。

### Y2-C：只在 Y2-B 通过后建 HNSW

为三个 X4-GD held-out 嵌入分别建索引。HNSW 取 top-1000，同样重排后记为 `G_hnsw1000_task`。
`ef_search` 只按精确 top-1000 的 recall 调到首个满足 `recall@1000 >= 0.99` 的值，不按 test `gold@10` 调参。

延迟分开报告：

1. HNSW top-1000 召回时间；
2. 1,000 个候选的 task-prior 查表与重排时间；
3. 两者相加的 end-to-end p50 / p95。

不把索引加载和一次性建索引时间算入单查询延迟，但单独报告索引大小与构建时间。

## 5. 代码门与泄漏检查

尽量写成断言，不作人工检查清单：

- `n_models == 3_016_439`，三 seed 的 model/dataset 映射完全相同。
- eligible query 数必须是 1,476 / 1,101 / 1,545。
- prior sidecar 的每条边只属于对应 seed 的 train+val message graph；不得出现 test 数据集边。
- 查询自身的评测边必须为空；root-aware 协议下 sibling 先验必须仍断言为空。
- X2/F6 与 X4-GD 的 sidecar 复用前，必须断言 model id、dataset id、task id 逐行一致。
- exact top-1000 必须是 1,000 个唯一 mappedID；HNSW 结果也必须唯一且属于全池。
- `G_dense` 与 X5/X6 已发布的逐 seed `gold@10` 不一致时，报告不得写出。

## 6. 预注册判据

| 判据 | 处理 |
|---|---|
| `G_full_task <= G_dense` | task 先验在 X4-GD 上无增益，Y2 停止 |
| `mean(G_exact1000_task / G_full_task) < 0.90` | top-1000 池不够，Y2 判否，不建 HNSW |
| exact 池通过，但 `recall@1000 < 0.99` | 只能说索引参数未达标，不能归因于先验 |
| `mean(G_hnsw1000_task / G_exact1000_task) < 0.98` | HNSW 近似损失过大，不接受为部署方案 |
| 上述门均通过 | 可以说“top-1000 两阶段检索保留了全池 task-prior 排序的大部分精度” |

比值均先逐 seed 计算再取平均，同时报告三个原始比值；不用均值之比替代。

1. 实现 sidecar/mapping/泄漏断言与 Y2-A。
2. 执行 exact top-1000 的 Y2-B；若保留率不足 90%，停止。
3. 仅在 Y2-B 通过后构建三个 HNSW 索引，调到 `recall@1000 >= 0.99`。
4. 执行 Y2-C 的精度与延迟测量，写出报告，不修改论文。

## 9. 执行结果

执行日期：2026-09-04。完整机器可读报告为
[`Y2_runs/Y2_REPORT.json`](Y2_runs/Y2_REPORT.json)。

### 9.1 精度

| 排序 | seed 0 | seed 1 | seed 2 | 均值 `gold@10` |
|---|---:|---:|---:|---:|
| `G_dense`：X4-GD | 0.1355 | 0.1417 | 0.1508 | **0.1427** |
| `P_task_only`：全池 task 先验 | 0.3327 | 0.3224 | 0.2278 | **0.2943** |
| `G_full_task`：全池 X4-GD + task 先验 | 0.3408 | 0.3651 | 0.2589 | **0.3216** |
| `G_exact1000_task`：exact top-1000 + task 先验 | 0.3286 | 0.3388 | 0.2427 | **0.3034** |
| `G_hnsw1000_task`：HNSW top-1000 + task 先验 | 0.3279 | 0.3388 | 0.2427 | **0.3031** |

先验在 X4-GD 上仍然有效：全池融合相对纯 X4-GD 是 2.25x。但 `P_task_only=0.2943`
已经接近融合结果，说明增益主要来自历史 task 先验，不是稠密表示本身。

exact top-1000 相对全池融合的保留率为 96.42% / 92.79% / 93.75%，三 seed 平均
**94.32%**，通过 90% 门。HNSW 相对 exact top-1000 的保留率为 99.79% / 100% / 100%，
平均 **99.93%**，通过 98% 门。从最终 HNSW 方案直接对全池融合计算，三 seed 平均保留率为
**94.25%**。

稠密 top-1000 包含 gold 的查询比例为 56.57% / 59.40% / 39.68%，均值 51.88%。
全池融合 top-10 中已经位于稠密 top-1000 的成员比例均值为 89.91%。因此剩余约 5.7% 的
`gold@10` 损失主要来自第一阶段池截断，不是 HNSW 近似误差。

### 9.2 HNSW 与延迟

| seed | `ef_search` | `recall@1000` | HNSW + 重排 p50 | HNSW + 重排 p95 |
|---:|---:|---:|---:|---:|
| 0 | 1000 | 0.9923 | 0.546 ms | 0.907 ms |
| 1 | 1500 | 0.9941 | 0.885 ms | 1.828 ms |
| 2 | 1500 | 0.9932 | 0.810 ms | 1.651 ms |

三 seed 的 end-to-end p50 平均为 **0.747 ms**，其中 task-prior 查表与 1,000 项重排的 p50
为 0.131 / 0.137 / 0.130 ms。每份索引约 2.214 GiB，三份合计 6.643 GiB；构建时间为
184.6 / 191.3 / 181.6 s，合计 557.5 s。

延迟在同一台 Windows 11 机器上用单查询、单 HNSW 查询线程测得；CPU 为 Intel64 Family 6
Model 183，24 个逻辑核。exact 3M 流式评测使用 RTX 4060 Laptop GPU。索引加载和建库时间不计入单查询延迟。

### 9.5 论文外结论

Y2 成立：**HNSW top-1000 + task 先验重排在不扫描全池的情况下，保留了全池融合约 94.3% 的
`gold@10`，并将平均 `gold@10` 从 X4-GD 的 0.1427 提高到 0.3031。** 实测损失几乎全部来自
top-1000 池的召回上限，HNSW 近似本身只造成 0.07% 左右的相对损失。

这说明现有 task 先验可以做成亚毫秒级两阶段检索，不必立即进行先验蒸馏。但它仍然主要利用历史评测统计，
不表示 X4-GD 的向量表示本身学到了这部分信号；按 Y0 的定位，暂不将它写入论文。
